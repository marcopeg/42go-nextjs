# Enable Per-URL Install Targets and Installable Quicklist Virtual Apps

## Elevator's Pitch

Allow a user to install an individual Quicklist list as its own virtual home-screen or desktop app. Each installed list opens directly at `/quicklists/<list-id>`, has a stable per-list web-app identity, and uses its list title. The framework supports fully dynamic icons, colors, and related presentation fields; Quicklist version one inherits the base app icon and colors.

This task began as an investigation and memory dump. Refinement approved implementation planning for the reusable framework and the first Quicklist vertical slice.

## Business Gain

Users could pin the lists they use most as distinct app-like launchers, giving one-tap access to groceries, chores, work, or other contexts without first opening Quicklist and choosing a list. A list icon could also improve recognition in the main list index.

## Current State

### Feasibility verdict

The feature is technically achievable, but not by changing only `start_url` and not with the current single global manifest/head implementation.

A correct implementation needs all of the following:

- a manifest linked from the list-install context;
- a stable, unique manifest `id` per list;
- a list-specific `start_url`;
- a deliberate `scope` strategy;
- list-specific manifest and Apple icon metadata;
- an authorization-safe dynamic manifest response;
- platform-specific installation UX;
- physical-device validation for same-origin installation and scope behavior.

Confidence is high that iOS/iPadOS and Chromium can represent distinct installed web apps by manifest identity. Confidence is medium that the desired same-origin, overlapping-scope experience will behave consistently enough across every target. Google supports multiple same-origin PWAs but explicitly discourages the arrangement because storage, permissions, uninstall behavior, and navigation scopes are not fully independent.

### Current Quicklist PWA pipeline

- `src/config/quicklist/config.ts` defines one app-level PWA:
  - `name: "QuickList"`
  - `shortName: "QuickList"`
  - `startUrl: "/quicklists"`
  - `scope: "/"`
  - `display: "standalone"`
- `src/app/manifest.ts` generates one request-resolved `/manifest.webmanifest` from `config.public.pwa` and `resolveAppIcons()`.
- The manifest does not emit an explicit `id`. By the manifest standard and Chromium behavior, the effective fallback identity is derived from `start_url`; for Quicklist that is currently `/quicklists`.
- `src/app/layout.tsx` generates app-level favicon, Apple icon, application name, Apple Web App metadata, and theme color.
- `src/42go/pwa/HeadTags.tsx` emits legacy Apple PWA tags and another Apple touch icon.
- `src/proxy.ts` excludes the root `/manifest.webmanifest` from proxy matching, although `getAppInfo()` can still resolve Quicklist from the request host. A nested list manifest route would not match that exact exclusion and would pass through the proxy.
- `src/42go/pwa/types.ts` has no `id` field in `TPWAConfig`, but the installed Next.js `MetadataRoute.Manifest` type does support `id`.
- No service worker is registered. Current Chrome and Edge can still install from browser UI without one. Offline behavior, push, and background features remain out of scope.

### Live verification on 2026-07-17

`https://ql42go.ngrok.app/manifest.webmanifest` returned HTTP 200 with `application/manifest+json`, `Cache-Control: public, max-age=0, must-revalidate`, and:

```json
{
  "name": "QuickList",
  "short_name": "QuickList",
  "start_url": "/quicklists",
  "scope": "/",
  "display": "standalone",
  "icons": [
    { "src": "/app-icons/quicklist/manifest-192x192.png" },
    { "src": "/app-icons/quicklist/manifest-512x512.png" },
    { "src": "/app-icons/quicklist/maskable-512x512.png", "purpose": "maskable" }
  ]
}
```

The response has no explicit `id`.

The live HTML contains the global `<link rel="manifest" href="/manifest.webmanifest">`. It also contains duplicate Apple Web App title/status tags and two 180px Apple touch icon links because both `HeadTags` and generated Metadata emit them.

This matters for per-list installation:

- The HTML standard says only the first manifest link in tree order may be used. Adding a list manifest as a second link is not a valid solution.
- WebKit says `apple-touch-icon` takes precedence over manifest icons on iOS/iPadOS. Leaving the global Quicklist Apple icon in the document can override the desired list icon.
- The PWA/head layer therefore needs one authoritative manifest and one authoritative Apple title/icon for the current install context.

### Current Quicklist list/settings model

- List detail route: `src/app/(app)/quicklists/[id]/page.tsx`.
- List info/settings route: `src/app/(app)/quicklists/[id]/info/page.tsx`.
- The detail page is a client component and cannot itself export server `generateMetadata`.
- The current Info page handles collaborators, invitations, leave, and delete. It is the natural settings entry point for an install section or a link to a dedicated install-preparation page.
- `quicklist.projects` stores `app_id`, UUID `id`, `title`, ownership, and timestamps. It has no icon or install metadata.
- The project list API and `ProjectItem` return/render title, role/ownership, and update time only.
- Any list icon shown in the index requires a DB field, API response changes, and an icon-key-to-component mapping.

## Desired State

### Refinement decisions — round 1

- `AppConfig.public.pwa` gains a declarative area for one or more URL-pattern overrides.
- A matching pattern selects a named server-only resolver. The resolver may dynamically load authorized database data and override the launch URL, name, icon set, colors, scope, display mode, and other supported manifest/head fields.
- AppConfig contains only serializable pattern and resolver-key declarations. Database-aware resolver functions stay outside the client-imported AppConfig object.
- The first delivery includes both the reusable 42Go framework and Quicklist as its complete reference consumer.
- Quicklist version one registers list URLs and overrides only the stable list identity, list-specific launch URL, and application name derived from the current list title. It inherits the base Quicklist icon, colors, display mode, and initial shared scope.
- Dynamic per-list icons and colors must be supported by the framework contract, but storing/editing them in Quicklist is deferred beyond the first pass.
- Device/browser testing remains required. Detecting, enumerating, or persisting which lists are installed is explicitly out of scope.

### Refinement decisions — round 2

- Each Quicklist list is one **virtual app** with a stable manifest identity based on its immutable list UUID.
- Every validated route belonging to the list, including `/quicklists/<uuid>` and nested pages such as `/info`, resolves to the same virtual-app identity and canonical `startUrl: /quicklists/<uuid>`.
- Native browser Add to Home Screen must work from every matched list route.
- The existing list Info page receives a reusable 42Go **Install this list** action. Chromium uses the native prompt when available; iOS/iPadOS and Safari receive manual platform instructions.
- Any authenticated owner or collaborator with current access may resolve the list manifest and install the virtual app.
- Installation never changes authorization. Revoked/deleted access blocks future manifest resolution and launches through the normal safe unavailable/login behavior.

### Product outcome

A user with access to a list can install or receive exact platform instructions. Installed list A and list B coexist, display their respective list titles, and launch their own list routes. Version one inherits the base Quicklist icon and colors; later Quicklist settings may exercise the framework's dynamic icon/color support.

The product calls each installed list a **virtual app**. This describes its separate identity, name, and launch destination without claiming origin-level isolation. Same-origin installs intentionally share server-side data and, on Chromium, origin-level browser storage and permissions.

### Version-one UX

1. Every matched list route renders the list-specific installation metadata automatically.
2. The existing Info page shows **Install this list** using the generic 42Go install component.
3. The displayed/default application name is the current list title; version one offers no separate stored install-name editor.
4. Version one previews and inherits the base Quicklist icon and colors.
5. Chromium Android/desktop shows a real **Install** button only after `beforeinstallprompt` fires and calls the saved event's `prompt()` from the click.
6. iPhone/iPad shows Share → Add to Home Screen instructions. On iOS/iPadOS 26, remind the user to leave **Open as Web App** enabled. JavaScript must not claim it can open the native flow.
7. macOS Safari shows File/Share → Add to Dock instructions.
8. Unsupported or ambiguous contexts show concise manual instructions without claiming installed-state knowledge.

The absence of `beforeinstallprompt` is not a reliable universal “already installed” signal. It can also mean unsupported browser, failed criteria, insufficient engagement, or an install context that the browser refuses to prompt from.

## Definition of Success

The feature is successful when list A and list B can coexist as installed launchers on validated iPhone, Android, and desktop targets; each opens its own authorized list and displays its list-derived name; inherited icon behavior is honest per platform; the base Quicklist and other 42go apps keep their existing PWA identity; and loss of list access fails safely.

Before full implementation, complete a narrow technical spike that proves:

1. a list route renders exactly one effective manifest link and one effective Apple icon;
2. the authenticated manifest is fetched with credentials;
3. two manifests with different stable IDs install side-by-side in Chrome Android and desktop;
4. two list launchers install and launch correctly on iOS/iPadOS;
5. the chosen scope does not create unacceptable navigation or link-capture behavior;
6. installing a list from inside an already-installed Quicklist app has a workable browser handoff or instruction flow.

## Additional Context

### Web platform findings

#### Manifest fields have different jobs

- `start_url` is the preferred URL opened from the installed icon. It is advisory, but Apple and Chromium document it as the launch URL.
- `id` is the stable web-app identity. The W3C says a different identity should be treated as a distinct app even when served from the same manifest URL. If `id` is missing, it falls back to `start_url`.
- `scope` defines which navigations remain in the app context. It is not an access-control boundary and does not isolate cookies, local storage, or permissions.
- `name` and `short_name` supply the installed label, subject to platform UI and user choice.
- `icons` supply launcher/task-switcher artwork. On iOS, an HTML `apple-touch-icon` overrides manifest icons.

A list manifest should use a stable identity that never depends on mutable title or icon, for example:

```json
{
  "id": "/quicklists/<list-id>",
  "name": "Groceries",
  "short_name": "Groceries",
  "start_url": "/quicklists/<list-id>",
  "scope": "/quicklists/",
  "display": "standalone"
}
```

The base Quicklist manifest should gain `id: "/quicklists"` so its explicit ID matches its current computed identity and does not accidentally become a new app after deployment.

#### iPhone and iPad

- WebKit states that iOS has always supported multiple installs of the same web app.
- Since iOS/iPadOS 16.4, WebKit supports manifest `id`. Apple combines the user-selected installed name with manifest ID for identity/Focus behavior.
- Apple explicitly presents distinct same-domain app IDs as useful for separate parts such as `/shop` and `/forums`.
- Apple confirms `start_url` is loaded when a Home Screen web app first opens.
- Since iOS/iPadOS 17.2, login cookies are copied into a newly created Home Screen web app. After installation, its cookies/storage are isolated from the browser and from other installed instances. Quicklist's cookie-based NextAuth session should therefore copy at install time, but logout/session changes can diverge between installed list apps.
- iOS/iPadOS has no supported `beforeinstallprompt` flow. The current WebKit request for that API remains a feature request. The product must provide instructions, not promise a native prompt from its button.
- iOS/iPadOS 26 lets any site be added with an **Open as Web App** toggle, enabled by default. A manifest is still useful for ID, start URL, name, icon, scope, and display behavior.
- Users can edit the name in the Add to Home Screen sheet. The web app controls its supplied icon; choosing an arbitrary photo is a Shortcuts feature, not normal web-app installation behavior.
- iOS gives `apple-touch-icon` precedence, so the current global Quicklist Apple icon must be replaced/overridden cleanly for the install page.

#### Android and desktop Chromium/Edge

- Chromium 96+ supports manifest `id` and treats a non-matching ID as a new PWA.
- Chrome supports multiple PWAs on one origin, including overlapping/nested scopes, but Google discourages it.
- Same-origin apps share cookies, local storage, storage quota, browser permissions, and some user settings. Uninstalling one app and choosing to clear its data can affect every app on the origin.
- Overlapping scopes can cause ambiguous notification attribution and link capture. Quicklist currently has no push, badges, URL handlers, or service worker, which reduces but does not eliminate the risk.
- Chrome's current prompt criteria include HTTPS, user engagement, a name, 192px and 512px icons, `start_url`, and an app-like `display`. The current Quicklist manifest has these fields.
- A service worker is no longer required for installation from Chrome's menu or Edge installation. It is still relevant to offline/push behavior, not this first feature.
- `beforeinstallprompt` can power an in-product button on supported Chromium browsers. The event must be captured, can be prompted only once, and still leads to browser confirmation.
- Chrome/Edge 148 introduced experimental `<install>` and `navigator.install()` origin trials. They are not stable enough to be the MVP dependency as of this investigation.
- Chrome may later update manifest name/icon/start URL. Some changes ask the user for confirmation. iOS and several mobile platforms require reinstalling to receive changed manifest metadata. Do not promise that renaming a list will rename an already-installed icon.

#### Desktop Safari and Firefox

- macOS Safari 14+ (Sonoma) can add any page to the Dock. The user can set the installed name and later change the app URL and icon. There is no documented JavaScript-triggered Add to Dock flow.
- Safari web apps copy current cookies at install and then isolate their website data from Safari.
- Firefox for Windows 143+ can pin any site as a web app. Firefox web apps are not currently available on macOS or Linux. Manifest-ID behavior for multiple same-origin Quicklist lists needs a physical/browser test rather than an assumption.

### Recommended technical architecture

#### Framework-level goal: make any same-origin URL an install target

The reusable 42Go feature should not be "Quicklist list manifests." It should be an **install-target system** that can describe any authorized same-origin URL as a distinct installable web app.

The framework contract should separate these concerns:

- application code decides **what** is installable and supplies resource data;
- 42Go decides **how** to validate it, render the head, serve the manifest, and drive the browser-specific installation flow.

An install target needs more than a URL. It needs a stable browser identity and presentation data:

```typescript
export type TPWAInstallTarget = {
  id: string;
  startUrl: string;
  scope: string;
  name: string;
  shortName?: string;
  description?: string;
  display?: "standalone" | "fullscreen" | "minimal-ui" | "browser";
  themeColor?: string;
  backgroundColor?: string;
  statusBarStyle?: "default" | "black" | "black-translucent";
  icons: {
    appleTouch180: string;
    manifest192: string;
    manifest512: string;
    maskable512: string;
  };
};
```

`id` and `startUrl` must remain separate. `startUrl` may change when routing changes; `id` must remain stable or the browser sees a different application. "Any URL" means any validated URL on the currently resolved 42Go app origin. It does not mean that a client may submit an arbitrary external URL or arbitrary manifest fields.

##### A. Add declarative AppConfig patterns backed by a server-only install-target registry

Extend the PWA area of AppConfig with serializable URL-pattern overrides, conceptually:

```typescript
public: {
  pwa: {
    // Existing app-level defaults.
    name: "QuickList",
    startUrl: "/quicklists",
    scope: "/quicklists/",

    targets: [
      {
        pattern: "/quicklists/:projectId{/**}",
        resolver: "quicklist-project",
      },
    ],
  },
}
```

The exact pattern syntax should be selected during planning and covered by tests. It must support one or more patterns, extracted parameters, exact or nested matching, and UUID validation by the resolver.

Add the corresponding server-only registry and resolver implementation under `src/42go/pwa/server/`. Each registered resolver should have:

- an AppID constraint;
- a cheap pathname matcher;
- an asynchronous resolver that loads and authorizes dynamic data only after the path matches;
- a stable target key or identity;
- an explicit unavailable result for missing, unauthorized, or unsupported targets.

Conceptual server API:

```typescript
export type TPWAInstallTargetDefinition = {
  key: string;
  resolve: (
    context: TPWAInstallTargetContext
  ) => Promise<TPWAInstallTarget | null>;
};
```

The pattern declaration belongs in AppConfig as requested, but the registry implementation must be server-only because a resolver may import the database, session, and authorization code. `useAppConfig()` imports the same `apps` object into client components, so putting database-aware resolver functions directly there risks crossing the server/client boundary. A named resolver key gives AppConfig the configuration surface without shipping database code to the client.

At startup or first resolution, validate that every configured resolver key exists, that keys are unique, and that no ambiguous pattern ordering can silently select the wrong target. Matching should use declaration order only if precedence is explicit and tested.

The static `public.pwa` configuration remains the fallback install target for the whole app. Dynamic registrations override it only on matching install contexts.

##### B. Give the framework a trusted current pathname

The root layout currently knows the AppID but has no reliable pathname. `src/proxy.ts` should:

- delete any incoming public pathname header;
- write a reserved internal pathname header from `request.nextUrl.pathname`;
- continue writing the resolved AppID header;
- include manifest endpoints in AppID resolution instead of excluding them accidentally.

The header needs a shared constant, just like `APP_ID_HEADER`, and must never trust a caller-supplied value. `resolvePWAInstallTarget()` can then use AppID plus pathname to select the correct target before server-rendering the page head.

Path matching should happen before dynamic loading so ordinary routes do not pay for a database/session query. Only a registered install context should resolve resource data.

##### C. Centralize all PWA head output

42Go must render one authoritative set of installation metadata for the resolved target:

- exactly one `<link rel="manifest">`;
- `crossorigin="use-credentials"` when the manifest is authorization-dependent;
- exactly one `apple-touch-icon`;
- one Apple Web App title/capability/status set;
- application name, favicon, theme color, and background color derived from the same target.

The current `src/app/manifest.ts` automatic file convention should be replaced by an explicitly linked framework manifest route, because the automatic link cannot express authenticated `crossorigin` and is difficult to replace per route. The duplicated responsibilities in root `generateMetadata()` and `HeadTags` should be collapsed into a single 42Go PWA head resolver/component.

This is the critical framework change. If both the base app manifest and the resource manifest are present, the feature is not deterministic.

##### D. Add one generic manifest delivery route

Add a framework-owned route such as:

```text
/api/42go/pwa/manifest/<target-key>.webmanifest
```

or an equivalent stable route whose parameters contain only an opaque/stable target key. The route should call the same install-target resolver used by the page head. It must not accept name, icons, scope, or redirect URLs directly from query parameters.

The manifest route must:

- resolve and verify AppID;
- validate the target key/path;
- load the session when required;
- delegate resource authorization to the registered resolver;
- validate all returned URLs as same-origin root-relative paths;
- verify that `startUrl` is compatible with the declared scope;
- emit an explicit stable `id`;
- return 404 rather than leak inaccessible resource metadata;
- send `Content-Type: application/manifest+json`;
- use private/no-store caching and `Vary: Cookie` for user-specific manifests;
- use public caching only for static app-level manifests.

The rendered manifest link and manifest endpoint must use the same stable key, so a title or icon change updates presentation without changing app identity.

##### E. Provide framework validators and safe defaults

Add pure helpers under `src/42go/pwa/` for:

- normalizing root-relative paths;
- rejecting absolute/cross-origin/protocol URLs;
- validating `id`, `startUrl`, and `scope` relationships;
- validating required 180/192/512/maskable icon slots;
- truncating or rejecting invalid names rather than emitting malformed manifests;
- converting static `TPWAConfig` into the same `TPWAInstallTarget` shape;
- preserving the existing computed identity when an old app config has no explicit `id`.

Extend `TPWAConfig` with an optional explicit `id`. Existing apps should continue working, but each should eventually receive an explicit ID before the framework migration to prevent accidental reinstall identities.

##### F. Provide a reusable client installation controller

Add a client hook/component such as `usePWAInstall()` and `InstallAppAction`. It should own:

- capturing and retaining `beforeinstallprompt` on Chromium;
- exposing `prompt-ready`, `manual-instructions`, `standalone`, and `unsupported/unknown` states;
- calling `prompt()` only from a user gesture and only once;
- recording the browser's accepted/dismissed result without pretending it proves installation forever;
- detecting iOS/iPadOS and Safari only to choose instructions, not to fake a native prompt;
- explaining how to continue in the browser when installation started inside an existing standalone PWA.

This component must not receive manifest identity or arbitrary URLs from the browser. The server-rendered install target remains authoritative. The component only controls presentation and the available browser prompt.

##### G. Keep route authorization independent

Installing a URL never grants access. The installed `startUrl` must still pass normal `protectPage`, session, feature, and resource authorization checks on every launch. If access is lost, the destination returns the safe unavailable/login experience.

The manifest resolver and target page may share an authorization helper, but neither should infer authorization from knowledge of the UUID or manifest URL.

##### H. Make application integration deliberately small

After the framework exists, a feature such as Quicklist should need only to:

1. register a pathname matcher and server resolver;
2. load/authorize the list and return `TPWAInstallTarget` data;
3. expose an install-preparation page or settings entry using the framework install action;
4. provide static icon assets or allow-listed icon keys;
5. keep the launch page protected as usual.

Quicklist should not create its own `<link rel="manifest">`, Apple meta tags, user-agent parsing, or `beforeinstallprompt` implementation. Those belong to 42Go once.

##### I. Suggested 42Go module layout

```text
src/42go/pwa/
├── types.ts                         # static config + install-target contracts
├── validation.ts                    # same-origin/path/identity/icon validation
├── target-from-config.ts            # app-level fallback adapter
├── HeadTags.tsx                     # the sole PWA head renderer
├── InstallAppAction.tsx             # reusable progressive install UI
├── usePWAInstall.ts                 # Chromium event + platform state
└── server/
    ├── registry.ts                  # server-only target definitions
    ├── resolve-install-target.ts    # AppID/path/key resolution
    └── manifest-response.ts         # validated response and cache headers

src/app/api/42go/pwa/manifest/[key]/route.ts
src/PWAInstallTargets.ts             # project/app registrations, server-only
```

The exact route and filenames can change during planning. The boundary should not: generic mechanics under `src/42go`, project registrations outside it, and resource data resolvers in their owning app modules.

##### J. Framework migration sequence

1. Add types, validation, explicit static IDs, and tests without changing rendered output.
2. Add the trusted pathname header and server-only registry.
3. Add the generic manifest response route and static app fallback adapter.
4. replace the automatic `src/app/manifest.ts` link with the single explicit PWA head renderer.
5. Remove duplicate Apple metadata and verify existing Quicklist/LingoCafe/Notes installs keep their IDs and icons.
6. Add the reusable client install controller.
7. Register one Quicklist list-install target as the first dynamic consumer.
8. Run the physical-device matrix before exposing the feature broadly.

##### Framework-level success criteria

- A test route can register two URLs on the same app origin with different IDs, names, start URLs, scopes, and icons.
- The two targets render exactly one credential-aware manifest link and one Apple icon each.
- Both dynamic manifests use the common route, resolver, validation, cache, and authorization pipeline.
- Normal routes continue using the static AppConfig PWA without dynamic database work.
- App code contains no raw Apple/PWA head tags and no browser-specific install-event plumbing.
- Existing app-level PWA identities survive the migration.
- Invalid, cross-origin, cross-app, and unauthorized targets fail closed.

#### 1. Make identity explicit

- Extend `TPWAConfig` with optional `id`.
- Emit `id: "/quicklists"` for the base Quicklist manifest to preserve its existing computed identity.
- Emit `id: "/quicklists/<project-id>"` for a list launcher.
- Never derive ID from list title, owner, installed name, icon, or a mutable version.

#### 2. Add an authorized dynamic list manifest

Candidate route: `/quicklists/<project-id>/manifest.webmanifest` or `/api/quicklists/<project-id>/install-manifest`.

The handler must:

- validate UUID and current AppID;
- require a valid session;
- authorize owner or collaborator exactly as the list GET does;
- return 404 for missing, cross-app, or inaccessible lists;
- return `application/manifest+json`;
- use `Cache-Control: private, no-store` and `Vary: Cookie` if content varies by user;
- emit stable ID/start URL and only allow same-origin URLs;
- use static allow-listed icon URLs;
- never expose title or ownership from an unauthenticated endpoint.

Manifest fetches omit credentials by default, even on the same origin. The list page must link it with:

```html
<link
  rel="manifest"
  href="/quicklists/<project-id>/manifest.webmanifest"
  crossorigin="use-credentials"
>
```

Next.js Metadata's `manifest` field accepts only a URL and cannot express `crossorigin` in the installed local type. The implementation therefore needs an explicit server-rendered link or another proven mechanism.

#### 3. Guarantee one manifest link

The root `src/app/manifest.ts` file convention automatically injects the global manifest link. A list-specific second link is unsafe because browsers may use only the first.

The spike must choose and prove one of these approaches:

- replace the automatic root convention with explicit route-aware manifest linking;
- make the root PWA head component choose the correct manifest using a trusted pathname header injected by `src/proxy.ts`;
- prove that nested Next.js metadata replaces rather than duplicates the file-convention link, then separately solve authenticated `crossorigin`.

Do not ship until rendered HTML confirms exactly one effective manifest link on the list install page and the normal app pages.

#### 4. Remove duplicate Apple metadata

Consolidate `src/app/layout.tsx` and `src/42go/pwa/HeadTags.tsx` so list-install HTML has one effective:

- `apple-mobile-web-app-title`;
- `apple-touch-icon` at 180px;
- app-capable/status-bar declaration.

The list Apple icon must be selected from the same semantic icon key as the list-index icon.

#### 5. Support dynamic icon/color overrides, but defer Quicklist persistence in version one

The 42Go target contract and resolver must allow icons, theme color, background color, display mode, and related fields to be fully dynamic. A resolver may read these values from the database and fall back field-by-field to the app-level PWA defaults.

Quicklist version one intentionally uses only:

- stable per-list manifest ID;
- `startUrl: "/quicklists/<project-id>"`;
- name/short name derived from the current list title.

It inherits the base Quicklist icons and colors. This keeps the first slice focused on proving multiple installed identities and launch routing. Per-list icon persistence and editing remain a follow-up built on the already-supported framework fields.

Future recommended Quicklist icon model:

- `quicklist.projects.icon_key`: shared, owner-editable, allow-listed semantic icon key;
- list title remains the default install name;
- if Chromium pre-install renaming is a hard requirement, add a per-user/per-list install preference table with `user_id`, `project_id`, and `install_name`.

Do not place user-provided name/icon in query parameters. The manifest URL must remain stable and should not become a tracking identifier.

Prefer a curated icon catalog with committed 180, 192, 512, and maskable PNG assets per key. Map the same keys to Lucide components for the list index. This avoids runtime rasterization, arbitrary uploads, content-type problems, and private icon endpoints.

Ownership decision:

- owners may change the shared list icon;
- collaborators may install using that icon;
- changing the shared icon must not promise immediate changes to existing installed launchers.

#### 6. Choose scope consciously

Three options need a spike:

1. `scope: "/"` or `"/quicklists/"` — smallest code change, but every list launcher overlaps the base app and every other list.
2. Per-list `scope: "/quicklists/<id>/"` — separates list scopes, but the current canonical detail URL and back/profile navigation need trailing-path and out-of-scope handling.
3. Dedicated install shell such as `/installed-lists/<id>/...` — clean non-overlapping scopes and best browser semantics, but requires more routing/UI work.

Recommendation: test option 1 as a minimal launcher spike and option 3 as the robust design. Do not treat scope as a security control. Separate subdomains offer real origin isolation but are disproportionate for one launcher per dynamic list and complicate auth, host matching, DNS, and certificates.

#### 7. Handle lifecycle honestly

- List renamed: new browser visits use the new manifest name; existing installed names/icons may remain until browser update, user approval, or reinstall.
- List icon changed: update the list index immediately; installed launcher update varies by platform.
- List deleted or access revoked: installed launch must show a safe “List unavailable” state with a path to `/quicklists` or login. The site cannot reliably uninstall the launcher.
- User logs out in one iOS list app: other installed list apps may retain isolated sessions.
- User uninstalls a Chromium list and clears data: shared origin data/session for other Quicklist installs may be cleared.
- There is no reliable cross-browser API that lists every installed per-list launcher. HV34 does not need to detect, enumerate, or persist installed lists. Prompt outcomes may be logged only if general product telemetry later requires them; they are not part of installation state.

## Implementation Outcome

The accepted framework and Quicklist vertical slice are implemented.

- `public.pwa.targets` now maps serializable URL patterns to named server-only resolvers, with validation for patterns, templates, same-origin paths, identities, scopes, icons, and resolver output.
- A trusted request pathname, server-only resolver registry, and explicit `/manifest.webmanifest` route resolve static or authorization-dependent install targets without exposing database logic to client AppConfig imports.
- The PWA head pipeline emits one authoritative, credentialed manifest link and one Apple touch icon. Crossing between base and virtual-app identities performs one full-document reload so browsers parse the server-resolved manifest as primary; navigation inside one virtual app stays client-side. Dynamic targets also set the document title as Safari fallback metadata.
- 42Go now provides a framework install provider, capability hook, and reusable install action. Chromium can use `beforeinstallprompt`; Apple and unsupported contexts receive honest instructions in the shared Modal.
- Quicklist registers every `/quicklists/<uuid>` route and nested route as one virtual app. Its immutable list UUID supplies the stable manifest identity and canonical launch URL; the current authorized list title supplies the app name. Base icons, colors, display mode, and shared `/` scope are inherited in version one.
- Dedicated list installs carry an exact target marker only in `start_url`. Standalone mode plus that launch/session context removes the list-detail back button; ordinary browser use and the installed base QuickList app retain it. The stable manifest ID and all authorization behavior remain unchanged.
- The dedicated installed list app also omits **Install this list** from its Info page. Browser and base QuickList contexts retain the action so they can create a separate list launcher.
- The OS-customized launcher label cannot replace the in-app list title because browsers do not expose that user-edited installation metadata to the document. The manifest name remains an input/default, not a readable installed-instance property. A synchronized custom title would require an app-owned setting chosen before installation.
- The existing list Info page exposes **Install this list** to owners and collaborators. Installed-list discovery and persistence were not added.
- Focused tests, TypeScript, targeted lint, the full repository QA build, and diff hygiene pass. Live desktop verification proved two different authorized lists produce different private manifests and that unauthenticated, malformed, cross-app, and external targets fail closed.
- The post-implementation security assessment found no direct authorization bypass, cross-app data leak, SQL injection, XSS, open redirect, CSRF state change, or private-cache leak. Current application-layer risk is low; the material residual concerns are installed-session lifecycle and persistence of list names in device/browser metadata.
- Physical-device coexistence and launch testing on iOS/iPadOS and Android remains open. The available browser could not apply the requested mobile viewport, so responsive mobile verification is also not claimed.

## Assumptions

- The intended unit of installation is one launcher per list, not multiple custom copies of the same list.
- A list-specific launcher remains on the existing Quicklist origin and uses normal Quicklist authorization.
- Users accept that iOS installed instances have isolated local sessions while Chromium same-origin installs share origin-level storage and permissions.
- The list icon is shared list data; a custom installed name may be per-user install data.
- The project continues to support current browsers, but UI progressively enhances rather than forcing one universal install flow.

## Constraints

- Keep the request-resolved multi-app behavior intact: Quicklist and LingoCafe must continue to expose their own app-level PWA metadata.
- Do not expose private list metadata or access through a manifest; normal authentication and list authorization must still apply after launch.
- Preserve the base Quicklist manifest identity when adding an explicit `id`.
- Render only one effective manifest link and Apple touch icon for the install context.
- Do not use scope, UUID secrecy, or a manifest URL as authorization.
- Do not base the MVP on an origin trial or experimental install API.
- Do not promise offline operation; there is no current service worker.
- Implement only from an accepted plan; the operator accepted and authorized this plan with `plan and execute it`.

## Dos

- Keep platform claims separate; do not assume iOS, Android, and desktop install semantics match.
- Prefer primary standards and vendor documentation for browser behavior.
- Treat list titles, icons, and access as mutable application data.
- Preserve stable manifest IDs across name, icon, and start URL changes.
- Feature-detect install capabilities and always offer manual instructions.

## Don'ts

- Do not equate changing an Apple meta tag with changing manifest `start_url` or `id`.
- Do not assume `beforeinstallprompt` exists on iOS.
- Do not add a second manifest link and assume the browser will select the nearest one.
- Do not serve private list titles from a public manifest endpoint.
- Do not promise installed icon/name updates across platforms.
- Do not call same-origin installs fully isolated apps.
