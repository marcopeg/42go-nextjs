# Execution Notes — Enable Per-URL Install Targets and Installable Quicklist Virtual Apps
**Task**: ./HV34.task.md
**Plan**: ./HV34.plan.md

## Decisions

- The operator's `plan and execute it` instruction is the explicit accepted-plan and execution authorization.
- AppConfig owns serializable `pattern` plus resolver-key declarations. Database/session resolver functions remain in a server-only registry.
- Version one uses a small `/literal/:param/**` pattern grammar and adds no routing dependency.
- The existing `/manifest.webmanifest` URL will be preserved through an explicit route handler so current app installations keep a valid manifest URL.
- Quicklist version one requires no migration: virtual apps override stable ID, list URL, and list-derived name while inheriting base Quicklist icons and colors.
- The shared 42Go Modal owns manual installation instructions; no app-specific overlay will be introduced.
- Displaying in standalone mode is not treated as proof that a particular list is installed.

## Problems Encountered

- Running the production build rewrote `.next` while an existing development server was still using Turbopack state. The server retained a stale import to the deleted `src/app/manifest.ts`. The exact process was stopped, only the generated `.next` directory was removed, and `make app.start` restored the runtime.
- The first client-side navigation check found that the application name changed but the manifest link remained `/manifest.webmanifest`. The fix introduced a server-seeded `ManifestLink` that follows AppConfig's serializable target pattern and manifest-path template after hydration. Navigating into a list now selects its credentialed manifest; navigating back restores the base manifest.
- The first real iPhone attempt still showed generic install information. The phone entered Quicklist with the base document and then reached Ica through App Router navigation. Although React replaced the manifest link, Safari retained the loaded document's base installation identity. The framework now detects crossings between base and virtual-app manifest identities and performs one controlled full-document reload. Direct/unauthorized requests cannot loop because reloads are only triggered when the client pathname differs from the trusted initial pathname. Dynamic targets also set `<title>` to the resolved resource name for Safari's title fallback.
- The in-app browser ignored the requested 390×844 viewport and reported 1280×720. Desktop behavior was verified, but no mobile-viewport claim is recorded.
- The LingoCafe and Notes ngrok endpoints were unavailable during the final browser pass. Their base manifest identities had already been verified locally with their respective `Host` headers before the final build.

## Deviations From Plan

- Added a framework documentation step during execution. The feature exposes a reusable AppConfig/server-registry contract, so leaving the only usage example in Quicklist would make the framework incomplete.
- Runtime client-side navigation initially updated Next metadata but retained the root layout's static manifest link. Added a client-aware manifest-link component seeded from the authenticated server result and driven by AppConfig's serializable pattern/template after hydration.
- Replaced the original assumption that mutating the manifest link was sufficient. Identity-boundary navigation now reloads the document; same-target nested navigation remains client-side.

## Security Assessment — 2026-07-17

**Overall rating**: Low immediate application-layer risk. No release-blocking vulnerability was found in the implemented Quicklist path. The feature does add medium lifecycle/privacy considerations that should be explicit product policy.

### Controls verified

- The proxy deletes caller-supplied `X-42Go-AppID` and `X-42Go-Pathname` values before setting trusted request values. Live ngrok checks confirmed forged values still return the host-resolved base Quicklist manifest.
- The manifest query accepts only a target path. Names, icons, colors, scope, identity, and launch URLs come from trusted AppConfig defaults plus the server resolver.
- Quicklist rejects non-UUID project IDs before database access.
- The Quicklist resolver requires a valid NextAuth session, enforces `appId === "quicklist"`, filters `quicklist.projects.app_id`, and checks owner-or-current-collaborator access in the same parameterized SQL statement.
- Missing, malformed, external, cross-app, unauthenticated, deleted, and unauthorized targets fail closed with 404 and no list title.
- Dynamic manifests use `private, no-store` and `Vary: Cookie`; the base manifest contains no private resource data and remains publicly revalidated.
- Manifest IDs, launch URLs, scopes, manifest paths, and icon URLs are root-relative and same-origin. Launch URLs must remain inside the declared scope.
- Database-derived names are length-bounded and serialized through React/Next metadata and `Response.json`; no raw HTML/script insertion was introduced.
- The manifest route is a read-only GET and performs no state change, so the credentialed request does not create a new CSRF mutation surface.
- The identity-boundary fix calls `window.location.reload()` on the current URL. It does not navigate to a query-provided or resolver-provided destination and therefore adds no open redirect.
- No service worker, dependency, database migration, upload path, or arbitrary external icon fetch was added.

### Residual risks and recommendations

1. **Medium — installed-session lifecycle on Apple platforms.** Apple copies login cookies into a new Home Screen web app and then separates that storage from Safari. Quicklist uses a 30-day stateless NextAuth JWT, so logging out in Safari or one installed app does not centrally revoke copies held by other installed list apps. Per-list installation increases the number of authenticated containers a user may forget. If global logout or lost-device revocation becomes a requirement, add server-side session/version revocation, a **Sign out all devices/apps** action, or shorter/re-authenticated sessions.
2. **Medium privacy — persistent list-name metadata.** The authorized list title becomes the document title, manifest name, and Home Screen label. It may remain visible in browser history, synced tabs, Focus/OS metadata, screenshots, or an orphaned launcher after list access is revoked. Authorization still blocks list data, but the label cannot be remotely erased. Consider warning users not to expose sensitive names or later allow a neutral per-install alias.
3. **Low to medium — same-origin blast radius on Chromium.** Virtual apps intentionally share origin cookies, storage, quota, permissions, and some uninstall behavior. The shared `/` scope also overlaps every list. This is not a Quicklist privilege escalation because every API request rechecks authorization, but it is not security isolation. Use separate origins only if future virtual apps need separate trust boundaries; otherwise keep permissions minimal and avoid treating a list launcher as a sandbox.
4. **Low framework footgun — future resolver discipline.** The framework cannot prove that future named resolvers enforce AppID, session, resource authorization, and private caching. Every database-backed resolver must follow the Quicklist pattern. Dynamic icons should come from an allow-listed static catalog, not raw user-entered same-origin paths, and user-controlled path parameters need resource-specific validation.
5. **Low availability cost.** A matched authenticated target adds session resolution and an authorization query to document/manifest requests. The input validation is bounded and SQL is indexed/parameterized, so this is comparable to existing Quicklist API reads. Normal edge/application rate limiting remains the appropriate DoS control.

### Security conclusion

The feature is acceptable to ship under the current Quicklist threat model. It does not grant access, weaken resource authorization, or expose private manifest data to unauthenticated callers. The main follow-up worth prioritizing for a higher-security product is global session revocation across installed Apple web apps; the main user-facing privacy consideration is that list names become durable device metadata.

## Known Limitations

- Physical iPhone/iPad and Android installation cannot be claimed until executed on real devices. Desktop browser emulation is not equivalent.
- Two simultaneous installed list launchers, restart launch behavior, browser link capture, and install-from-an-already-installed-PWA remain part of the physical-device matrix.
- Mobile viewport usability was not proven because the available browser control ignored the viewport override.
- Both sampled lists were owner-accessible and had no collaborators. Collaborator authorization was reviewed in SQL and uses the same owner/collaborator condition as the existing Quicklist API, but it was not exercised with a live collaborator account.
- Installed app names/icons can remain stale according to platform update behavior; the feature intentionally does not track or enumerate installed lists.
