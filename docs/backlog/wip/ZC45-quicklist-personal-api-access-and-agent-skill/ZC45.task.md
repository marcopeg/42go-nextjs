# QuickList Personal API Access and Agent Skill

## Elevator's Pitch

Give each QuickList user an opt-in personal API that can perform the same list and item operations the user can perform in the app, authenticated by a rotatable bearer token, and ship a reusable Codex-compatible skill so an agent can execute requests such as "add milk to my list."

## Business Gain

QuickList becomes safely automatable from Codex, Claude Code, scripts, and other agent harnesses without requiring a browser session or exposing NextAuth cookies. Users can integrate their personal and shared lists into agent workflows while retaining a simple off switch and token rotation control.

## Current State

QuickList already has session-protected application endpoints for listing accessible lists, reading a list and its tasks, creating and deleting lists, updating list information, creating/updating/checking/deleting tasks, reordering tasks, and other app operations. Access is scoped by the resolved app and current signed-in user, including owned lists and collaborations. QuickList also has a configurable profile page backed by profile data, but it has no user-managed API-access toggle, no personal bearer-token authentication path, no intentionally public/versioned automation contract, and no project skill for agents to call it.

## Desired State

QuickList users can enable personal API access from their profile settings. When no credential exists, the settings show **Create token**. Creation returns the raw bearer token once and presents it in a focused disclosure with clear instructions to copy and store it safely. Later settings visits show only a masked token indicator and a **Rotate token** action; rotation invalidates the previous token and returns the replacement raw token once. Disabling account API access requires confirmation that the token will be deleted; confirmation deletes it and later re-enabling requires a new token. A dedicated, documented, versioned QuickList API authenticates the bearer token without a normal NextAuth session, resolves the associated QuickList user and app, and applies exactly the same resource visibility and action permissions as the app. It must not turn collaboration access into ownership or bypass owner-only rules.

API visibility also requires an independent per-list setting. The list owner sees an **Enable API access for this list** switch in the normal session-authenticated list settings UI; collaborators do not see or change this setting, and token-authenticated routes cannot read or mutate it. Lists created through the UI start disabled and are excluded from API discovery and access. Lists created through the automation API start enabled because they originate inside the API boundary. Account-level disable leaves all per-list flags untouched. If an owner enables a list while account API access is off, the setting remains enabled and a small inline yellow warning beneath the switch explains that the list will remain unavailable to that owner's token until API access is enabled from the profile.

For lists passing both gates, the API covers full practical management of accessible lists and their items: enumerate lists, read one list, create a list, update list settings, delete a list when authorized, list items, add an item, update an item, mark/unmark it checked, and delete it. An API-enabled shared list is available through each collaborator's own token, and the collaborator may perform exactly the same ordinary list and item operations available to them in the UI, including renaming, changing mode, adding/editing/checking/deleting items, and reordering. Sharing administration is out of scope: the API does not invite or remove collaborators or otherwise manage list sharing. Owner-only actions, including deleting the whole list, remain owner-only. A repository-owned skill documents the contract and includes a small reliable client, likely using Python's standard library or another low-dependency approach. The skill reads its base URL and token from local secret configuration, never embeds the token in tracked files, and can be installed or copied into project-local or global Codex skill locations. The design remains simple and personal-use oriented; MCP-server work is explicitly deferred unless refinement finds a strong reason to change course.

## Definition of Success

After enabling API access and placing the generated credential in the supported local secret location, an operator can install the supplied skill and instruct a compatible agent to discover accessible QuickList lists and complete an end-to-end action such as adding "milk" to a chosen list. The same credential can read and mutate only what that user could read and mutate in the QuickList UI. Disabling access or rotating the token immediately invalidates the old credential.

Only lists explicitly enabled for API access are discoverable or addressable through the API. UI-created lists remain private by default; API-created lists are immediately usable through the API.

## Additional Context

Generate at least 256 bits of cryptographically secure randomness and encode new tokens using ASCII letters and digits only. Display the full token only in the direct response to creation or rotation. Persist only a deterministic hash such as SHA-256 because the token already has high entropy, compare hashes in constant time, and keep credential metadata server-only. A short alphanumeric non-secret prefix may be retained for recognition. Store one active credential per QuickList app-scoped user in a dedicated QuickList-schema table with creation/update and `last_used_at` metadata. The profile page owns the credential lifecycle UI, but ordinary profile reads never expose the token hash or raw token. Log neither Authorization headers nor token values. Use HTTPS in deployed environments. Full per-call audit logging, multiple named tokens, scopes, and mandatory rate limiting are deferred from this personal-use v1; conservative rate limiting may be added later without changing the contract.

The agent skill should support deterministic commands for list discovery and CRUD rather than relying on prompt-only curl examples. Its default secret store is one documented user-level credentials JSON file excluded from version control and restricted to the owning user. The file contains a top-level `credentials` map. A project-local skill installation stores and selects its credential under the canonical absolute project path; a globally installed skill uses the reserved `_global` key. Every entry contains `baseUrl` and the raw bearer `token`. Moving a project changes its scope key and requires reconfiguration or deliberate entry migration. The skill may also accept explicit environment-variable overrides. The one-time profile copy action packages a versioned JSON object containing the current QuickList origin and raw token into a prefixed, unpadded Base64URL connection code. This encoding is for convenient copy-paste transport and provides no secrecy. When the selected entry is missing, the skill prints one setup command for the operator to run in a user-controlled integrated or external terminal. That script accepts the connection code through hidden input, validates and decodes it, writes the correct scoped entry with owner-only permissions, and exits; the operator then retries the original request. Tokens and connection codes are never requested in the Codex conversation or accepted as command-line arguments. As an explicit mobile fallback, a user may voluntarily paste an envelope into chat: the skill first warns that the raw secret will remain in conversation and potentially tool history, sends it only through the configure process's stdin, performs the requested operation, then recommends immediate rotation and normal hidden-prompt reconfiguration. Credential selection must be deterministic, and the client must avoid printing or returning bearer values in normal output. List names resolve by case-insensitive exact match only: one match proceeds, while zero or multiple matches stop and report choices for clarification. Explicit list IDs remain available. The client should provide useful errors for missing scope entries, disabled/revoked credentials, ambiguous list names, authorization failures, validation errors, and network failures.

## Assumptions

This feature is QuickList-specific for the first implementation. There is exactly one active personal token per user per QuickList app context. A bearer token represents the user, not a single list, so its effective resources change as the user's owned/collaborative access changes. Existing domain queries and permission rules should be reused or extracted rather than duplicated with subtly different authorization. Use a dedicated versioned automation namespace under `/api/quicklists/v1`; do not retrofit bearer behavior into the session-oriented browser handlers. List enumeration uses cursor pagination and stable JSON envelopes. Item updates, including check/uncheck, use normal PATCH fields such as `completed`. The repository source skill is QuickList-specific and lives under `.agents/skills/quicklist`; documentation explains user-level installation under `~/.agents/skills/quicklist`. The first skill targets Codex's SKILL.md model but keeps its client and API documentation generic enough for Claude Code and other harnesses. Personal-use scale does not require OAuth scopes, mandatory v1 rate limiting, or a full token-management platform.

## Constraints

Do not authenticate automation routes with NextAuth session cookies. Do not let token authentication bypass QuickList app isolation, list membership checks, collaboration permissions, or owner-only actions. Do not store the reusable bearer secret in plaintext in the database or tracked project files unless refinement explicitly rejects the hash-only recommendation. Do not expose token hashes or credential metadata through the generic profile payload without a demonstrated need. Do not log tokens. Treat disabling and rotation as immediate revocation. Keep the public automation contract separate enough from browser-internal endpoints that it can be versioned and documented. Do not introduce an MCP server in this task unless refinement deliberately changes scope.

Enforce both account-token validity and per-list API exposure. API-disabled lists must not be discoverable or addressable through token-authenticated routes. Account-level disable must not rewrite per-list exposure settings.

Only the list owner may view or change the per-list API exposure setting, and only through the normal signed-in UI. Token-authenticated endpoints must not expose or mutate this setting. Enabling a shared list makes it eligible for each collaborator's own token, but never expands that collaborator's underlying permissions.

Sharing management is excluded. Do not add API operations for invitations, collaborator removal, or other collaboration administration. Existing collaboration membership still determines which lists and actions the represented user can access.

## Acceptance Criteria

- QuickList profile settings derive API access directly from token existence and do not show a redundant account-level switch.
- When no token exists, helper text explains that creating an API token enables trusted tools for explicitly exposed lists, and the sole action is **Create API token**.
- When a token exists, the available lifecycle actions are **Rotate token** and **Disable API access**.
- When no token exists, QuickList profile settings show a **Create token** action.
- Creation generates a cryptographically random personal bearer token and presents the full value only in a deliberate one-time copy-and-store disclosure.
- Newly generated bearer tokens contain only ASCII letters and digits while retaining at least 256 bits of entropy.
- The one-time disclosure has one header action: **Copy token**, changing to **Done** after a successful copy. Selecting the token itself also copies and changes the action to **Done**. Both copy paths place the full versioned connection code, containing the current QuickList origin and raw token, on the clipboard.
- When a token exists, later settings reads show only a masked indicator and approved non-secret metadata, never the raw token or hash.
- The user can rotate the token; the previous token stops working immediately.
- The user can disable/revoke API access; the current token stops working immediately.
- Disabling account API access requires an explicit confirmation that the current token will be deleted.
- Confirming account API disable deletes the token and leaves every per-list API setting unchanged.
- A dedicated table in the `quicklist` schema stores the app-scoped user association, token hash, and approved lifecycle metadata; it never stores the raw token.
- Dedicated, versioned QuickList API endpoints accept `Authorization: Bearer <token>` without requiring a normal session.
- Missing, malformed, disabled, unknown, or revoked tokens are rejected without leaking credential or account details.
- Token authentication resolves the correct QuickList app and user and remains app-scoped.
- Every owner-facing list settings screen provides an **Enable API access for this list** switch; collaborators do not see or change it.
- The per-list API exposure value is omitted from token-authenticated response schemas and cannot be enabled or disabled through the automation API.
- Lists created through the UI default to API-disabled.
- Lists created through the automation API default to API-enabled.
- If a list is API-enabled while account API access is disabled, an inline yellow warning explains that account access must be enabled from the profile; the per-list setting remains enabled.
- The API lists only lists that are both visible to the represented user and explicitly API-enabled, including permitted collaborations only when the list-level gate allows them.
- For an API-enabled shared list, collaborators can perform the same list and item operations through their token that they can perform in the UI.
- Token access never upgrades a collaborator to owner-only sharing, collaborator administration, or whole-list deletion powers.
- Direct token-authenticated access to an API-disabled list is denied without exposing its existence.
- The API can read one accessible list and enumerate its items.
- The API can create a list.
- The API can update list settings and delete a list only when the represented user has the same permission in the app.
- The API can add, update, check/uncheck, and delete items when the represented user has the same permission in the app.
- The API exposes no invitation, collaborator removal, or other sharing-management operations.
- API validation, not-found, conflict, authentication, and authorization responses are consistent and documented.
- Automated tests cover token lifecycle, app/user isolation, owned and shared-list behavior, denied owner-only operations, and core list/item CRUD.
- A repository-owned Codex-compatible skill includes `SKILL.md`, API usage guidance, setup/install instructions, secret-handling guidance, and an executable low-dependency client or equivalent reliable call mechanism.
- The skill supports configurable API base URL and obtains the token from an approved untracked local source, never from a committed value.
- The default user-level credentials JSON has a `credentials` map, uses canonical absolute project-path keys for project-local installations, and uses `_global` for a global installation.
- Every credential entry stores `baseUrl` and the raw bearer `token`.
- The credential file is created with owner-only permissions, and normal skill output never reveals stored bearer tokens.
- Missing credentials produce one documented setup command; the user-controlled setup script accepts the connection code through hidden terminal input, validates and decodes it, and writes the correct scoped entry.
- The default setup flow does not ask the operator to paste a bearer token into the Codex conversation and does not depend on automatically opening or closing a terminal window.
- If the operator voluntarily supplies a connection envelope in chat as a mobile fallback, the skill warns about conversation/tool-history exposure, configures it through process stdin without a shell argument, completes the requested operation, and recommends token rotation plus normal terminal setup afterward.
- A documented end-to-end verification uses the skill to find a list and add an item such as "milk", then confirms it through the API or UI.
- Case-insensitive exact list-name lookup proceeds only for one match; zero or multiple matches stop without mutation and return useful choices, while explicit list IDs are supported.
- `npm run qa` passes after implementation.

## Dos

- Reuse or extract the same QuickList authorization/domain layer for browser and token callers.
- Prefer a dedicated `/api/.../v1/...` automation namespace and stable response schemas; finalize naming during refinement.
- Use a CSPRNG and unbiased alphanumeric token encoding.
- Prefer SHA-256 hash-only storage for a high-entropy token and constant-time comparison.
- Make rotate and disable behavior explicit and test immediate invalidation.
- Preserve per-list API exposure flags when account API access is disabled.
- Default UI-created lists to API-disabled and API-created lists to API-enabled.
- Keep API access opt-in and QuickList-specific.
- Ensure shared-list actions mirror current collaboration permissions exactly.
- Restrict visibility and mutation of the per-list API exposure setting to the list owner.
- Keep the exposure switch exclusively on session-authenticated UI/server routes; do not make it part of agent-facing list settings.
- Document examples for list discovery, disambiguation by ID, and item CRUD.
- Keep the agent client deterministic, quiet about secrets, and useful on errors.
- Document both project-local and global skill installation paths where supported.

## Don'ts

- Do not grant ownership powers merely because the request uses an API token.
- Do not expose API-disabled lists through list enumeration, direct lookup, errors, or mutations.
- Do not reuse browser cookies as the automation credential.
- Do not put bearer values in URLs, logs, analytics, screenshots, error messages, shell history examples, or Git.
- Do not store the live token inside SKILL.md or a committed `.env` file.
- Do not fork business rules into an API-only implementation that can drift from the UI.
- Do not require an MCP server for the initial outcome.
- Do not overbuild OAuth, multiple scopes, multiple named tokens, or enterprise key management before refinement proves they are needed.
