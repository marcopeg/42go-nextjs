# Clarify Round v2 — QuickList Personal API Access and Agent Skill

## Questions

### 1. Can the token use a dedicated server-only database table with hash-only storage and one-time display of the original token?

## Answers

### 1.

The operator challenged the need for a separate table and asked whether the token hash can be saved in the existing user settings. The operator also proposed that the skill ask for the original token, hash it, and store the hash for calls.

After reviewing the tradeoff, the operator chose a QuickList-owned token table so credential data is not mixed into profile JSON and cannot leak through the generic profile API. When no token exists, settings show **Create token**. Creation returns the raw token to the browser once and displays a copy-and-store warning in a popover-like disclosure. On later visits, settings show only a masked token indicator and a **Rotate token** action. Rotation likewise returns the replacement token once.

## Resolution Summary

- Store QuickList API credential records in a dedicated table in the `quicklist` schema, linked to the app-scoped user.
- Store only a hash and safe lifecycle metadata. Never persist the raw bearer token.
- Return the raw token to the authenticated browser only in the direct response to creation or rotation.
- The normal settings read path exposes only whether a token exists and any approved non-secret metadata; it never recovers or returns the raw token or hash.
- The settings lifecycle is **Create token** when absent, then masked status plus **Rotate token** when present.
- The skill stores and sends the original bearer token; the server hashes the received value and compares it with the stored hash.
