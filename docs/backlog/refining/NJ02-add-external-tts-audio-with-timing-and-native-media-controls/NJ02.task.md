# Add External TTS Audio with Timing and Native Media Controls

## Elevator's Pitch

Extend the LingoCafe reader playback system with optional, externally produced audiobook assets and synchronized timing metadata. When a book has a published audio-package reference, play real media audio so playback can continue while a supported phone is locked and can expose native lock-screen, Control Center, headset, and notification controls. When it does not, retain the current device/browser TTS provider as the fallback.

## Business Gain

Give learners a more consistent, audiobook-like voiceover experience across devices, including background playback and native phone controls. Audio production is deliberately manual for the first book, so playback has no runtime TTS cost or provider dependency. Preserve sentence and word highlighting so the audio remains a language-learning feature rather than becoming a detached podcast player.

## Current State

YI11 implemented device/browser playback with `speechSynthesis`, sentence and best-effort word highlighting, playback controls, seeking, translation-aware pausing, guided scrolling, fixed pauses, and continuous page transitions. The reader already exposes a replaceable speech-provider boundary. Browser speech synthesis does not produce a reusable audio asset, does not provide a durable timing manifest, and cannot reliably create an iOS background media session or native lock-screen controls.

## Desired State

Each book may optionally reference a manually published audio package. If the reference exists and its package validates, the reader uses its real audio resource and deterministic sentence/word timing metadata through an `HTMLAudioElement`, integrating with `navigator.mediaSession` where supported. If there is no reference, the package is unavailable, or playback fails, the reader uses the existing device TTS path.

High-level package and playback workflow:

1. Add an optional book-level reference to a versioned, manually published audio package.
2. Load and validate its small JSON timing manifest before presenting external playback. The manifest identifies the book, source-content version, language, voice, ordered tracks, audio duration, reader-page ranges, sentence IDs, and word time ranges.
3. Select the manifest’s current track and play its stream through one persistent `HTMLAudioElement`; do not create a separate media element for each reader page or sentence.
4. Drive sentence and word highlighting, percentage/sentence seeking, translation pause/resume, and guided scrolling from `audio.currentTime` and the timing manifest.
5. Each reader page is a book chapter and has at most one audio track. When the current chapter track ends, prefetch and load the next chapter into the same media element, update the reader route/surface, and resume it without another user action.
6. Register Media Session metadata and supported play/pause/seek/previous/next handlers. Verify native controls and locked-screen playback on physical devices.
7. Keep fixed sentence, paragraph, summary/body, and page-transition pauses in the authored audio/timing contract; speed handling must not silently shorten those pauses.
8. Use device/browser TTS when a book has no valid package or external playback cannot start or continue.

## Refinement Decisions

- **Manual assets first:** NJ02’s first implementation does not call a TTS provider, generate audio, manage provider credentials, or create a synthesis job queue. An operator produces and publishes the audio package for one selected book outside the application. The production source may be AI-generated narration or a real author recording; the reader consumes the same package contract either way.
- **Optional per-book capability:** A book may have an audio-package reference or no reference. A valid reference selects external-media playback; no reference, an invalid manifest, an unavailable asset, or runtime media failure selects the current device/browser TTS without blocking reading.
- **One chapter/page track:** A reader page is already a book chapter. The package therefore contains at most one complete audio file per reader page/chapter, never a file per paragraph or sentence. A valid first package covers every readable page in its book; partial packages do not create a mixed external-audio/device-TTS session.
- **Production boundary:** A later task may automate synthesis, cache management, or multi-book publication. It must produce the same versioned audio-package contract rather than changing reader playback again.

## Proposed First Audio-Package Layout

Publish one immutable package for the selected book, outside PostgreSQL, with a stable manifest URL recorded on the book. The manifest is small and cacheable; audio stays in ordinary object/CDN storage. Each reader page is a chapter and therefore gets no more than one audio file.

```text
books/{book-id}/audio/{package-version}/
  manifest.v1.json
  cover-512.jpg
  tracks/
    {page-id-001}.m4a       # one complete reader page/chapter; AAC-LC mono
    {page-id-001}.mp3       # fallback when required
    {page-id-002}.m4a
    {page-id-002}.mp3
```

`manifest.v1.json` should contain the package and source-content versions plus an ordered `tracks` list. Each track has exactly one `pageId`, `durationMs`, and preferred/fallback source URLs and MIME types. It also contains the page’s sentences and word ranges. Every sentence records its existing reader `sentenceId`, `startMs`, `endMs`, and a normalized-text hash. Every word records its `startMs`, `endMs`, and JavaScript UTF-16 `start`/`end` offsets within that sentence. The manifest, rather than filenames or source-provider offsets, is the reader’s source of truth.

For the first book, make each track one complete reader page/chapter. Do not emit one file per paragraph or sentence: that creates unnecessary source switches and makes normal audiobook/lock-screen continuity weaker. Do not begin with one whole-book file: it increases initial download, makes retries costly, and makes a small correction republish the whole book.

Use AAC-LC in an M4A container as the preferred high-quality speech source (roughly 64–96 kbps mono after audition), with a 96 kbps mono MP3 fallback only if target-device testing shows it is needed. Codec choice affects quality and bandwidth; lock-screen behavior comes from continuous real-media playback plus Media Session, not from a special audiobook extension.

## Definition of Success

A user can play a published external voiceover package, follow synchronized sentence and word highlighting, seek and change speed according to the published package, lock a supported phone without stopping playback, and control playback from the phone interface. Package failures do not break reading, and device TTS remains available according to the agreed fallback policy.

## Additional Context

- Related baseline: YI11 deliberately introduced a narrow provider boundary so an API-backed TTS provider could be added without replacing reader controls or sequencing.
- Provider analysis as of 2026-07-13 — Google Cloud Text-to-Speech WaveNet: recommended starting point. Google lists multiple Swedish WaveNet voices, supports SSML `<mark>` timepoints, does not bill the `<mark>` tags themselves, and currently lists WaveNet at USD 4 per million characters after a 4-million-character monthly free allowance. Revalidate prices and quotas during refinement/implementation. Official references: https://cloud.google.com/text-to-speech/pricing, https://cloud.google.com/text-to-speech/docs/voices, https://cloud.google.com/text-to-speech/docs/ssml
- Provider analysis — Amazon Polly: strong deterministic sentence/word Speech Marks and Swedish Neural voice `Elin`. Standard audio is currently listed at USD 4 per million characters and Neural at USD 16 per million. Speech Marks are returned instead of audio and are billed as a separate synthesis request, so audio plus timing can double the character-processing cost. Official references: https://aws.amazon.com/polly/pricing/, https://docs.aws.amazon.com/polly/latest/dg/speechmarks.html, https://docs.aws.amazon.com/polly/latest/dg/neural-voices.html
- Provider analysis — Microsoft Azure AI Speech: viable neural-voice candidate with word-boundary/bookmark support and useful Swedish voice options. Keep it as a quality comparison candidate; confirm exact regional pricing, timing export behavior, and caching terms before selection. Official references: https://azure.microsoft.com/pricing/details/speech/ and https://learn.microsoft.com/azure/ai-services/speech-service/text-to-speech
- Provider analysis — OpenAI/Azure OpenAI TTS: viable quality candidate, but not the preferred baseline because this feature prioritizes predictable low per-character cost and deterministic sentence/word timing metadata. Reassess if its timing APIs or pricing become clearly superior.
- Provider analysis — ElevenLabs: acknowledged as a high-quality option but explicitly excluded from the preferred baseline because the operator considers it too expensive.
- A 100,000-character book would cost about USD 0.40 at a USD 4-per-million rate before storage/egress and before generating additional voice or speed variants. Caching must make generation cost depend on unique assets, not play count.
- Native controls on the web depend on Media Session and actual media playback support. A future native wrapper could provide stronger guarantees, but this task should first evaluate the existing web/PWA surface. Reference: https://developer.mozilla.org/docs/Web/API/Media_Session_API

## Assumptions

- Audio production and hosting are outside this first implementation; the reader consumes the manually published package only.
- The existing YI11 playback controller, sentence catalog, highlights, controls, translation behavior, analytics events, guided scrolling, and cross-page flow remain the UX baseline.
- Published audio may be replayed under the applicable production-provider contract and the application's content rights; this must be verified before production use.
- The externally published audio path requires network access to retrieve streams, while device TTS remains available when a package is absent or unusable.
- One canonical normalized timing-manifest format can hide provider-specific timing representations from the reader UI.
- Exact background/lock-screen behavior must be tested on real iOS and Android devices; browser emulation is insufficient.
- Additional voice and speed variants increase production and storage cost and should be separately published only when justified.

## Constraints

- Do not add a provider credential, billable synthesis endpoint, or audio-generation job queue in this first implementation.
- Reuse the YI11 provider boundary and existing playback UI rather than creating a second independent player.
- Preserve current sentence IDs and text offsets so translation, highlights, seeking, and analytics remain synchronized.
- Preserve fixed sentence, paragraph, summary/body, and page-transition pause semantics independently from spoken-voice speed.
- Use actual media audio for native phone controls; do not attempt to attach Media Session controls directly to `speechSynthesis`.
- Store large audio binaries outside PostgreSQL unless refinement documents a compelling reason otherwise.
- Require versioned package references and source-content checks so changed text never uses stale audio or timing data.
- Handle Unicode offsets consistently; provider byte offsets must not be mistaken for JavaScript character indexes.
- Do not regress device TTS, translation pause/resume, reader scrolling, playback seeking, page continuity, or mobile control placement.
- Run `npm run qa` and real-device playback checks before completion.

## Acceptance Criteria

- [ ] A book may expose an optional versioned audio-package descriptor containing a playable audio stream and normalized sentence/word timing manifest.
- [ ] The reader uses external media only when the current book has a valid package; otherwise it uses device TTS.
- [ ] The first implementation adds no TTS provider credentials, synthesis endpoint, generation queue, or runtime provider charge.
- [ ] Audio packages are immutable, versioned, and rejected when their source-content, language, voice, timing/pause policy, or speed-asset version does not match the book reference.
- [ ] The normalized timing manifest maps existing reader sentence IDs and words to audio time offsets without Unicode offset corruption.
- [ ] Sentence and word highlighting follow external audio timing and remain synchronized after pause, resume, seek, speed change, and page transition.
- [ ] Existing percentage seeking maps deterministically to the correct sentence/audio time and native seek actions update the reader state.
- [ ] The existing translation interaction pauses external audio and resumes it according to current reader behavior.
- [ ] Existing guided scrolling and manual-scroll suspension/reactivation work with external audio.
- [ ] Sentence, paragraph, summary/body, and automatic page-transition pauses match the configured policy and are not shortened or lengthened by playback-speed selection.
- [ ] Cross-page playback continues without requiring another Play action and begins the next page from its title/top according to the existing reader flow.
- [ ] On supported real iOS and Android devices, audio continues after screen lock and native controls expose at least play/pause and seek or previous/next behavior supported by the platform.
- [ ] Media Session metadata identifies the book and current page/chapter and is cleared when playback closes or the reader unmounts.
- [ ] The current device/browser TTS provider remains available according to the refined fallback or user-selection policy.
- [ ] Missing, invalid, inaccessible, or incompatible published assets produce understandable states without breaking the reader or its device-TTS fallback.
- [ ] Non-sensitive diagnostics identify package/version and media failures without exposing source text or asset credentials.
- [ ] Existing `audio.play` event privacy rules remain intact and do not add sentence text or sentence IDs unless separately approved.
- [ ] `npm run qa` passes and real-device regression checks cover foreground, background, lock-screen controls, highlighting, seeking, translation, and page continuity.

## Don'ts

- Don't remove or destabilize the current device TTS path while external audio is being introduced.
- Don't generate audio in response to a Play action.
- Don't add a text-to-audio proxy to this task.
- Don't rely on browser speech boundary events for externally generated audio timing.
- Don't assume provider byte offsets match DOM or JavaScript string offsets.
- Don't apply global playback rate when it changes fixed pause durations contrary to the reader's playback rules.
- Don't store provider secrets, generated binary audio, or copyrighted source text in client-visible logs.
- Don't claim native background support based only on desktop mobile emulation.
