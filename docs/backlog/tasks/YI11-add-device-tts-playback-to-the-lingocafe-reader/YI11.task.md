# Add Device TTS Playback to the LingoCafe Reader

## Elevator's Pitch

Add a reader playback mode that uses the device and browser text-to-speech capability to read the current book page aloud sentence by sentence. The reader should provide a bottom-right FAB to start playback, a floating playback control that stays at the bottom while active, sentence highlighting with best-effort word highlighting, automatic guided scrolling, and scroll-position seeking.

## Business Gain

Users can listen while following the text on screen, turning the reader into an accessible language-learning experience for pronunciation practice, reading support, and hands-free study. Chuck Norris does not lose his place. The reader keeps it for him.

## Current State

The LingoCafe reader is implemented at `/books/[bookId]/[pageId]` with separate desktop and mobile scroll surfaces, persisted `progress_bps` scroll progress, reader preferences, restricted markdown rendering, and sentence-level translation interactions. The reader does not currently provide device TTS playback, playback controls, sentence playback state, automatic guided scrolling, or playback seeking. The existing sentence rendering and scroll-container behavior are the likely integration points.

## Desired State

On a readable book page, a playback FAB is fixed at the bottom-right when playback is inactive. Clicking it starts device/browser TTS from the sentence corresponding to the current reading context:

- If the user tapped a sentence and then starts playback, begin with that sentence.
- Otherwise, derive the starting sentence from the current reader scroll position.
- If playback is already active, the control exposes the active playback state and lets the user pause/resume or stop/close it.

While playback is active:

- Show a floating audio-player-style control fixed to the bottom of the page.
- Keep a close action that ends playback and removes the floating control.
- Show playback progress as a scroll percentage that can be moved backward or forward to choose the sentence to play.
- Provide one playback-speed button that cycles through `0.5×`, `0.75×`, `1×`, and `1.25×`; default to `1×` and cycle from `1.25×` back to `0.5×`.
- Highlight the sentence currently being spoken and, where supported by the browser/device speech boundary events, highlight the word currently being spoken inside that sentence. Sentence highlighting remains the fallback when word-level timing is unavailable.
- Keep the page manually scrollable. Manual page scrolling never changes the active or next playback sentence.
- Suspend guided auto-scroll after the user manually scrolls away from the spoken sentence. Re-enable it once the spoken sentence is visible in the active reader viewport; from then on, auto-scroll the next sentence to the center only when that next sentence is outside the viewport.
- Preserve sentence tapping for the existing translation behavior; tapping any sentence, including during playback, opens its translation without changing the active or next playback sentence.
- Insert a two-second pause between paragraphs.
- Re-synchronize speech only when the user changes the playback percentage, so the selected sentence becomes the next sentence spoken.

Playback must use a device voice matching the book's source/content language. If that exact language is unavailable, or browser speech synthesis is unsupported, playback is unavailable rather than using a mismatched fallback voice.

## Definition of Success

A user can open a book page, tap Play, and follow the spoken content while the active sentence is highlighted and guided into view. The user can scroll freely, seek through playback using the visible percentage control, tap sentences for translation, start from a selected sentence or the current scroll position, and close playback without losing the normal reader experience.

## Additional Context

The reader already has sentence-level rendering and translation code in `src/app/(app)/(lingocafe)/books/_components/BookPageReader.tsx`, and the page route coordinates desktop/mobile scroll containers and `progress_bps` in `src/app/(app)/(lingocafe)/books/[bookId]/[pageId]/page.tsx`. Existing reader work established the sentence model, translation popover, scroll progress, and mobile/desktop surface differences. The implementation should account for the Web Speech API's asynchronous utterance lifecycle, browser autoplay/user-gesture rules, voice availability, `boundary` event support, cancellation when seeking, and cleanup when navigating away or closing playback.

The baseline provider is device/browser TTS, but the playback orchestration should sit behind a small provider boundary so a future API-backed provider such as AWS Polly can replace the speech engine without rewriting reader controls, sentence sequencing, highlighting, or scroll behavior. The baseline must not introduce server-side audio generation or a new audio file pipeline.

Each sentence that begins playback must record an `audio.play` reader event with `language`, `book_id`, and `page_id`. Do not record sentence content or a sentence ID in the event payload. The separate analytics repository will cluster adjacent events to derive session duration; this task only records the events.

## Assumptions

- The primary implementation uses the browser/device Web Speech API (`speechSynthesis` and `SpeechSynthesisUtterance`) rather than a server audio provider.
- The current book-page sentence segmentation is reused for playback and for mapping scroll positions to sentences.
- The existing desktop and mobile reader scroll containers both need playback-aware viewport measurement and auto-scroll behavior.
- Playback position is page-local and does not replace persisted reading progress unless refinement explicitly chooses to connect the two.
- Speech advancement does not update persisted reading progress; normal user scrolling remains the only source of `progress_bps` updates.
- The two-second paragraph pause applies after each paragraph before the next paragraph begins, but not between sentences within the same paragraph.
- Word highlighting is best effort because speech boundary events and word timing vary by browser and device.
- Playback controls may use the shared overlay/floating-surface patterns already present in the reader where they fit the bottom-fixed interaction.
- Manual page scrolling suspends guided auto-scroll until the current spoken sentence becomes visible again.
- Playback is available only when the device exposes a voice whose language matches the book language; a mismatched fallback voice is not acceptable.
- Existing reader event tracking can record one `audio.play` event whenever a sentence starts, without sentence-level payload data.

## Constraints

- Keep the existing `/books/[bookId]/[pageId]` reader route and translation interaction intact.
- Do not require server-side TTS, external audio storage, or an API-backed provider for the baseline feature.
- Keep speech-engine integration behind a small provider boundary so a future API-backed TTS provider can replace browser/device synthesis without rewriting reader playback orchestration.
- Use the actual active reader scroll container on both desktop and mobile; do not rely only on `window.scrollY`.
- Keep the page scrollable while playback is active.
- Do not auto-scroll on every speech boundary; only move the next sentence into the centered viewport when guided auto-scroll is active and that next sentence is outside the active viewport.
- Manual page scrolling must not seek, pause, or otherwise alter the active or next playback sentence.
- Guided auto-scroll must remain suspended after manual page scrolling until the currently spoken sentence is visible in the active reader viewport again.
- Cancel and clean up active utterances, timers, listeners, and highlighting when playback is closed, the page changes, or the component unmounts.
- Preserve sentence tapping and translation popover behavior during playback.
- Enable playback only when browser/device speech synthesis is supported and a matching book-language voice is available; provide an understandable unavailable state otherwise.
- Record an `audio.play` event each time a sentence starts, with `language`, `book_id`, and `page_id`; do not include sentence content or a sentence ID.
- Follow the authenticated app-page and reader component conventions already used by LingoCafe.
- Run `npm run qa` after implementation.

## Dos

- Do reuse the reader's existing sentence wrappers and translation anchors where practical.
- Do centralize playback state so the FAB, floating control, sentence highlighting, and active scroll surface stay synchronized.
- Do keep browser/device speech synthesis behind a narrow provider interface that a future API-backed TTS provider can implement.
- Do model paragraph boundaries explicitly so the two-second pause is deterministic.
- Do treat browser/device speech events as fallible and keep sentence-level playback working without word boundaries.
- Do test both desktop and mobile scroll containers, including a selected sentence start and a scroll-position start.
- Do make seeking visibly update the active sentence and scroll percentage.
- Do use the existing reader event tracker to emit one `audio.play` event for every sentence start without sentence-level payloads.

## Don'ts

- Don't replace or bypass the existing sentence translation interaction.
- Don't lock the reader to the active sentence or disable normal scrolling during playback.
- Don't let manual page scrolling seek, pause, or change playback position.
- Don't assume every device exposes speech boundary events or the same voice list.
- Don't send text to a new external speech service as part of the baseline task.
- Don't use a mismatched-language fallback voice when a matching book-language voice is unavailable.
- Don't record sentence text or a sentence ID in `audio.play` events.
- Don't create a second reader scroll-progress model just for playback.
- Don't leave an utterance, timer, or boundary listener running after playback is closed or the page changes.
- Don't broaden the task into persistent playlists, background audio, or cross-page continuous playback unless refinement explicitly adds that scope.
