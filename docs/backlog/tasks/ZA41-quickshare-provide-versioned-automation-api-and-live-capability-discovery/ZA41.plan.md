# Plan — QuickShare: Provide versioned automation API and live capability discovery

## Goal

Expose complete owner-scoped QuickShare automation through a versioned bearer API whose validation and documentation-as-API discovery are generated from the same live contracts as the human editor.

## Milestones

### Milestone 1 — Define the canonical automation contract

- [x] Step 1 — Build one operation and capability registry
  - Achieve: Describe stable operation IDs, resource types, templates, validators, limits, errors, availability, deprecation, replacement, removal timing, and disruptive effects from deployed contracts.
  - Create: Automation registry, JSON-schema-compatible serializers, versioned response/error/pagination envelopes, and contract tests.
  - Modify: Existing resource/template catalogs only to expose already-authoritative metadata.
  - Delete: Any duplicate automation-only type/template vocabulary.
  - Touch points: Zod validators, endpoint templates, `publishedUrl`, `nextPublicUrl`, lifecycle/disruption metadata.
  - Validation: Registry uniqueness, deterministic serialization, and proof that discovery schemas agree with server validators.
  - Notes: An unpublished resource serializes `publishedUrl: null`.

### Milestone 2 — Implement owner-scoped CRUD and draft routes

- [x] Step 2 — Add versioned list, create, read, and save operations
  - Achieve: Authenticate with KQ66, require an explicit supported type, accept optional custom ID, and manipulate only the represented account's authoritative drafts.
  - Create: `/api/quickshare/v1` collection/item routes and shared automation serializers.
  - Modify: Earlier QuickShare domain services only to expose reusable operations, not duplicate rules.
  - Delete: Nothing.
  - Touch points: Cursor pagination, UUID lookup, revision conflict, text, Markdown, web-page/assets, pinned template configuration.
  - Validation: Missing/unknown type, default short code, custom-ID conflict, repeated saves, every type, and cross-account/app denial tests.
  - Notes: Clients never choose owner IDs, handles, paths, or publication pointers.

- [x] Step 3 — Add coordinated Delete
  - Achieve: Delete drafts safely and require the stronger disruptive contract for ever-published resources, purging delivery before removing the record.
  - Create: Versioned delete operation/handler and confirmation-intent validation.
  - Modify: Shared lifecycle service only.
  - Delete: Nothing.
  - Touch points: Publication history, IF14 purge, deterministic conflicts/errors.
  - Validation: Purge failure preserves the record; foreign resources do not leak existence; successful delete leaves no output.
  - Notes: Discovery must state the irreversible effect.

### Milestone 3 — Add explicit publication lifecycle

- [x] Step 4 — Add Publish and Unpublish operations
  - Achieve: Compile and atomically publish through IF14 or purge delivery while retaining the draft.
  - Create: Versioned publish/unpublish routes or action handlers.
  - Modify: Shared lifecycle service only.
  - Delete: Nothing.
  - Touch points: Compiler selection, exact draft revision, identifier promotion, current/next URLs, disruption confirmation.
  - Validation: Publish every registered type, failed compile/activation preservation, repeated publish, identifier switch, and unpublish/republish tests.
  - Notes: Save never implies Publish.

### Milestone 4 — Publish token-authenticated live discovery

- [x] Step 5 — Expose documentation as API
  - Achieve: Return the effective methods, paths, request/response schemas, fields, enums, defaults, constraints, limits, errors, types, templates, and lifecycle metadata required to construct supported requests.
  - Create: `/api/quickshare/v1/discovery` GET route and discovery serializer.
  - Modify: Automation registry as gaps are found.
  - Delete: Nothing.
  - Touch points: Contract version, token-effective capabilities, deprecation timeline, destructive/disruptive markers.
  - Validation: Discovery requires a valid token, covers every exposed operation, is deterministic, and contains no secrets/deployment internals.
  - Notes: This endpoint is runtime truth for VG23.

- [x] Step 6 — Prove a discovery-driven generic workflow
  - Achieve: Use only token plus discovery to create, save, publish, inspect, unpublish, and delete every supported resource family.
  - Create: Generic test consumer, automation/discovery integration tests, and focused test scripts.
  - Modify: Nothing beyond fixes revealed by contract testing.
  - Delete: Test resources and output through production lifecycle operations.
  - Touch points: Default localhost app, seeded users, Nginx fetch, pending identifier changes.
  - Validation: `john/john` and `admin/admin` remain isolated, foreign-app tokens fail, public requests have no session dependency, focused tests and `npm run qa` pass.
  - Notes: The test consumer must not carry a second hard-coded payload catalog.

### Milestone 5 — Freeze the VG23 handoff

- [x] Step 7 — Document compatibility and stable operation semantics
  - Achieve: Define how compatible changes, deprecations, replacements, and contract-version breaks are communicated to clients.
  - Create: Maintainer-facing automation compatibility documentation.
  - Modify: Memory-bank feature documentation and canonical task notes.
  - Delete: Nothing.
  - Touch points: Stable operation IDs and schema evolution.
  - Validation: Review discovery examples against live responses and rerun all automation contract tests.
  - Notes: VG23 begins only when the whole lifecycle is discovery-driven.
