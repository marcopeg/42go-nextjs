# QuickShare: Provide versioned automation API and live capability discovery

## Elevator's Pitch

Expose QuickShare's complete owner-scoped resource workflow through a versioned bearer-token API whose live discovery contract teaches agents the currently supported operations, payloads, types, templates, and options.

## Business Gain

Agents and scripts can automate every supported share lifecycle without browser sessions, while dynamic documentation-as-API keeps integrations stable as compatible payloads and options evolve.

## Current State

The QuickShare task set defines resource domain services, static publication, and personal bearer-token authentication, but has no versioned automation routes or machine-readable capability discovery.

## Desired State

A dedicated versioned automation namespace authenticates the personal token from KQ66 and derives the represented QuickShare account. It provides list/read/create/update/delete plus explicit save, publish, and unpublish operations for every registered resource type. Creation requires a stable explicit type and may include an available custom ID. A token-authenticated GET discovery endpoint returns the effective live contract needed to construct and validate those requests without hard-coded payload knowledge.

## Definition of Success

Using only a valid token and discovery, an agent can learn the effective contract, create each supported resource kind, save it, publish it, inspect publication state, unpublish it, and delete it without crossing account or app boundaries. Compatible server-side payload or option changes require no skill rewrite.

## Additional Context

Discovery returns a contract version and effective resource-type/template catalog. Each operation describes its HTTP method, endpoint template, request and response schemas, required and optional fields, types, enum values, defaults, validation constraints and limits, supported actions, custom-ID rules, representative machine-readable errors, and lifecycle metadata such as availability, deprecation, replacement, and removal timing. Template entries include stable template ID/version and configuration schema. Resource responses expose publishedUrl for the currently working route and nextPublicUrl for the configured route. They differ only while a published resource has a pending identifier change; after successful Publish they converge, while an unpublished resource has publishedUrl null. Unpublish and Delete are separate disruptive operations and discovery describes their effects.

## Assumptions

The editor UI and automation API call the same domain authorization, validation, compiler, and publisher services. One owner-scoped API vocabulary covers all resource kinds while retaining kind-specific validated payload schemas.

## Constraints

Depend on all version-one resource types, IF14 publication, and KQ66 token authentication. Every automation endpoint, including discovery, requires a valid personal token. Derive owner and app scope from the verified token; clients never choose owner IDs, raw output paths, Nginx paths, or publication pointers. Do not authenticate automation with NextAuth cookies or expose token secrets, filesystem paths, or deployment internals.

## Acceptance Criteria

- A dedicated versioned automation namespace accepts personal bearer tokens without requiring a browser session.
- Missing, malformed, revoked, foreign-app, or otherwise invalid tokens fail closed without leaking account or resource existence.
- Token routes support owner-scoped list/read/create/update/delete, repeated draft save, explicit Publish, and explicit Unpublish for plain text, Markdown, web pages with managed assets, and registered template instances.
- Creation requires an explicit supported resource type; omission or an unknown type returns a clear validation error.
- Creation accepts an optional custom ID and returns the configured nextPublicUrl plus publishedUrl null until first publication.
- Published resources return publishedUrl and nextPublicUrl; the values differ only for a pending identifier change and converge after successful Publish.
- Unpublish purges complete delivery output while retaining the resource draft; Delete purges delivery output before resource-record removal.
- Token-scoped GET discovery returns the versioned live operation, schema, type, template, option, limit, error, and lifecycle metadata required to construct supported requests.
- Discovery and server validation derive from the same contracts used by the human creation catalog.
- API authorization, isolation, lifecycle, discovery-contract, and end-to-end publication tests pass.
- npm run qa passes.

## Dos

- Reuse shared domain services rather than duplicating UI business rules.
- Keep response envelopes, pagination, error semantics, and discovery contract versioned and deterministic.
- Mark destructive and disruptive operations so callers can obtain operator confirmation.

## Don'ts

- Do not let bearer clients select ownership or deployment internals.
- Do not hard-code a second resource-type vocabulary inside discovery.
- Do not include the maintained agent skill/client in this task.

## Open Questions

None that blocks planning; exact route names and schema serialization format belong to implementation planning.
