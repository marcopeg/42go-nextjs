# Restore Native Safari Browser-Chrome Collapse Across LingoCafe Mobile Reading Surfaces

## Elevator's Pitch

Refactor the LingoCafe Conversations library, Book Details page, and Book Reader on mobile so the root document owns vertical scrolling. Preserve each surface's sticky top chrome, fixed or sticky bottom controls, reader state, and full-screen visual treatment while allowing iPhone Safari to perform its native address-bar and toolbar collapse during user scrolling.

## Business Gain

- Recover the larger, native-feeling reading viewport already experienced on the Books and Profile pages.
- Make mobile scrolling consistent across discovery, conversation practice, book details, and reading.
- Remove mixed root-versus-nested scroll behavior that can strand application chrome or make gestures feel broken.
- Keep reader progress, playback, translation, and navigation reliable while using the browser's preferred scroll model.

## Current State

- Books and Profile use document-level scrolling, so iPhone Safari can automatically minimize its browser chrome when the user scrolls down.
- Conversations enables `AppLayout.containedMobileScroll`; the mobile app shell is fixed and `<main>` owns `overflow-y-auto`, which prevents normal document scrolling and therefore prevents Safari's browser chrome from minimizing.
- The contained Conversations shell was introduced to prevent a gesture beginning on the fixed bottom navigation from scrolling the outer document and stranding the 64 px app toolbar off-screen.
- Mobile Book Details renders a fixed `inset-0` / `100dvh` surface with an independently scrolling content element.
- The Book Reader is rendered inside an always-open full-screen Modal and its mobile reading surface owns an independently scrolling element.
- Reader progress calculation, progress restoration, playback auto-scrolling, page transitions, and scroll-derived header state currently depend on element-level `scrollTop`, `scrollHeight`, and scroll listeners.
- `containedMobileScroll` is also consumed by the backoffice Users page and must not be changed without an explicit regression audit.

## Desired State

- On mobile Safari, Conversations, Book Details, and Book Reader use the root document as their vertical scroller so normal user scrolling can minimize and restore Safari's browser chrome.
- Application headers remain sticky and bottom navigation, reading actions, playback controls, and floating controls remain safely positioned while Safari's visual viewport changes.
- Conversations no longer mixes an independently scrolling `<main>` with a separately scrollable document; a gesture starting from the bottom navigation cannot strand the app toolbar.
- Mobile Book Details keeps its full-page visual design, back control, independently useful content flow, and bottom reading action without a fixed `100dvh` scroll shell.
- The mobile Book Reader becomes a route-level document-scrolling surface rather than a body-locking full-screen Modal. Desktop may retain its current contained reader scroller when that remains the best desktop model.
- Reader scroll consumers use a shared abstraction that can read, observe, restore, and programmatically move either the mobile document scroller or the desktop element scroller.
- Temporary reader overlays such as Preferences and Contents may continue using Modal and body scroll locking, but closing them restores the exact document position without jumps.
- Installed/PWA mode, where Safari browser chrome does not exist, remains visually and functionally correct.

## Definition of Success

- On a real iPhone Safari session, upward content scrolling minimizes native browser chrome in all three target surfaces just as it already does in Books and Profile.
- The app's own top and bottom controls remain reachable and stable throughout native browser-chrome expansion and collapse.
- No gesture can reproduce the missing or permanently stranded app-toolbar failure.
- Reader progress, restoration, playback, translation, page navigation, and overlay behavior remain correct on mobile and desktop.

## Additional Context

- Safari controls browser-chrome visibility. The application can make native behavior possible through root-document scrolling but must not attempt to force or imitate browser UI state.
- Apple's viewport documentation distinguishes the page viewport from the visible area on iOS: https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/UsingtheViewport/UsingtheViewport.html
- Relevant WebKit discussion connects automatic toolbar visibility with root scrolling and dynamic viewport behavior: https://bugs.webkit.org/show_bug.cgi?id=261185
- Primary implementation areas include `AppLayout`, `ConversationLibraryShell`, mobile Book Details, the reader route and surfaces, reader progress persistence/restoration, playback auto-scroll, and Modal scroll restoration.
- The app shell changes at `md`/768 px; this task is primarily about the mobile scroll model below that breakpoint.

## Assumptions

- The desired reference behavior is the current Books/Profile behavior in normal iPhone Safari.
- Sticky application headers and fixed bottom controls can coexist with document scrolling when content padding and safe-area offsets are correct.
- Safari's native browser UI may vary by iOS version, tab-bar configuration, orientation, and standalone/PWA mode; success means enabling supported native behavior rather than guaranteeing a particular browser-owned animation.
- Desktop reader containment may remain element-based if mobile and desktop scroll access is cleanly abstracted.
- The task should audit but not automatically redesign unrelated `containedMobileScroll` consumers such as Backoffice Users.

## Constraints

- Do not use fixed full-viewport or nested `overflow-y-auto` containers as the primary mobile page scroller on the three target surfaces.
- Do not use JavaScript scroll loops, synthetic gestures, viewport-height tricks, or fake browser chrome to imitate Safari's UI collapse.
- Do not weaken Modal focus management or body locking for genuine temporary overlays.
- Preserve the standard 64 px app header and mobile navigation contracts, semantic safe-area spacing, light/dark themes, keyboard access, and reduced-motion behavior.
- Preserve the reader's existing URL/server progress override rules, bounded restoration behavior, progress persistence, playback continuation, automatic sentence scrolling, and horizontal page-swipe discrimination.
- Avoid changing desktop layout or scrolling unless required by a shared abstraction and covered by regression tests.
- Verify on physical iPhone Safari because desktop responsive emulation cannot prove browser-chrome behavior.

## Acceptance Criteria

- [ ] Conversations uses document-level vertical scrolling on mobile and no longer requires a fixed viewport shell or nested full-page `<main>` scroller.
- [ ] A vertical gesture beginning on or immediately above the mobile bottom navigation cannot scroll the app toolbar away or strand the document at an unrecoverable offset.
- [ ] Mobile Book Details uses document scrolling while preserving its full-page treatment, sticky back/header region, content layout, and bottom reading action.
- [ ] Mobile Book Reader uses document scrolling without placing the main reader surface inside a body-locking full-screen Modal.
- [ ] The reader header remains sticky and reader floating/playback controls remain correctly fixed with safe-area spacing as Safari browser chrome expands or collapses.
- [ ] Reader progress calculation and persistence use correct document metrics on mobile and retain correct element metrics on desktop.
- [ ] Reader progress restoration works from both explicit URL progress and persisted same-page progress without visible bounce or repeated restoration.
- [ ] Playback sentence focusing, manual-scroll detection, progressive reveal, page continuation, and progress saves remain correct with the mobile document scroller.
- [ ] Horizontal reader page swipes remain distinct from vertical document scrolling and text selection.
- [ ] Opening and closing Preferences, Contents, translation surfaces, and other temporary overlays preserves the exact underlying document scroll position.
- [ ] Normal iPhone Safari minimizes its native browser chrome when the user scrolls down within Conversations, Book Details, and Book Reader, and can reveal it again through normal native interaction.
- [ ] Books and Profile retain their current working mobile scrolling behavior.
- [ ] Installed/PWA mode remains usable without browser chrome, viewport gaps, or controls hidden behind safe areas.
- [ ] Desktop Conversations, Book Details, and Reader behavior remains unchanged unless an intentional shared-scroll abstraction change is explicitly verified.
- [ ] Automated coverage protects root-scroller selection, sticky/fixed chrome, reader progress/restoration, overlay scroll restoration, and the original missing-toolbar regression.
- [ ] Physical-device checks cover current iPhone Safari in portrait, browser chrome expanded and minimized, plus at least one installed/PWA smoke check.
- [ ] Checks at approximately 390 px, 768 px, and 1280 px confirm the responsive handoff and absence of horizontal scrolling.
- [ ] `npm run qa` passes.

## Dos

- Use `document.scrollingElement` or a small typed scroll-target abstraction for mobile document metrics and desktop element metrics.
- Keep route-level content in normal document flow and reserve Modal for temporary overlays.
- Preserve sticky headers and fixed bottom actions with explicit content offsets and safe-area padding.
- Test the original bottom-navigation gesture as well as ordinary content scrolling.
- Test progress save/restore near the top, middle, and end of a reader page.
- Audit every consumer of `containedMobileScroll` before changing or removing its shared contract.

## Don'ts

- Do not declare success from desktop device emulation alone.
- Do not make the whole document fixed or body-locked during normal page reading.
- Do not duplicate reader progress logic separately for mobile and desktop when one scroll-target abstraction can express both.
- Do not sacrifice sticky application controls to obtain Safari browser-chrome collapse.
- Do not broaden the task into a visual redesign of Conversations, Book Details, or Reader.
- Do not alter authorization, data contracts, reading content, or unrelated navigation policies.

## Open Questions

- What minimum iOS/Safari version must be supported beyond the operator's current physical device and latest stable Safari?
- Should the shared `containedMobileScroll` option remain for dense backoffice pages, be renamed to clarify its browser-chrome tradeoff, or be replaced by a narrower desktop-only/internal-scroll contract?
- Should desktop Reader retain its current element scroller, or should the task pursue one document-scroll model at all breakpoints if validation shows no regression?
