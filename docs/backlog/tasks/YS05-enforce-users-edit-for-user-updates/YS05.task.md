# Enforce users:edit for User Updates

## Elevator's Pitch

Repair user-update authorization so `PATCH /api/users` and its eventual backoffice-namespaced successor require the dedicated `users:edit` grant end to end, with consistent production provisioning, client capability gating, and tests.

## Business Gain

- Restore least-privilege separation between viewing users and modifying them.
- Prevent operators with list-only access from changing account data.
- Make the existing `users:edit` grant real and dependable across supported apps instead of leaving it partially seeded and unenforced.

## Current State

- `PATCH /api/users` currently requires `users:list`, so list permission also authorizes updates.
- `users:edit` is defined in the default authentication seed but is not consistently assigned to the app-scoped backoffice role.
- The LingoCafe test-user seed provisions `users:list` and `users:delete` but does not consistently provision/assign `users:edit`.
- The users client gates deletion through `users:delete` but does not expose an equivalent reliable `users:edit` capability boundary.
- Changing only the PATCH policy would break legitimate editors where the grant has not been provisioned.

## Desired State

- Require `users:edit` for every user-update API handler while retaining `users:list` for list/read and `users:delete` for account erasure.
- Provision the global `users:edit` grant and its intended app-scoped backoffice-role assignments through a production-safe, idempotent mechanism rather than relying only on development seeds.
- Expose a clear client `canEditUsers` capability and hide or disable edit actions when the session lacks `users:edit`.
- Return the platform-standard forbidden response when a list-only operator attempts a direct update.
- Keep behavior consistent before and after the separate `/backoffice/users` route migration.

## Definition of Success

- Viewing users never implies permission to modify them.
- Existing intended backoffice editors retain access after deployment because grant assignment is migrated safely.
- API, client UI, session grants, and tests agree on the same exact permission.

## Additional Context

- Current GET and PATCH policies are in `src/app/api/users/route.ts`.
- Current client policy and capability checks are in `src/app/(app)/users/page.tsx`.
- Global grants and app-scoped role mappings live in `auth.grants` and `auth.roles_grants`.
- Existing relevant grants are `users:list`, `users:edit`, and `users:delete`.

## Assumptions

- `users:edit` remains the canonical exact grant name.
- The app-scoped `backoffice` role is intended to receive edit permission in apps that expose user administration unless refinement documents exceptions.
- This security fix should be independently deployable before or after the route migration.

## Constraints

- Grant checks remain exact; do not introduce wildcard grants.
- Do not depend only on seeds for production authorization state.
- Do not weaken app scoping, session checks, role checks, list access, or deletion access.
- Do not move user routes as part of this task.
- Use parameterized database operations and run `npm run qa`.

## Acceptance Criteria

- [ ] User-update PATCH handlers require feature `api:users`, authenticated session, current app, role `backoffice`, and exact grant `users:edit`.
- [ ] GET/list continues to require `users:list`; DELETE/account erasure continues to require `users:delete`.
- [ ] A production-safe idempotent migration/provisioning path ensures `users:edit` exists and assigns it to each intended app-scoped backoffice role.
- [ ] Default and LingoCafe development/test provisioning agree with production grant state.
- [ ] The users client derives `canEditUsers` from the authenticated session grants.
- [ ] Edit controls are hidden or disabled with an accessible explanation when `users:edit` is absent.
- [ ] Direct PATCH by an authenticated backoffice user with `users:list` but without `users:edit` returns 403 and performs no write.
- [ ] A user with `users:edit` can perform the existing valid update workflow.
- [ ] Tests cover list-only, edit-capable, delete-only/relevant mixed-grant, wrong-app, unauthenticated, and non-backoffice cases.
- [ ] Authorization and operator documentation describes the distinct list/edit/delete grants.
- [ ] `npm run qa` passes.

## Dos

- Audit existing role assignments before changing the handler requirement.
- Make grant provisioning idempotent and safe for existing databases.
- Keep server enforcement authoritative even when the UI hides controls.
- Test exact app-scoped roles and grants.

## Don'ts

- Do not fix the API policy without provisioning the grant for intended editors.
- Do not treat `users:list` as edit permission.
- Do not grant `users:edit` globally to every authenticated user.
- Do not bundle the `/backoffice/users` route move into this task.

## Open Questions

- Should every existing app-scoped backoffice role receive `users:edit` automatically, or only apps that expose both `page:users` and `api:users`?
- Should missing edit permission hide edit controls entirely or render them disabled with an explanation?
- Does any non-backoffice role intentionally hold `users:edit` and need preservation?
