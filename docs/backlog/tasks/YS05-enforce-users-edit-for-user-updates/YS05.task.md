# Enforce users:edit for User Updates

## Elevator's Pitch

Repair user-update authorization so `PATCH /api/backoffice/users` requires the dedicated `users:edit` grant end to end, with consistent development provisioning, an operator-run production SQL script, standard client policy gating, and tests.

## Business Gain

- Restore least-privilege separation between viewing users and modifying them.
- Prevent operators with list-only access from changing account data.
- Make the existing `users:edit` grant real and dependable across supported apps instead of leaving it partially seeded and unenforced.

## Current State

- User administration has already moved to `/backoffice/users` and `/api/backoffice/users`; the legacy `/users` and `/api/users` routes no longer exist.
- `PATCH /api/backoffice/users` currently requires `users:list`, so list permission also authorizes `update-user`, `reset-profile`, and `reset-consent`.
- `users:edit` exists in the initial authentication seed, but the default app's backoffice role is not assigned it consistently.
- The current LingoCafe test-user seed already defines `users:edit` and assigns it to the LingoCafe backoffice role.
- The users client gates deletion through a direct session check for `users:delete`, but its edit and reset controls have no equivalent `users:edit` boundary.
- Changing only the PATCH policy would break legitimate editors where the grant has not been provisioned.

## Desired State

- Require `users:edit` for all three PATCH operations: `update-user`, `reset-profile`, and `reset-consent`; retain `users:list` for list/read and `users:delete` for account erasure.
- Make the default and LingoCafe development/test seeds consistently define `users:edit` and assign it to their app-scoped backoffice roles.
- Add an idempotent, transaction-wrapped SQL file inside the YS05 task folder that creates `users:edit` if missing and assigns it to every existing app-scoped `backoffice` role. Document manual execution, verification, and rollback guidance. Do not execute the script as part of this task.
- Do not add or use a Knex migration for authorization-data provisioning. No schema change is required.
- Wrap edit, reset-profile, and reset-consent controls with the standard client `ProtectComponent`, using an exact `users:edit` policy and null loading/error renderers so unauthorized controls are not displayed.
- Return the platform-standard forbidden response when a list-only operator attempts a direct update.
- Preserve all existing role/grant mappings, including `users:edit` mappings for non-backoffice roles.

## Definition of Success

- Viewing users never implies permission to modify them.
- Existing intended backoffice editors can be provisioned safely by the operator before or with deployment, without an automatic production data mutation.
- API, client UI, session grants, and tests agree on the same exact permission.

## Additional Context

- Current GET, PATCH, and DELETE policies are in `src/app/api/backoffice/users/route.ts`.
- Current client policy and capability checks are in `src/app/(app)/backoffice/users/page.tsx`.
- The standard conditional UI primitive is `ProtectComponent` from `@/42go/policy/client`; repository menu code demonstrates silent omission with null loading/error renderers.
- Global grants and app-scoped role mappings live in `auth.grants` and `auth.roles_grants`.
- Existing relevant grants are `users:list`, `users:edit`, and `users:delete`.

## Assumptions

- `users:edit` remains the canonical exact grant name.
- Every existing app-scoped `backoffice` role is intended to receive `users:edit`; feature flags continue to determine whether an app exposes user administration.
- The operator will decide when to execute the supplied SQL against existing environments.

## Constraints

- Grant checks remain exact; do not introduce wildcard grants.
- Do not create a migration that inserts, updates, or deletes authorization data.
- Do not execute the operator SQL file.
- Keep the operator SQL idempotent, parameterized where inputs are needed, transaction-wrapped, and limited to `users:edit` plus missing backoffice mappings.
- Do not weaken app scoping, session checks, role checks, list access, or deletion access.
- Do not recreate or modify the removed legacy user routes.
- Use parameterized database operations and run `npm run qa`.

## Don'ts

- Do not treat `users:list` as edit permission.
- Do not grant `users:edit` globally to every authenticated user.
- Do not mutate authorization data through a Knex migration.
- Do not execute the task's operator SQL script.
- Do not touch existing non-backoffice grant assignments.
