# Refinement Questions v1 — Enforce users:edit for User Updates

Answer inline under each question, then return to chat and say `next round`.

## Questions

### 1. Which PATCH operations require `users:edit`?

The current `/api/backoffice/users` PATCH handler performs three operations:
`update-user`, `reset-profile`, and `reset-consent`.

Should `users:edit` authorize all three operations, or should profile/consent
resets use a different grant?

Recommendation: require `users:edit` for all three because each operation
modifies another user's account data and they currently share one PATCH
authorization boundary.

Answer:

`users:edit` for all three

### 2. Which app-scoped backoffice roles should receive `users:edit` during migration?

Should the idempotent production migration assign `users:edit` to every app
that already has an app-scoped `backoffice` role, or only to apps known to
expose both `page:users` and `api:users`?

Recommendation: assign it to every existing app-scoped `backoffice` role. This
matches the current authorization model, avoids coupling a database migration
to runtime AppConfig, and does not grant access unless the app also exposes the
user-management features.

Answer:

No, the migration should not add roles to existing data. The migration should only contain structural changes to the schema. And you can add those roles to the back office in the development seeds, but for existing applications you can add a SQL file inside the task folder with instructions to automatically create the grant and apply it to the back office role, but you should not execute it. I will execute it manually.

### 3. How should the backoffice users UI behave without `users:edit`?

The edit button, the row-menu edit action, and the reset-profile/reset-consent
actions can either be hidden or remain visible but disabled with a missing-grant
explanation.

Recommendation: keep them visible but disabled with an accessible
`Missing users:edit grant` explanation. This makes the list-only role legible
without pretending those capabilities do not exist.

### 4. How should existing non-backoffice `users:edit` assignments be treated?

Recommendation: preserve every existing assignment. The migration should only
ensure the grant exists and add missing app-scoped backoffice mappings; it
should not revoke or reinterpret mappings for other roles.

Answer:

the migration should not touch the data
