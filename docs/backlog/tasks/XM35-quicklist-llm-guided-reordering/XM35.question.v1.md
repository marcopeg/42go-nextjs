# Refinement Questions v1 — QuickList LLM-Guided Reordering

Answer inline under each question, then return to chat and say `next round`.

## Questions

### 1. Who may edit a list's sorting instructions?

Recommendation: use the same permissions as ordinary list settings. Owners and collaborators who can already rename, change mode, and reorder the list may edit the instructions. This keeps the instructions aligned with the users who can act on them through the UI or bearer-token API.

Alternative: owner-only editing, matching the API-exposure switch rather than ordinary list settings.

Answer:

Use the same permissions as ordinary list settings. Owners and collaborators who can already edit those settings may edit sorting instructions.

### 2. What exact body should the reorder POST accept?

Recommendation: make it a literal GET-edit-POST round trip. `GET /api/quicklists/v1/{listId}/reorder` returns:

```json
{
  "list": {
    "id": "list-id",
    "name": "Shopping",
    "sortingInstructions": "Group produce first, then pantry items."
  },
  "items": [
    {
      "id": "item-id",
      "text": "Apples",
      "position": 1
    }
  ]
}
```

`POST` accepts that same envelope after the LLM changes only `items[].position`. The path list ID remains authoritative. The server verifies that list metadata and item text still match current data and rejects altered or stale context instead of treating those fields as mutations.

Alternative: POST accepts only `{ "items": [{ "id": "...", "position": 1 }] }`, while GET keeps the richer context envelope.

Answer:

Use the compact mutation payload only:

```json
{
  "items": [
    {
      "id": "item-id",
      "position": 1
    }
  ]
}
```

POST does not receive list metadata or item text.

### 3. How much sorting-instruction text should one list allow?

Recommendation: plain text, optional, trimmed on save, maximum 4,000 Unicode characters. An empty or whitespace-only value clears the instructions and GET returns an empty string. This is enough for useful LLM guidance without turning list settings into a document store.

Answer:

Accept the recommendation. Enforce a 4,000-character maximum on sorting instructions at the server boundary.

Also standardize list names and item text at a maximum of 250 characters. Enforce these limits server-side across their create and update paths.

### 4. Should POST protect against a list changing after the LLM's GET?

Recommendation: yes. GET returns an opaque revision/ETag derived from reorder-relevant state: list name, sorting instructions, item IDs, item text, and positions. POST requires that revision through `If-Match` or an equivalent body field and returns `409 Conflict` without changes when it is stale. The agent then fetches and reasons again. Completion status is excluded because it is deliberately invisible and does not affect the requested sort context.

Alternative: validate only the submitted complete item set. This rejects added/deleted items but permits overwriting an order or text context that changed after GET.

Answer:

Accept the recommendation. Protect POST from stale GET context using the proposed opaque revision/ETag flow.

### 5. Confirm the public names.

Recommendation:

- Endpoint: `GET/POST /api/quicklists/v1/{listId}/reorder`
- List Info action: **Sorting instructions**
- Editor title: **Sorting instructions**
- Primary action: **Save instructions**

This keeps the API resource short and the UI language focused on what the user is writing.

Answer:

Accept all recommended public names.
