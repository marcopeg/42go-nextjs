# QuickList: Refresh Open List After Rotation to Portrait

## Elevator's Pitch

When a phone is displaying an individual QuickList and rotates from landscape to portrait, trigger a best-effort background refresh of that open list so the portrait view immediately reconciles with the latest server state.

## Business Gain

- Users returning from the landscape-only phone experience see current list contents without tapping refresh or leaving the list.
- Shared-list changes made by collaborators are pulled in at a natural device transition with no full-page reload or visible interruption.
- The behavior remains isolated to QuickList and does not add orientation-driven network traffic to other applications.

## Current State

- QuickList individual-list data is owned by `useQuicklistData`, with conditional background checks implemented by `useQuicklistPolling`.
- The poller already pauses while hidden, prevents overlapping requests, uses an ETag-backed conditional fetch, and avoids applying background data across active mutations.
- QuickList can refresh on configured polling intervals and foreground/resume signals, but it does not explicitly react to a landscape-to-portrait orientation transition.
- The shared `AppQrOverlay` already observes a phone-landscape media query through `window.matchMedia`, but that UI is framework-wide and must not become the owner of QuickList data refresh behavior.

## Desired State

- While `/quicklists/[id]` is mounted on an iPhone or Android-class smartphone, remember the prior orientation and detect a real transition from landscape to portrait. Use the existing practical phone boundary from the landscape QR behavior, or an equivalent smartphone-specific check; tablets and desktop browsers do not qualify.
- On that transition, request one background refresh for the currently open list using the existing QuickList conditional-fetch/reconciliation path where practical.
- The trigger is independent of the account's scheduled auto-refresh level, including when scheduled polling is Off; it is a device-transition refresh, not a polling interval.
- Keep the current list visible during the request. Apply changed authoritative data without a route reload, full-document reload, loading-screen flicker, or scroll reset; do nothing visible for an unchanged response.
- Coalesce duplicate orientation/resize signals and preserve the existing in-flight request and optimistic-mutation protections. If a mutation or refresh is active when the transition occurs, discard the orientation signal without deferring a later check.
- Register and clean up the chosen browser listeners only for the mounted QuickList detail experience. Prefer native browser APIs unless refinement identifies a concrete cross-browser need for a small hook library.

## Definition of Success

- Rotating a phone from landscape to portrait with an individual QuickList open initiates one safe background check and displays newer server data when present.
- The transition causes no full-page navigation and no visible refresh state when the list is unchanged.
- No orientation-triggered refresh occurs on the QuickList overview, settings/info pages, tablets, desktop browsers, or non-QuickList apps.
- Portrait-to-landscape changes and initial portrait rendering do not trigger this refresh.

## Additional Context

- Primary touch points: `src/lib/quicklists/hooks/useQuicklistPolling.ts`, `src/lib/quicklists/hooks/useQuicklistData.ts`, and `src/app/(app)/quicklists/[id]/page.tsx`.
- Existing orientation detection reference: `src/42go/components/AppQrOverlay/AppQrOverlay.tsx` uses `window.matchMedia` and a phone-landscape media query.
- Related completed work VT60 established conditional QuickList polling, resume-signal coalescing, and mutation-race protection.

## Assumptions

- A background reload means refreshing the list data in place, not calling `window.location.reload()`.
- The behavior applies only to a concrete QuickList list-detail page and not to `/quicklists` or `/quicklists/[id]/info`.
- The orientation-triggered check should still happen when scheduled auto-refresh is Off.
- Only smartphones such as iPhone and Android phones qualify. Tablets and desktop browsers are explicitly excluded.
- If a mutation or another refresh is active, discard the orientation signal. Do not queue or defer a check for when the active work settles.

## Constraints

- Keep the implementation QuickList-owned; do not add app-specific refresh behavior to shared `42go` layout or QR-overlay components.
- Do not introduce a full browser/document reload.
- Do not overwrite optimistic edits, duplicate an in-flight request, or apply a stale response after a newer mutation.
- Use a reliable smartphone/orientation signal with listener cleanup and compatibility fallbacks appropriate to supported iPhone and Android phone browsers or installed-app modes.
- Preserve the existing practical smartphone boundary used by the landscape QR behavior, or an equivalent check; do not broaden the feature to tablets or desktop browsers.
- Avoid adding a dependency unless native APIs cannot satisfy the supported-browser contract.

## Acceptance Criteria

- [ ] With `/quicklists/[id]` open on a supported iPhone or Android-class smartphone, one landscape-to-portrait transition schedules exactly one conditional background list check.
- [ ] If the server list changed, the current title and tasks reconcile to the authoritative response without navigating away or resetting the page.
- [ ] If the server returns an unchanged result, the UI does not flicker, replace state, or expose a loading screen.
- [ ] The orientation trigger works even when the QuickList scheduled auto-refresh preference is Off.
- [ ] Initial portrait mount, portrait-to-landscape rotation, unrelated resize noise, and duplicate browser orientation events do not cause extra portrait-transition checks.
- [ ] No orientation-triggered list request runs on `/quicklists`, `/quicklists/[id]/info`, other QuickList routes, tablets, desktop browsers, or any other configured app.
- [ ] If an active manual refresh, background check, or optimistic list/task mutation exists when portrait is detected, the orientation signal is discarded without starting, queuing, or deferring another check.
- [ ] Event/media-query listeners and any timers are removed when the list route unmounts or the project ID changes.
- [ ] Automated tests cover transition detection, signal coalescing, Off-level behavior, route cleanup, and mutation/in-flight guards.
- [ ] Mobile verification covers at least the supported iPhone/Safari or installed-PWA flow and one Chromium-based mobile flow where available.
- [ ] `npm run qa` passes.

## Dos

- Reuse the existing ETag-backed conditional refresh and cache reconciliation behavior.
- Model the transition from the previous orientation state rather than treating every portrait event as a refresh.
- Keep the request best-effort and preserve the current list while it runs.

## Don'ts

- Do not call `window.location.reload()`.
- Do not refresh every app because the shared layout observed an orientation change.
- Do not start another request when one is already active or while local mutations are unsafe to reconcile.
- Do not assume a resize event alone uniquely identifies phone rotation.
