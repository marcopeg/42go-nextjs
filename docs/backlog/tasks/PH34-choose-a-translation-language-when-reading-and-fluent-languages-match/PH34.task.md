# Choose a Translation Language When Reading and Fluent Languages Match

## Elevator's Pitch

Prevent LingoCafe reader translation failures when the book's reading language and the user's fluent language are the same. Instead of attempting an invalid same-language translation, show a compact "Translate to" language selector in the reader translation experience, save the chosen language as the user's fluent language, and continue the requested translation.

## Business Gain

Readers can recover from an incorrect or incomplete language profile without leaving the story or seeing a generic translation error. The flow also corrects the durable profile setting, so later translations use a meaningful language direction automatically.

## Current State

The reader page API exposes the book language as the translation source and the user's `ownLang` profile value as the translation target. The translate endpoint validates uncached requests against `profile.targetLang` and `profile.ownLang`. When the reading language (`targetLang` / book language) and fluent language (`ownLang`) are identical, the reader still attempts the request and the translation provider returns an error. The current translation popover can show loading, success, or a generic error, but it cannot ask the reader to choose a different target language.

## Desired State

Before making a translation request, compare the normalized source reading language with the normalized fluent/translation-target language. When they differ, preserve the existing translation flow. When they match, do not call the translation endpoint or provider. Open the existing reader translation surface with a clear prompt such as "Which language do you want me to translate to?" and a simple `Translate to` dropdown populated from the existing LingoCafe fluent-language profile choices. Exclude the current reading language; for example, Swedish must not appear while reading a Swedish book. Selecting a language is the complete action: immediately persist it through the established profile update flow as `ownLang`, update the active reader state, and automatically continue the original word or sentence translation without another tap or confirmation button. The backend must also reject every same-language translation request before cache lookup or provider use so a modified or stale client cannot reproduce the error.

## Definition of Success

Tapping a translatable word or sentence never produces the current provider error solely because the reading and fluent languages match. The reader is asked for a valid destination language, the selection becomes the durable fluent-language profile setting, and the pending translation completes in the chosen language. Existing translation behavior remains unchanged when the two languages already differ.

## Additional Context

The core reader UI is in `src/app/(app)/(lingocafe)/books/_components/BookPageReader.tsx`. The reader page response derives translation `to` from `ownLang` in `src/app/api/(lingocafe)/lingocafe/books/[bookId]/pages/[pageId]/route.ts`. Supported fluent and reading languages plus profile validation live in `src/config/lingocafe/profile-options.ts`. Profile editing already exists in `LingocafePreferences.tsx` and the shared `/api/profile` flow. Server-side direction checks live in `src/app/api/(lingocafe)/lingocafe/translate/route.ts`. The selector belongs to the translation interaction that exposed the conflict; it should not force the reader to navigate away to settings.

## Assumptions

- The user's fluent language is the profile field `ownLang`; the reading/learning language is `targetLang` and should agree with the current book language.
- The selector uses the existing LingoCafe `ownLang` profile choices rather than an unrestricted provider language list.
- Selecting a destination language is a durable profile change, not a one-off override for one translation.
- Selecting a destination language immediately starts the save operation; there is no separate confirmation or `Translate` button.
- After a successful profile update, the reader automatically resumes the exact pending translation selection.
- Both full-sentence and single-word translation modes must use this conflict-resolution flow.
- Language comparison should use the same normalization rules as the translation backend.

## Constraints

- Do not call Google Translate or `/api/lingocafe/translate` while normalized source and destination languages are the same.
- Do not include the current reading language in the destination choices.
- Persist the selected destination through the existing validated profile API as `ownLang`; do not create a second translation-only preference.
- Keep the translation selector compact and usable in the existing reader popover on mobile and desktop.
- Preserve translation authorization, global enablement, page-content validation, cache behavior, and sentence/word scope rules.
- Handle profile-save failures explicitly and do not issue the pending translation until persistence succeeds.
- Do not change the user's reading language or book filter as part of resolving the conflict.
- Run `npm run qa` after implementation.

## Acceptance Criteria

- When normalized reading/source language and fluent/destination language differ, tapping a word or sentence follows the existing translation flow without an extra prompt.
- When normalized reading/source language and fluent/destination language match, the reader does not send a translation request.
- The active translation surface explains that a destination language must be chosen and shows a clearly labeled `Translate to` dropdown.
- The dropdown is populated from the existing LingoCafe fluent-language profile choices and does not include the active reading language.
- Choosing a valid destination language saves it as the user's `ownLang` through the established profile update flow.
- Choosing a language immediately starts the save-and-translate flow without a separate confirmation button.
- The reader shows an appropriate saving/loading state and prevents duplicate submissions while the profile update is pending.
- After the profile update succeeds, the active reader state uses the new destination language and automatically completes the originally requested word or sentence translation.
- The saved fluent-language choice is reflected in normal LingoCafe profile settings and remains effective after reload and on later reader visits.
- If the profile update fails, the reader shows a client-safe error, keeps the language selector available, and does not call the translation provider.
- The flow works for both full-sentence and single-word translation modes.
- The selector is keyboard accessible, has an accessible label, and remains usable on mobile and desktop.
- The backend rejects translation requests whose normalized `from` and `to` languages are equal before cache lookup, event creation, or any provider call.
- Same-language rejection returns a specific client-safe validation response rather than a generic provider failure.
- No translation event or cache entry is created for a rejected same-language request.
- Tests or smoke checks cover differing languages, same-language prompting, successful profile persistence and automatic retry, profile-save failure, and direct same-language API rejection.
- `npm run qa` passes after implementation.

## Dos

- Reuse the existing reader translation popover and profile update infrastructure.
- Use the canonical language labels and codes from LingoCafe profile options.
- Keep the pending translation selection intact while the reader chooses and saves a destination language.
- Normalize language codes consistently on the client and server.
- Make the corrective action understandable without requiring knowledge of `ownLang` or `targetLang` field names.

## Don'ts

- Do not show the existing generic translation error for this known profile conflict.
- Do not translate text into the same language.
- Do not silently pick a destination language for the user.
- Do not make the choice temporary or store it only in local storage.
- Do not redirect the reader to the profile page to finish the translation.
- Do not broaden this task into adding new provider-supported languages beyond the current product language options.
