# QuickShare: Establish isolated app, account onboarding, and data model

## Elevator's Pitch

Create the isolated QuickShare application boundary and durable account-scoped source-of-truth database model.

## Business Gain

All later QuickShare work rests on a clean product boundary that cannot inherit QuickNotes data, URLs, or behavior.

## Current State

No QuickShare AppConfig, hostname match, data schema, onboarding, handle namespace, or editor account space exists.

## Desired State

A new QuickShare AppConfig resolves quickshare.42go.dev. Authenticated users are required to select an app-unique normalized handle before authoring. Additive migrations create a QuickShare-owned schema for accounts, permanent resources, typed database-authoritative drafts, template instances, publication metadata, URL identifiers, immutable release versions, bundle manifests, and emitted asset records; ownership is server-derived and app scoped.

## Definition of Success

QuickShare accounts have isolated handles and can own durable resource records without observing or mutating any other account, app, or QuickNotes data.

## Additional Context

The resource model must support four authoring modes without sharing QuickNotes storage: plain text, Markdown, advanced web page, and template instance. A template draft records a stable template ID, explicit template version, and validated configuration. A publication version records the exact draft revision and bundle manifest that produced it. The random short code is globally unique and stable across resource updates; an optional normalized custom ID is unique within the current account handle.

## Assumptions

- Publication records may reference many emitted files; no schema assumption limits a release to one HTML document.
- Template catalog code is deployed with the application while account-entered template configuration remains database source of truth.

## Constraints

Use intended prior handle availability rules: normalize deterministically, enforce uniqueness transactionally in the QuickShare account namespace, and expose safe availability validation. Do not reuse a shared resource model or temporary lifecycle. Preserve QuickNotes unchanged. Use additive migrations and host-only editor cookies.

## Acceptance Criteria

- quickshare.42go.dev resolves only the new QuickShare AppConfig and protected editor surface.
- First authenticated authoring requires completed QuickShare handle onboarding.
- Normalized handle uniqueness and account ownership are enforced in PostgreSQL transactions.
- The schema models permanent typed drafts, publish metadata, stable random codes, optional handle/custom IDs, immutable release versions, bundle manifests, and sidecar assets without using QuickNotes tables.
- Template instances persist template ID, pinned template version, and validated account-owned configuration without duplicating rendered output as source of truth.
- Public identifier validation reserves any internal release/asset namespace required by the Nginx and future object-key layout.
- Cross-account and cross-app reads or writes fail closed.
- Migration, policy, and QA checks pass.

## Dos

- Use stable internal resource identity independently from mutable draft content and public path aliases.
- Keep draft revisions and publication versions traceable enough to reproduce what was released.

## Don'ts

- Do not infer ownership from handles, custom IDs, short codes, or filesystem paths.
- Do not model template output or publication files as the editable source of truth.

## Open Questions

None that blocks this foundation; exact table names and normalization helpers belong to implementation planning.
