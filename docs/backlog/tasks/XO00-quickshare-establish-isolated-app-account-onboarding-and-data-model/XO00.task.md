# QuickShare: Establish isolated app, account onboarding, and data model

## Elevator's Pitch

Create the isolated QuickShare application boundary and durable account-scoped source-of-truth database model.

## Business Gain

All later QuickShare work rests on a clean product boundary that cannot inherit QuickNotes data, URLs, or behavior.

## Current State

No QuickShare AppConfig, hostname match, data schema, onboarding, handle namespace, or editor account space exists.

## Desired State

A new QuickShare AppConfig resolves quickshare.42go.dev. Authenticated users are required to select an app-unique normalized handle before authoring. Additive migrations create a QuickShare-owned schema for accounts, durable explicitly deletable resources, typed database-authoritative drafts, template instances, publication metadata, URL identifiers, immutable release versions, bundle manifests, and emitted asset records; ownership is server-derived and app scoped.

Handles remain editable. A replacement handle is normalized and availability-checked transactionally before a strongly confirmed change. Resource lifecycle distinguishes draft-only, published, and unpublished-again states; Unpublish preserves the database record and draft, while Delete removes the account-owned resource after the appropriate confirmation contract and supports coordinated delivery-output purge.

## Definition of Success

QuickShare accounts have isolated handles and can own durable resource records without observing or mutating any other account, app, or QuickNotes data.

## Additional Context

Each resource type has a stable machine-readable identifier shared by database validation, UI creation choices, token/API creation payloads, and agent-readable type discovery. Clients cannot invent or omit the type on creation, and the system must not maintain divergent type vocabularies for people and agents.

The resource model must support four authoring modes without sharing QuickNotes storage: plain text, Markdown, plain HTML/CSS/JavaScript web page, and template instance. A template draft records a stable template ID, explicit template version, and validated configuration. A publication version records the exact draft revision and bundle manifest that produced it. Every resource has an internal UUID independent of public paths and exactly one active public identifier: creation assigns a globally unique random short code, while an optional normalized custom ID replaces and removes that code and is unique only within the current account handle. Removing a custom ID generates a new random short code rather than restoring the former one. The current public-path mapping must support either atomic identifier change on a later publish, without changing the resource UUID or release history.

The persistence and domain contract distinguish nullable `publishedUrl` from configured `nextPublicUrl`. The values differ only while a published resource has a pending short-code/custom-ID switch; content-only edits do not change either URL. Successful Publish atomically promotes the candidate and retires the prior route. Unpublished resources have `publishedUrl: null`.

## Assumptions

- Publication records may reference many emitted files; no schema assumption limits a release to one HTML document.
- Template catalog code is deployed with the application while account-entered template configuration remains database source of truth.

## Constraints

Use intended prior handle availability rules: normalize deterministically, enforce uniqueness transactionally in the QuickShare account namespace, and expose safe availability validation. Do not reuse a shared resource model or temporary lifecycle. Preserve QuickNotes unchanged. Use additive migrations and host-only editor cookies.

## Acceptance Criteria

- quickshare.42go.dev resolves only the new QuickShare AppConfig and protected editor surface.
- First authenticated authoring requires completed QuickShare handle onboarding.
- Normalized handle uniqueness and account ownership are enforced in PostgreSQL transactions.
- Handle changes validate normalized availability transactionally and expose enough affected-resource information for strong disruptive confirmation and atomic delivery-folder rename without redirects.
- The schema models durable typed drafts with no automatic expiry, internal resource UUIDs, publish metadata, one active public identifier per resource (random short code by default or handle/custom ID when set), immutable release versions, bundle manifests, and sidecar assets without using QuickNotes tables; explicit confirmed Delete remains supported.
- Resource lifecycle can represent draft-only, published, and unpublished-again states; Unpublish retains the authoritative draft while Delete removes the resource record only through the coordinated purge workflow.
- Resource state can represent current published-route identity separately from a pending configured identifier so UI and APIs expose `publishedUrl` and `nextPublicUrl` without claiming an unpublished candidate already works.
- Resource-type identifiers drive the editor catalog, API creation validation, and discovery response without duplicated type vocabularies.
- Template instances persist template ID, pinned template version, and validated account-owned configuration without duplicating rendered output as source of truth.
- Public identifier validation reserves any internal release/asset namespace required by the Nginx and future object-key layout.
- Cross-account and cross-app reads or writes fail closed.
- Migration, policy, and QA checks pass.

## Dos

- Use stable internal resource identity independently from mutable draft content and public path aliases.
- Keep draft revisions and publication versions traceable enough to reproduce what was released.

## Don'ts

- Do not infer ownership from handles, custom IDs, short codes, or filesystem paths.
- Do not model template output or publication files as the editable source of truth.
