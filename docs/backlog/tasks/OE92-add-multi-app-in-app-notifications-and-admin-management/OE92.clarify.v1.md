# Clarify Round v1 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. How should whitelist and blacklist membership be stored?

The recommended design is a normalized audience table with one row per
notification, user, and rule (`allow` or `deny`). This gives us foreign keys,
indexed eligibility checks, reliable audience counts, and simple enforcement of
blacklist precedence. The alternative is to keep the originally proposed JSONB
arrays directly on each notification.

### 2. What should the first poll version support?

The recommended first scope is one required selection from a fixed list of
stable option IDs and labels. Submission is final, dismisses the message, and
results are visible only to backoffice administrators. Multiple selection, free
text, public results, and changing a vote would remain out of scope.

### 3. How should edits and removal behave after users have interacted?

The recommended policy is soft archive instead of hard deletion. Content,
targeting, poll options, and agreement meaning become immutable after the first
qualified display or response; an administrator creates a replacement message
for semantic changes. Schedule-end adjustments may remain allowed. This keeps
the audit trail truthful.

## Answers

### 1.

Use a normalized audience table. Each row references one message, one user, and
an `allow` or `deny` rule. The message foreign key must use schema-level
`ON DELETE CASCADE` so permanently deleting the message removes its targeting
rows automatically. Whether `app_id` should be repeated in this and other child
tables for composite same-app foreign-key enforcement is deferred to the next
clarification round.

### 2.

The first release must let an administrator add multiple options and configure
whether the user may select exactly one option or multiple options. The
administrator must also configure whether answering is required or whether the
user may skip and dismiss the poll without selecting an option.

### 3.

Add `published_at` and `aborted_at` lifecycle fields. A message remains a
mutable draft until an administrator publishes it. Publishing sets
`published_at`; only published messages may be delivered. After publication,
the message, configuration, targeting, and poll dataset are immutable. An
administrator may abort a published message, which sets `aborted_at` and makes
it immediately unavailable regardless of its display window while preserving
all information collected so far for inspection.

Administrators may also permanently delete any message. Hard deletion removes
the message and all associated answers and other dependent notification data.

## Resolution Summary

- Audience membership uses normalized `allow`/`deny` rows with schema-level
  cascade deletion from the message.
- The first poll release supports administrator-defined options, single- or
  multiple-selection mode, and required-answer or skippable mode.
- Messages are mutable drafts until publication, immutable after publication,
  abortable with collected data retained, and permanently deletable with all
  dependent data removed.
