# Clarify Round v12 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. How should an open page discover newly published notifications?

The recommendation is browser fetch on mount, refetch on window focus/network
reconnect, refetch after every reaction, and a modest 60-second polling interval
while the component is mounted and the document is visible. Real-time push is
unnecessary for this use case. Stop polling when hidden or unmounted.

### 2. Accept this AppConfig shape?

Recommended:

```ts
app: {
  notifications?: {
    profile?: {
      show?: boolean; // default true
    };
    showHistoryLink?: boolean; // default false
  };
}
```

`api:notifications` controls whether delivery APIs exist.
`page:notifications` controls whether `/notifications` exists.
Explicit component placements remain possible when the API feature is enabled.
Do not add a third redundant `enabled` switch.

### 3. What happens when the creating administrator is deleted?

The recommendation is to preserve the communication and collected data, set
the nullable `created_by` foreign key to null through `ON DELETE SET NULL`, and
render “Deleted administrator” in backoffice history. Do not retain copied
email/name snapshots after account erasure. `created_at` remains the durable
audit timestamp.

## Answers

### 1.

Fetch once when the component mounts. These are not real-time notifications.
Do not add polling, focus/reconnect refresh, or push delivery in the first
release. Advance through the initially fetched queue locally after reactions.

### 2.

Use a simplified AppConfig shape:

```ts
app: {
  notifications?: {
    showInProfile?: boolean; // default true
    showHistoryLink?: boolean; // default false
  };
}
```

`api:notifications` controls API availability and `page:notifications`
controls the history page. Do not add a redundant `enabled` switch. This shape
may evolve later.

### 3.

Preserve the communication and collected data. Make `created_by` nullable and
use `ON DELETE SET NULL`; render “Deleted administrator” when the creator no
longer exists. Do not retain copied administrator identity fields.

## Resolution Summary

- Delivery fetches once per mount and advances through local state.
- AppConfig uses `showInProfile` and `showHistoryLink` without a redundant
  enablement flag.
- Creator deletion sets `created_by` to null and preserves the communication.
