# Add Multi-App In-App Notifications and Admin Management

## Elevator's Pitch

Build a reusable 42Go in-app notification system that lets backoffice administrators create, schedule, target, edit, inspect, and remove app-scoped messages. Logged-in users see eligible messages through a client-only shared component that can be inserted into any authenticated application page and records qualified displays plus the user's required response.

## Business Gain

- Give every app a consistent way to communicate announcements, warnings, agreements, and polls without building app-specific message systems.
- Let administrators target and schedule communication while retaining an auditable record of exposure and user action.
- Provide a reusable component that app owners can place where it is most useful while keeping a configurable default on the profile page.

## Current State

- The repository has multi-app resolution, app-scoped users, AppConfig-driven authenticated profile blocks, RBAC/policy enforcement, and client-only authenticated pages.
- There is no shared database-backed in-app notification model, backoffice message-management UI, reusable notification container, targeting engine, or per-user exposure/response history.
- Fourteen clarification rounds have resolved the interaction, lifecycle, audience, history, security, route, configuration, and first-release scope decisions captured below.

## Desired State

- Create an extensible app-to-user communication capability under the shared `src/42go` platform layer. The first delivery surface is an in-app notification/message, but the model must not assume that every future communication is rendered in-app. Every communication belongs to one `app_id`, and only users authenticated in that app can receive or act on its in-app form.
- Separate delivery channel from interaction kind so one overloaded `type` field does not confuse concepts. The model uses `communication` as the root domain, a delivery `channel` such as `in_app` or `email`, and an in-app `interaction` such as notice/acknowledgement, agreement, poll, or open input. Presentation style and ordering priority remain independent.
- Notifications select a hardcoded reaction template from the backoffice. Initial templates are acknowledgement (`OK`), confirmation (`I accept`/`I reject`), hard confirmation (`I accept` only), agreement (`Agree`/`Disagree`), hard agreement (`Agree` only), and binary question (`Yes`/`No`). The template defines the semantic meaning, button labels, and permitted reaction strings. A successful reaction dismisses the message. Store the exact presented-and-clicked reaction verb as a string and enforce its validity against the selected template in backend logic rather than creating database tables for reaction definitions.
- For polls, the administrator can define multiple stable options, choose single- or multiple-selection mode, and decide whether the entire poll is required or skippable. Polls independently support a short `Other` input, which acts as an alternative to preset choices, and an optional long notes textarea for supplemental commentary. Short input is limited to 500 characters and textarea to 5,000. In mandatory single-choice mode, exactly one preset option or `Other` is allowed. In mandatory multiple-choice mode, at least one preset option or `Other` is required and `Other` may accompany preset selections. Notes are always optional, never satisfy the mandatory answer, and appear through a compact secondary affordance when enabled. Open Input communications collect standalone typed feedback through a short input or textarea with the same limits.
- Use a presentation-only `style` field with `info`, `warning`, `danger`, and `success` icon/color treatments following the classic contextual-message UI convention. Style never affects ordering.
- Add a separate numeric priority used only for in-app ordering. The backoffice presents Low (`0`), Normal (`5`, default), and High (`10`) through a compact segmented selector. Email ignores priority. Eligible in-app communications sort by priority descending and then `published_at` descending, so the newest item wins within the same priority.
- Store a title and Markdown body, with neither necessarily forcing the other when a valid communication can be title-only or body-only. Render Markdown through the platform's sanitized Markdown pipeline.
- Apply initial content limits: title 160 characters, email subject 200, Markdown body 20,000, poll option label 200, short input 500, and textarea/notes 5,000. Use a strict Markdown allowlist with no raw HTML.
- Support an optional link URL on an in-app communication. The rendered link opens in a new tab with safe opener isolation. This supports short announcements that point to a larger article or newly released content. Require HTTPS outside local development.
- Support optional URL-addressed media with an explicit media type, initially image or video. Administrators provide an HTTPS asset URL outside local development; direct asset upload and asset-repository management remain future work.
- Store creator, creation time, optional `available_from`, optional `available_until`, `published_at`, and `aborted_at`. `published_at` is the irreversible, channel-neutral go-live transition; the availability fields define the channel-neutral eligibility window.
- Store `created_by` as a nullable user reference with `ON DELETE SET NULL`. Deleting the administrator preserves the communication and collected data; backoffice UI renders “Deleted administrator” and does not retain copied identity fields.
- Messages remain mutable drafts and are never delivered until an administrator explicitly publishes them. Publication sets `published_at` and permanently locks the message content, kind, style, priority, targeting, availability window, poll options, and poll rules. A published message can be aborted; setting `aborted_at` immediately removes it from user delivery regardless of its availability window while retaining the message and all information collected so far for backoffice inspection.
- The administrator chooses an immutable authoring kind when creating a draft. The `+ New` control opens a compact menu with Notification, Poll, Input, and Email. This initial intention selects the relevant editor and derived channel/interaction values; it cannot be changed later, even while the record is still a draft.
- Each communication selects exactly one audience mode: `everyone`, `whitelist`, or `blacklist`. The backoffice labels these `Everyone in this app`, `Only selected users`, and `Hide from specific users`. Everyone is the default. Whitelist delivers only to selected users; blacklist delivers to every app user except selected users. Modes cannot be combined.
- Proposed data architecture: the root table owns communication content, channel/interaction configuration, style, app, schedule, creator, lifecycle metadata, and `audience_mode`. A per-message/per-user state table stores `first_displayed_at`, final reaction, validated response payload, and acknowledgement/submission time. A separate append-only display-event table stores every qualified exposure timestamp. This normalized event model is preferred over appending display timestamps to a JSONB array because it avoids hot-row updates and supports indexing, audit queries, later exports, and message-centric or user-centric history.
- Store selected audience users in a normalized audience table rather than JSONB arrays. Each row references one app, communication, and user; the root `audience_mode` gives those membership rows their whitelist or blacklist meaning, so no per-row allow/deny field is needed. A uniqueness constraint prevents duplicate membership for the same message/user. Audience and user-state rows repeat `app_id` and use composite foreign keys so PostgreSQL rejects cross-app message/user relationships. The message foreign key uses `ON DELETE CASCADE`, so permanent message deletion removes all audience, state, display, and response data at schema level.
- The mobile-friendly backoffice audience picker filters current-app users by name, username, or email and shows selected people as removable user entries. Technical storage vocabulary does not leak into the operator labels.
- Expose backoffice-only client pages and protected APIs for listing, creating, reading, updating, publishing, aborting, and permanently deleting messages. Both frontend policy and every mutating/read API must require the `backoffice` role and resolve the current app safely; client checks are never the security boundary. Permanent deletion removes the message and all associated audience, display, response, and answer data.
- Follow the repository's separation between feature availability and privileged grants. User self-service reads rely on feature, session ownership, and app scope rather than a `notifications:view` grant. Backoffice surfaces additionally require the `backoffice` role and exact notification-management grants.
- Introduce `/backoffice` as the top-level authenticated management namespace. Place notification management at `/backoffice/notifications` and its APIs at `/api/backoffice/notifications`. User surfaces remain `/notifications` and `/api/notifications`. All four surfaces explicitly use `page:notifications` or `api:notifications` as appropriate; the namespace never replaces page/API policy enforcement.
- Use `page:notifications` and `api:notifications` as the availability features for all notification surfaces. Add exact app-scoped grants `notifications:list`, `notifications:create`, `notifications:edit`, `notifications:publish`, and `notifications:delete`, and assign all five to the backoffice role by default. The management page requires list; each action and API requires its corresponding grant. Publishing and aborting both require `notifications:publish`.
- Document the communication domain, AppConfig behavior, user/backoffice routes, APIs, feature flags, grants, lifecycle, targeting, reaction templates, poll validation, display tracking, and extension points. Document `/backoffice` as the namespace for future management surfaces.
- The admin list is ordered newest first. Each row shows the message-type icon; active, scheduled, or expired state; public or restricted audience state; a status-aware date; and a two-line title/text summary with bold title. Show `created_at` for drafts, `published_at` for published records, and the availability range when scheduled or bounded. Keep the paginated list query limited to root communication data and simple status/audience classification; do not aggregate audience, display, or response counts for every row.
- A `+ New` action appears at the right side of the admin top bar and opens the kind-selection menu. The entire backoffice authoring and inspection experience is responsive and deliberately usable from a phone. Each kind presents only relevant fields. Selecting a row opens a details panel where the administrator can edit a draft and inspect users who qualified as having displayed a published message and users who operated on it, including their timestamps and response values. That details request lazy-loads the current eligible-audience, qualified-viewer, and final-response/skip counts for the selected communication only.
- Permanent deletion uses the shared destructive modal. If no user display/response data exists, a normal confirmation is sufficient. If dependent user data exists, the modal shows the counts and requires typing the exact communication title before the API permits cascade deletion.
- Expose a minimalist, elegant, visible client-only 42Go notification container. It fetches in the browser with same-origin credentials, renders one eligible unacknowledged message at a time, shows `1 of N`, updates the counter locally as messages are handled, and animates removal/collapse or transition to the next message. It returns `null` when there is nothing to display.
- Fetch the eligible queue once when the component mounts. Do not poll, refetch on focus/reconnect, or implement push delivery in the first release. Advance through the fetched queue locally as reactions succeed; newly published communications appear on a later mount/reload.
- Make the container available for explicit placement on any app-specific authenticated page. Render it at the top of the profile page by default, with an AppConfig switch to disable that default. LingoCafe should place it at the top of the books list. QuickList should place it at the top of the project list and at the top of each list page.
- Extend AppConfig with global in-app communication behavior. It controls default profile placement and whether the notification component offers a link to the notification-history route.
- Use `app.notifications.showInProfile?: boolean` with default `true` and `app.notifications.showHistoryLink?: boolean` with default `false`. Do not add a redundant `enabled` switch: `api:notifications` controls API availability and `page:notifications` controls the history page.
- Implement a client-only authenticated `/notifications` page under `src/app/(app)/notifications/` and protect it with an explicit page feature flag in AppConfig. The component shows its history link only when both the link toggle is enabled and the page feature flag is present. If link configuration and the feature flag disagree, fail safely by omitting the link.
- The notifications page shows current active communications and a separate history section. Collapse history by default while active items need attention; open it by default when no active items remain. Fetch history from a server-paginated API ten records at a time and append subsequent pages through a `Load more` control. Hide aborted and deleted communications. After expiration, include a communication only when the user gave a final reaction or response; a qualified display alone is insufficient.
- The user history has no search, numbered pagination, or infinite scrolling. Server queries derive the authenticated user and current app, return only that user's eligible/history records in the agreed order, and provide ten records per `Load more` request.
- A display event is written at most once per component mount/route visit after at least 50% of the message has remained continuously visible in the viewport for 10 seconds while the document is visible. Leaving the viewport, hiding the tab, changing route, or advancing to another communication resets the timer. Ordinary React rerenders do not create another event. Acknowledgement or response is stored when the required action succeeds.
- Index the model for both directions: all users exposed/responding to one message and all messages exposed/responded to by one user. This supports current backoffice analysis queries, later export work, future notification history inside the admin user panel, and the authenticated `/notifications` page where users review what they saw and how they responded.
- Do not implement an export UI or endpoint in the first release. Preserve normalized data and indexes so a later task can add the format and scope proven useful by real operation.
- Every user-facing communication API requires an authenticated session and derives/enforces the current app on the server. Placement under an `(app)` route group does not replace API authorization.
- Support authoring and publishing email communications in the first release. The initial email editor contains a required plain-text subject and Markdown body plus the same mutually exclusive normalized audience targeting and lifecycle fields. Email has no interaction configuration; links, questions, or options can be written directly in its Markdown body. Published email records are queryable for a future external consumer but are not returned to the in-app component, and nothing sends or consumes them in this task. The model should remain extensible for later template selection, template-specific validated data, external pickup, and delivery reporting.

## Definition of Success

- A backoffice administrator can manage app-scoped messages and inspect their audience, qualified displays, and responses.
- Eligible authenticated users see only current, correctly targeted messages and can complete the interaction required by each supported type.
- The shared component is reusable across apps, defaults safely on the profile page, supports app-specific placement, performs no authenticated page SSR, and disappears completely when empty.
- The database history is queryable and auditable without storing an ever-growing display timestamp array on one row.
- The content and response model can add future channels and interaction schemas without renaming or overloading existing semantics.

## Additional Context

- `auth.users` is already app-scoped through `app_id`, so audience eligibility and audience counts can be computed against users in the notification's app.
- The existing authenticated page convention requires `"use client"`, `AppLayout`, and browser-side fetching with `credentials: "same-origin"`.
- The existing AppConfig profile system under `app.profile.items` is relevant to the default profile placement, but notification placement should remain a generic component contract rather than a profile-only block.
- The details panel should use the repository's shared Modal abstraction if it is implemented as a dialog, drawer, sheet, side panel, or overlay.
- Date and schedule comparisons should use server-authoritative timestamps and PostgreSQL `timestamptz`; the browser may format dates in the user's locale.
- Reuse the existing shared `src/42go/components/DisplayDate` for relative dates with full timestamp disclosure on hover/touch. It currently exists in duplicate file/folder implementations and mishandles future timestamps; implementation should consolidate one canonical accessible component and add correct past/future relative formatting rather than introduce a third date component.
- Related prior work: FH48 established the configurable authenticated profile-page pattern.
- The feature-flagged user notification-history page is required in this task. Future admin user-grid integration is an architectural consumer of the same indexes but remains out of scope.
- Moving existing user administration into `/backoffice` and correcting `users:edit` authorization are tracked as separate follow-up tasks and must not be folded into OE92 implementation.

## Assumptions

- A notification is app-scoped and an administrator manages notifications only within an app context they are authorized to administer.
- Only authenticated users are eligible; anonymous delivery is out of scope.
- An acknowledged, answered, or explicitly skipped message is no longer returned to that user.
- Audience modes are mutually exclusive; one communication never has both whitelist and blacklist semantics.
- Display windows are inclusive at the start and exclusive at the end unless refinement chooses different boundary semantics.
- Creating and editing draft messages needs an `updated_at` field even though it was not in the initial field list.
- The initial implementation can fetch a finite ordered set of eligible messages rather than requiring real-time push delivery.
- Remote media uses administrator-supplied URLs in the first release; uploading and managing assets is out of scope.
- Communication kind is immutable from the moment the draft is created; other draft fields remain editable until publication.
- Priority is null/ignored for email and defaults to Normal (`5`) for in-app kinds.

## Constraints

- All supporting tables must live in the `42go_data` PostgreSQL schema.
- All notification and administration views must be client components. Do not server-render notification/admin data or call internal APIs during server rendering.
- Use protected server APIs with server-side input validation, app scoping, session checks, and `backoffice` role enforcement.
- Never trust `app_id`, `created_by`, user ids, reaction string, poll option, schedule status, or audience membership supplied by the browser without server-side resolution and validation.
- Strictly sanitize rendered Markdown with no raw HTML and validate content limits, link/media URL schemes, media types, and response payloads on the server. Require HTTPS except for explicitly allowed local-development URLs.
- A missing feature should follow the platform's policy semantics, and unauthorized administration must fail closed.
- `audience_mode` is required and defaults to `everyone`; whitelist and blacklist modes require validated current-app membership rows.
- Draft and aborted messages must never be returned by user-delivery APIs. Published message fields are immutable; only the abort and permanent-delete lifecycle actions remain available.
- The reusable UI belongs under `src/42go`; app-specific route placement belongs in each app area/configuration.
- Use the shared 42Go Modal component for the admin details panel if the chosen interaction is an overlay.
- Use absolute `@/` imports, Knex parameterized queries, accessible controls, and the existing design system.
- Run `npm run qa` after implementation.

## Dos

- Keep schedule and audience filtering in server-side query/service code shared by all delivery endpoints.
- Use server-derived current app and administrator identity when creating or mutating records.
- Prefer normalized append-only display events and a constrained per-user response record.
- Enforce dependent-data deletion through database foreign keys with `ON DELETE CASCADE`, not application cleanup alone.
- Define a typed, documented AppConfig contract for default profile visibility.
- Treat audience counts as security-sensitive aggregates and scope every count by app.
- Design and index the read model for both message-centric and user-centric history.
- Keep the visual treatment consistent across light/dark themes and keyboard/screen-reader accessible.

## Don'ts

- Do not make this a LingoCafe-only or QuickList-only feature.
- Do not rely on client-side role checks, app ids, clocks, or targeting filters for security.
- Do not SSR the authenticated notification or admin views.
- Do not store repeated display timestamps as one mutable JSONB array without an explicit refined decision overturning the normalized event recommendation.
- Do not let a poll submit an arbitrary option or payload that is absent from the server-stored definition.
- Do not count excluded blacklist members, non-whitelisted users, cross-app users, or otherwise ineligible users in audience details.
- Do not create bespoke fixed overlays for the admin details panel.
- Do not implement direct media upload or an email-sending engine in this task.
- Do not implement communication export UI/endpoints in the first release.
