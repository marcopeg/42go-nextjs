# Clarify Round v4 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Which action modes should a Notification offer?

The latest direction mentions acknowledgement, confirmation, and
accept/reject-style decisions. The recommended storage model uses two action
shapes: `acknowledge` with one button, and `decision` with stable
`positive`/`negative` results. The backoffice can select semantic label presets
such as Agree/Disagree, Accept/Reject, or Yes/No without creating different
database action types for synonymous button text.

### 2. What is the initial email body contract?

The recommended first contract is a required plain-text subject and a Markdown
body, using the same sanitized authoring format as in-app content. The future
consumer can derive plain text and HTML. Link/media/interaction fields remain
in-app-only for now, while normalized audience and lifecycle fields are shared.

### 3. Should channel-neutral schedule names replace display-specific names?

Now that email records exist, `display_at` and `display_until` are too tied to
the in-app channel. The recommendation is `available_from` and
`available_until`: for in-app messages they control display eligibility; for a
future email consumer they control pickup eligibility. Published email records
need no sent/delivery status in this task because nothing consumes them yet.

## Answers

### 1.

Use a hardcoded reaction-template registry exposed as a dropdown in the
backoffice Notification editor. Initial templates include a simple
acknowledgement that renders `OK`, a confirmation template that renders
`I accept`, and an agreement template that renders `Agree` and `Disagree`.
The selected template carries the semantic meaning and defines the permitted
reaction strings. Store the user's reaction as a string and validate it against
the selected template in backend logic. Do not create database tables for
reaction definitions or possible values.

### 2.

Use a required plain-text email subject and Markdown body. Email has no user
interaction fields. Links, questions, or options can be authored directly in
the Markdown body. Audience targeting and lifecycle are shared with the other
communication kinds.

### 3.

Rename the schedule fields to `available_from` and `available_until`.
Keep `published_at` as the channel-neutral, irreversible go-live timestamp.
Publication and availability serve different purposes: a record must be
published and inside its availability window to be eligible for its channel.

## Resolution Summary

- Notifications select a hardcoded reaction template; permitted reaction
  strings are enforced by the API and stored directly with the user state.
- Email initially uses a plain-text subject and Markdown body with no
  interaction configuration.
- `published_at` is the go-live transition; `available_from` and
  `available_until` define the channel-neutral eligibility window.
