# Clarify Round v13 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Accept this audience-picker and history pagination contract?

Use server-side search scoped to the current app across username, name, and
email. Return 20 users per search page. The mobile-first editor adds selected
users as compact Allow or Deny chips and prevents duplicate/conflicting rules.
In notification details, display user name/username, email, and stable user ID;
paginate qualified viewers and responses 25 rows at a time with `Load more`.

### 2. What export belongs in the first release?

The data model and indexes make analysis possible, but “exportable” needs a
concrete operator surface. The recommendation is a backoffice-only JSON export
for one communication containing immutable communication/configuration data,
audience rules, full display events, and responses. JSON preserves nested poll,
input, and timestamp data without flattening it badly. CSV/Parquet and bulk
cross-communication exports can follow through the 42go CLI.

## Answers

### 1.

The user `/notifications` page has no search. It returns only current-app
communications visible to the authenticated user, in the agreed order, ten at
a time through an explicit `Load more` button. Do not use infinite scrolling or
numbered pagination.

The original question accidentally mixed this user history with the separate
backoffice audience-targeting editor. Round v14 resolved the admin editor with
mutually exclusive Everyone, Only selected users, and Hide from specific users
modes plus current-app identity filtering.

### 2.

Do not implement an export feature in the first release. Keep the normalized,
indexed data suitable for later analysis and add an operator export only after
real usage clarifies the required format and scope.

## Resolution Summary

- User history has no search and uses ordered ten-at-a-time `Load more`;
  round v14 completed the backoffice audience-selection UX.
- No first-release export surface is required.
