# Clarify Round v9 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Accept these routes and feature boundaries?

Recommended user surface: `/notifications`, `page:notifications`, and
session/app-scoped APIs under `/api/communications`. Recommended backoffice
surface: `/backoffice/communications`, `page:backoffice-communications`, and
APIs under `/api/backoffice/communications` requiring both session and the
`backoffice` role. API feature names can mirror the two surfaces as
`api:communications` and `api:backoffice-communications`.

### 2. Accept these initial content limits and Markdown policy?

Recommended limits: title 160 characters, email subject 200, Markdown body
20,000, poll option label 200, short input 500, and textarea/notes 5,000.
Allow the existing sanitized Markdown subset with headings, emphasis, lists,
links, and code, but no raw HTML. Link and media URLs must use `https`, with
`http` allowed only for local development.

### 3. How should permanent deletion be confirmed?

Because deletion intentionally cascades through audience, display, and response
data, the recommendation is a destructive confirmation modal showing the exact
dependent-record counts. For a published communication with any collected
data, require typing the communication title; for an untouched draft, a normal
confirm button is enough.

## Answers

### 1.

Repository inspection found one feature system and one privilege system:

- App availability uses exact `page:*` and `api:*` feature flags.
- Privileged operations use exact grants. Existing notification-relevant
  precedent is the backoffice-only `/users` page with `page:users`,
  `api:users`, role `backoffice`, and `users:list`/`users:edit`/
  `users:delete` grants.
- There is no existing `/admin` or `/backoffice` URL prefix convention.

The operator prefers the `notifications` noun for page and API coherence.
Round v10 resolved the exact grants and round v11 resolved the backoffice route
namespace.

### 2.

Accepted. Initial limits are title 160 characters, email subject 200, Markdown
body 20,000, poll option label 200, short input 500, and textarea/notes 5,000.
Use strict sanitized Markdown with no raw HTML. Links and media require HTTPS
outside local development.

### 3.

Accepted with collected data as the threshold. An untouched draft or any
communication without dependent user data uses a normal destructive
confirmation. Deleting an active, expired, or otherwise published
communication that has collected display/response data requires a strong modal
showing dependent counts and typing the exact title before deletion.

## Resolution Summary

- Repository conventions, notification features/grants, and route namespaces
  were completed in rounds v10-v11.
- Content limits and strict no-HTML Markdown policy are resolved.
- Deletion uses ordinary confirmation without collected data and title-typing
  confirmation when collected user data will cascade.
