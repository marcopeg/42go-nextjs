# Clarify Round v5 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. How should required/skippable behavior apply to typed answers?

The recommended rules are: standalone Input explicitly chooses required or
skippable; a Poll independently chooses whether a choice response is required
and whether its configured free-answer field is optional or required. Skip is
shown only when the entire communication is skippable. Suggested initial limits
are 500 characters for short input and 5,000 for textarea.

### 2. What exactly qualifies as one display-history event?

The recommended rule is one event per component mount/route visit after at
least 50% of the notification has remained continuously in the viewport for
10 seconds while the document is visible. Leaving the viewport, hiding the tab,
changing route, or changing to the next message resets the timer. Normal React
rerenders do not create another event.

### 3. How should ordering and the admin audience number work?

The recommended user order is severity rank (`danger`, `warning`, `info`,
`success`), then `available_from`, then `published_at`, oldest eligible first
within each rank. The admin list should show separate counts for currently
eligible audience, qualified viewers, and completed/skipped responses rather
than compressing three different meanings into one number.

## Answers

### 1.

Use 500 characters for short input and 5,000 for textarea. Polls may be
skippable. For a non-skippable poll, validation must account for configured
free-text response paths rather than blindly requiring a preset choice.

Treat short input and textarea as independent poll features. The short input is
an `Other`-style alternative to preset choices. The textarea is supplemental
notes. The exact rule for when each satisfies or is required by a mandatory
poll is deferred to the next round.

### 2.

Resolved in round v6: one event per mount/route visit after 50% continuous
visibility for 10 seconds in a visible document, with interruptions resetting
the timer and rerenders not duplicating events.

### 3.

Severity is presentation only and must not control ordering. Add a dedicated
numeric in-app priority with a three-choice segmented UI: Low stores `0`,
Normal stores `5` and is the default, and High stores `10`. Email does not use
priority. User delivery sorts by priority descending and then `published_at`
descending, so newer communications appear before older ones at equal priority.
Admin count semantics were resolved in round v8: load targeted aggregates only
for the selected details panel, not for every list row.

## Resolution Summary

- Typed-answer limits and the distinction between an `Other` short input and
  notes textarea are resolved; their exact mandatory-poll validation remains
  pending.
- Qualified display-event semantics were completed in round v6.
- User ordering uses dedicated priority and newest-first publication; admin
  count semantics were completed in round v8.
