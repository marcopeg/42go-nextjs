# Clarify Round v10 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Accept this notification route and feature layout?

Recommended user page: `/notifications` with `page:notifications`.
Recommended management page: `/notifications/manage` with the explicit
`page:notifications-manage` feature. Both live under `(app)`.

Use `/api/notifications` for user delivery/history/reactions and
`/api/notifications/manage` for backoffice CRUD/publish/abort/delete. All share
the `api:notifications` availability feature, while management handlers add
role/grant checks. This keeps one coherent noun and avoids inventing a global
backoffice URL convention for one feature.

### 2. How granular should notification-management grants be?

The recommendation is:

- `notifications:list` — list/read details and aggregates
- `notifications:create` — create drafts
- `notifications:edit` — edit drafts
- `notifications:publish` — publish or abort
- `notifications:delete` — permanent cascade deletion

The management page requires `notifications:list`; each action and API requires
its exact grant. The default backoffice role can receive all five.

### 3. Which dates should the lean admin list show?

The recommendation is a compact status-aware date line: `created_at` for
drafts; `published_at` for published records; and the availability range when
scheduled or bounded. Put `updated_at`, `aborted_at`, and all exact timestamps
in the details panel. Format in the browser's locale/timezone while API values
remain ISO timestamps.

## Answers

### 1.

Use `page:notifications` and `api:notifications` as the feature flags for both
user and backoffice notification surfaces. The user routes remain
`/notifications` and `/api/notifications`. Round v11 selected `/backoffice`
and `/api/backoffice` as the management namespaces.

### 2.

Accepted. Add `notifications:list`, `notifications:create`,
`notifications:edit`, `notifications:publish`, and
`notifications:delete`. Assign all five to the app-scoped backoffice role by
default. The management page requires list access; every action and API checks
its exact grant.

### 3.

Accepted. The lean list uses a status-aware date: `created_at` for drafts,
`published_at` for published records, and the availability range when
scheduled/bounded. Full lifecycle timestamps belong in details and render in
the browser locale/timezone.

Reuse the existing shared `DisplayDate` component rather than creating another
date component. It already provides relative display and full details on hover
or touch, but implementation planning must account for its duplicate source
files and its lack of correct future-date formatting. Consolidate it to one
canonical implementation and extend it for accessible past/future relative
dates plus full timestamp disclosure.

## Resolution Summary

- User routes, notification features, and the `/backoffice` namespace are
  resolved.
- Five exact notification-management grants are resolved and assigned to the
  app-scoped backoffice role.
- Admin date presentation reuses and upgrades the existing shared
  `DisplayDate` component.
