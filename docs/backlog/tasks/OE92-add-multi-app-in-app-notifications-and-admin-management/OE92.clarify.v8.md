# Clarify Round v8 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Which public URL should the authenticated page use?

In this repository, `src/app/(app)/notifications/page.tsx` produces
`/notifications`, because parentheses define an invisible route group.
Producing `/app/notifications` requires a real `app` route segment. The
recommendation is `/notifications`, consistent with the existing authenticated
routes such as `/profile` and `/books`.

### 2. Which records belong in a user's history?

The recommended rule is user-specific history only: include communications for
which the user has a qualified display or final reaction/response. Include
expired or aborted communications if the user previously saw or answered them.
Exclude communications deleted by an administrator and communications the user
never qualified as seeing. Current eligible/unanswered items belong in the
active section instead.

### 3. Which counts should an admin list row show?

The recommendation is three compact counts: current eligible audience,
qualified viewers, and final responses/skips. One ambiguous “users” number
cannot truthfully represent targeting, exposure, and completion at the same
time.

## Answers

### 1.

Use the public URL `/notifications` implemented under
`src/app/(app)/notifications/` so it participates in the repository's
authenticated app organization and `AppLayout` convention. Every user-facing
API must independently require an authenticated session and enforce app scope;
filesystem route groups are organization, not an API security boundary.

### 2.

The active section contains current eligible communications. User history
excludes aborted and deleted communications. A non-expired communication may
remain represented after qualified viewing, acknowledgement, or response as
appropriate to the active/history split. Once expired, it appears in history
only if the user gave a final reaction or response; a qualified display without
interaction is insufficient. Aborted records remain inspectable by backoffice
but are hidden from user history.

### 3.

Do not calculate aggregate counts for every admin list row. Keep the paginated
list query and mobile payload lean with root communication data and simple
status/audience classification. When an administrator opens one details panel,
lazy-load current eligible audience, qualified viewers, and final
responses/skips for that communication using targeted indexed aggregates.

## Resolution Summary

- Use `/notifications` under the authenticated `(app)` route group; APIs also
  enforce session and app scope explicitly.
- User history excludes aborted/deleted records and includes expired records
  only after a final reaction or response.
- Aggregate audience/view/response counts are loaded only in one communication's
  details panel, not across the admin list.
