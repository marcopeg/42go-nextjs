# Clarify Round v2 — Add Multi-App In-App Notifications and Admin Management

## Questions

### 1. Should child tables repeat `app_id` to enforce same-app relationships?

Message IDs are globally unique, so `notification_id` alone is sufficient to
identify and cascade-delete a message. The reason to repeat `app_id` is
different: composite foreign keys can then make PostgreSQL reject an audience
or reaction row that links a notification from app A to a user from app B.
Without repeated `app_id`, both foreign keys can be individually valid while
the cross-app relationship is wrong, and only application code can prevent it.

The recommendation is to repeat `app_id` in audience and user-state tables and
use composite same-app foreign keys. It is controlled relational redundancy,
not a second source of truth.

### 2. Should user summary and display history use two related tables?

The recommended model is one `notification_user_state` row per message/user
with `first_displayed_at`, final action/answer, and `acknowledged_at`, plus an
append-only `notification_display_events` table with one row and timestamp per
qualified display. A transaction inserts each display event and fills
`first_displayed_at` only when it is still null.

This keeps the commonly needed first-display and final-response data together
without storing an expanding timestamp list in JSONB.

### 3. Which final-action fields should the user-state row contain?

The recommended fields are `action` (`ok`, `agree`, `disagree`,
`poll_submit`, or `poll_skip`), nullable `answer` JSONB for validated poll
option IDs, and `acknowledged_at`. The unique message/user row makes the final
action immutable and idempotent.

## Answers

### 1.

Repeat `app_id` in the audience and user-state tables. Use it in composite
foreign keys so PostgreSQL enforces that the message and user belong to the
same app. The redundancy is accepted as an additional tenant-safety boundary.

### 2.

Use a per-message/per-user summary row plus normalized append-only display
events. The summary keeps the first qualified display and final response; the
event table keeps every qualified display timestamp. Index both directions so
the backoffice can inspect a message's users and a future user panel can inspect
everything one user has seen and answered.

### 3.

The response model must now cover acknowledgements, agreement choices, poll
selections, poll skips, and a new open-input interaction. Keep a stable action
and timestamp in indexed columns while allowing a validated response payload
for type-specific data. The exact interaction/configuration vocabulary is
deferred to the next round.

## Resolution Summary

- Audience and user-state rows repeat `app_id` for composite same-app foreign
  keys and stronger tenant isolation.
- One user-state summary plus append-only display events supports first-display,
  full-history, message-centric, and user-centric queries.
- Reactions need stable indexed action/timestamp columns plus an extensible,
  server-validated response payload.
