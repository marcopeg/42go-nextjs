# Fix Reader Sentence Segmentation Skipping Sentence-Ending Full Stops

## Elevator's Pitch

Fix the LingoCafe reader's sentence segmentation so every ordinary sentence-ending full stop is evaluated and two adjacent sentences render as separate translation targets. The current bug can make a tap select both sentences, after which the translation API correctly rejects the combined text under its one-sentence safeguard.

## Business Gain

Readers can translate the sentence they tapped instead of being blocked by a validation error caused by the reader itself. Chuck Norris does not ask an API to translate two sentences disguised as one.

## Current State

The reader splits clickable sentence targets in `src/app/(app)/(lingocafe)/books/_components/BookPageReader.tsx` through `splitSentenceSegments()`. The translation API independently validates that submitted text has no full stop in the middle in `src/app/api/(lingocafe)/lingocafe/translate/route.ts`. Its current raw period-count check also rejects a single sentence that contains an abbreviation, such as `Dr. Watson arrived.`.

The defect was introduced with the playback-oriented splitter in commit `4a2dfe5`. When it detects the first character of a word, it advances `cursor` through the word and the loop increment then moves it past the immediately following punctuation. That skips standard full stops after normal words, so no boundary is emitted.

The seeded Chapter 20 content demonstrates the defect exactly: `Han hade ändrat åsikt om min vän. Förut var han avundsjuk, men nu hade han stor respekt.` is rendered as one target. Tapping it submits two full stops to the API, which correctly returns `Text must be one sentence with no full stops in the middle.`.

## Desired State

The reader must create a distinct clickable target for each real sentence boundary, including ordinary periods directly after a word. In the reported Chapter 20 example, the target ending `min vän.` and the target beginning `Förut var han...` must be separate, so each can be translated successfully on its own.

The correction must use one shared language-independent sentence-boundary utility for the reader and server-side validator where runtime-compatible. It must not rely on a fixed, English-only abbreviation list to determine whether a period ends a sentence. If a shared utility cannot run in both places, equivalent behavior must be proven with shared fixtures. A single sentence containing an abbreviation must remain one valid translation target and must be accepted by the API. The implementation must preserve intended handling of initials, decimal numbers, closing quotation/parenthesis characters, and non-Latin sentence terminators. The reader's sentence catalog and playback highlighting must remain aligned with the rendered translation targets.

## Definition of Success

A reader can tap either sentence in the reported Chapter 20 example and receive a translation without the one-sentence validation error. A sentence with an abbreviation is also accepted as one sentence. Sentence wrapping, playback catalog entries, and API validation agree on the same language-independent boundaries.

## Additional Context

The fault is in client-side sentence tokenization, not in API validation. The API's rejection is a safeguard working as intended.

There are currently no focused automated tests for `splitSentenceSegments()` or the API's formal sentence validation. Planning should choose a testable extraction or equivalent coverage that locks down the exact regression and boundary edge cases.

The operator requires language-independent sentence detection. They will perform the manual mobile-reader verification after implementation is handed off; the implementation validation must therefore include focused automated regression coverage and `npm run qa`.

## Assumptions

- The API must remain strict and must not be weakened to accept multi-sentence requests as a workaround.
- The reader should keep one translation request per sentence.
- Existing playback behavior depends on the rendered `data-reader-sentence-id` catalog and must stay synchronized.
- The operator will perform the manual mobile-reader smoke test after implementation hand-off.
- The shared boundary utility is used by both client and server where their runtimes support it; shared fixtures are the required fallback proof of equivalence.

## Constraints

- Do not relax or bypass the translation API's one-sentence validation.
- Do not change book content to work around the tokenizer.
- Use language-independent sentence-boundary behavior; do not base correctness on a fixed English-only abbreviation list.
- Use the same boundary behavior in the reader and translation API; do not retain raw period-count validation that rejects a one-sentence abbreviation.
- Preserve abbreviation, decimal-number, closing-quote/parenthesis, and Unicode terminator behavior.
- Preserve stable sentence catalog ordering and reader playback integration.
- Add regression coverage before considering the defect fixed.

## Dos

- Do isolate sentence-boundary logic into a testable unit if that is the smallest clean path.
- Do treat the reported Swedish Chapter 20 string as a permanent regression case.
- Do preserve API validation as a separate server-side safety boundary.
- Do use the manual mobile-reader smoke test as hand-off verification, not as a substitute for automated regression coverage.
- Do keep one-sentence enforcement based on detected sentence boundaries, not a raw count of periods.

## Don'ts

- Don't paper over the problem by accepting multiple sentences in the API.
- Don't make one sentence wrapper span a full paragraph.
- Don't silently remove punctuation from the text sent to translation.
- Don't regress reader playback, sentence highlighting, or translation caching.
- Don't solve language independence by growing an unbounded, language-specific abbreviation list.
- Don't accept arbitrary multi-sentence text merely because it contains an abbreviation.
