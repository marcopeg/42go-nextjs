# PickNote: Repair List Refresh and Add Conditional Auto-Refresh

## Elevator's Pitch

Repair manual refresh on both the PickNote lists overview and an open list, then add one account-wide auto-refresh control with Off, Slow, Medium, and Fast levels. Auto-refresh applies to every list but runs only while an individual list is open. Polling should use a lightweight change token so unchanged lists do not repeatedly transfer the full payload.

## Business Gain

- Shared lists reflect collaborators' changes without requiring navigation away from the list.
- Users control the trade-off between immediacy and request frequency for each list.
- Conditional responses minimize bandwidth, payload parsing, and unnecessary React rendering during polling.

## Current State

- The open-list refresh action at `/quicklists/[id]` invalidates the React Query project key, but `useQuicklistData` can continue rendering its separate non-null local `tasksState` and `listTitleState`; fresh query data may therefore arrive without becoming visible.
- `GET /api/quicklists/[projectId]` already calculates a project `freshness` value from existing project/task timestamps, but the current response does not expose a change token and does not honor conditional requests.
- Archived tasks ACC and AAY describe an earlier ETag/Last-Modified conditional-fetch contract and frontend polling design, but that behavior is absent from the current route and client hook.
- The lists overview has a manual refresh action, but its behavior must be verified and repaired alongside the detail-page refresh.
- There is no account-wide list auto-refresh preference today.

## Desired State

- Manual refresh reliably fetches and displays the latest authoritative data on both the lists overview and an individual list, including after local list/task mutations.
- Explicit manual refresh always bypasses the conditional change token and requests a full authoritative payload. Conditional requests are reserved for scheduled polling.
- The account has one personal tab-style segmented control on `/profile`, matching the Theme Preference interaction pattern, with exactly four ordered values: Off, Slow, Medium, Fast. The selected level applies to every individual list rather than being stored separately by list.
- Implement the control as a QuickList-owned custom ProfileBlock, following the LingoCafe custom preferences pattern. Register it directly in `src/config/quicklist/config.ts` with `type: 'component'` and profile-key ownership metadata; do not add QuickList UI to the shared `42go` block library.
- Store and validate the enum in the existing `auth.users.profile` JSON through the central `/api/profile` load/save flow and QuickList `app.profile.schema`, avoiding a database migration.
- The preference is stored as an account setting, fetched whenever the PickNote app loads in any browser, and applied locally to control list polling.
- Intervals are Slow = 30 seconds, Medium = 15 seconds, and Fast = 5 seconds; Off performs no scheduled polling.
- Medium is the default. If the account has no saved auto-refresh value, an open list polls every 15 seconds immediately.
- Auto-refresh runs only while a concrete list detail page is mounted. It never runs on the lists overview. Pause scheduled work while the document/app is hidden and prevent overlapping requests.
- When a list is still open and the app returns to the foreground (for example after locking and unlocking a phone, resuming the installed web app, restoring the page, or making the tab visible), immediately run one conditional refresh check for Slow, Medium, or Fast even if the normal interval has not elapsed. Off performs no resume check.
- Polls send the last known opaque change token (prefer standards-based `If-None-Match`/ETag, with `Last-Modified` only if useful). The API returns `304 Not Modified` with no list payload when unchanged and `200` with the complete authoritative payload plus the new token when changed.
- Derive the token from the timestamps/version information already maintained by the project and its tasks if this can be made collision-safe; avoid a schema migration.

## Definition of Success

- A second browser/session can change a shared list and the first open list reflects that change after manual refresh or within the selected auto-refresh interval.
- The lists overview reflects newly created, renamed, shared, or removed lists when its manual refresh is used, without starting scheduled polling.
- A user who pockets/locks a phone with a list open sees current data as soon as the app is resumed, without waiting for the remaining polling interval.
- Unchanged polls return no full JSON payload and do not replace UI state or cause visible flicker.
- No database migration is required.

## Additional Context

- Relevant client files: `src/app/(app)/quicklists/[id]/page.tsx`, `src/lib/quicklists/hooks/useQuicklistData.ts`, and `src/lib/quicklists/hooks/useQuicklists.ts`.
- Relevant API file: `src/app/api/quicklists/[projectId]/route.ts`.
- Relevant profile pattern: `src/app/(app)/(lingocafe)/_components/LingocafePreferences.tsx`, registered from `src/config/lingocafe/config.ts` with `type: 'component'`, `profileKeys`, `useProfile()`, and `useProfileBlockHandle()`.
- The QuickList profile config already composes core profile blocks in `src/config/quicklist/config.ts`; the new app-specific block should participate in the existing global `Save preferences` orchestration.
- The route currently computes `GREATEST(p.updated_at, MAX(t.updated_at), MAX(t.completed_at)) AS freshness`; mutation routes generally touch `quicklist.projects.updated_at`.
- Related historical contracts: archived ACC (conditional project GET) and AAY (list-page polling). Their timestamp token was only second-precision; the new design must not miss multiple changes within one second, especially at the Fast interval.

## Assumptions

- The operator's PickNote name maps to the repository's current QuickList app and `/quicklists/[id]` route.
- Personal means the preference belongs to the signed-in account and is not shared with collaborators.
- One account-wide level applies to every list. It is not keyed by list ID.
- The setting must follow the account across browsers and devices; browser-only persistence is not sufficient.
- The profile JSON is the migration-free persistence mechanism for this account setting.
- Existing and new accounts may have no stored auto-refresh key; absence resolves to Medium rather than Off or a validation error.

## Constraints

- Do not add a database migration unless refinement proves a correct collision-safe conditional token cannot be built from existing data.
- Keep polling minimal: one request at a time, only on the list detail route, no scheduled polling from the projects overview or list info page, and no full payload on unchanged detail responses.
- Treat foreground/resume signals as one deduplicated conditional check; do not start overlapping visibility, focus, pageshow, and interval requests.
- Preserve access control and anti-enumeration behavior on every conditional request.
- Do not let background refresh overwrite an in-flight optimistic mutation or discard unsaved list/task edits.
- Use a collision-safe token with enough precision or hashing to distinguish rapid consecutive changes.

## Acceptance Criteria

- [ ] The individual-list manual refresh always reconciles the rendered title and task collection with the latest successful server payload.
- [ ] The lists-overview manual refresh always reconciles the rendered projects and invitations with the latest successful server payload.
- [ ] Manual refresh actions expose accessible pending/disabled states and do not start duplicate concurrent fetches.
- [ ] Manual refresh bypasses ETag/change-token short-circuiting and receives a full `200` payload; scheduled polling sends the last token and may receive `304`.
- [ ] One personal account control exposes Off, Slow, Medium, and Fast in that order and applies the selected value to every individual list.
- [ ] The control is rendered only on the QuickList `/profile` page through an app-owned custom component registered as `type: 'component'` in `app.profile.items`.
- [ ] The custom block uses `useProfile()` for central profile state, participates in save/validation orchestration through `useProfileBlockHandle()`, and declares ownership of its profile key through `profileKeys`.
- [ ] QuickList `app.profile.schema` validates the persisted value as exactly one of `off`, `slow`, `medium`, or `fast` while remaining compatible with existing QuickList profiles that do not yet contain the key.
- [ ] Saving uses the existing `/api/profile` and `auth.users.profile` JSON path; no new preference endpoint, user-id input, or database migration is introduced.
- [ ] Off disables scheduled polling; Slow polls every 30 seconds; Medium every 15 seconds; Fast every 5 seconds.
- [ ] A missing preference resolves to Medium, so an open list auto-refreshes every 15 seconds without requiring the user to visit `/profile` first.
- [ ] The selected level is persisted once per account, follows the user across browsers/devices, is not keyed by list, and does not become a collaborator-shared setting.
- [ ] The PickNote app fetches the account setting on load and applies it locally before starting scheduled polling.
- [ ] Polling starts only for the mounted list detail page, cleans up on route change/unmount, does not overlap requests, and pauses while the page is hidden if supported by the chosen implementation.
- [ ] For Slow, Medium, and Fast, returning an already-open list to the foreground triggers one immediate conditional check regardless of elapsed interval time; Off triggers none.
- [ ] Mobile resume/unlock is handled through appropriate web lifecycle signals such as `visibilitychange`/visible and `pageshow`, with focus as a guarded fallback where useful.
- [ ] Duplicate resume signals are coalesced, an in-flight request is not duplicated, and the regular interval restarts from the completed resume check.
- [ ] The lists overview never starts scheduled polling, regardless of the account level; it updates only through its existing lifecycle fetches and explicit manual refresh.
- [ ] `GET /api/quicklists/[projectId]` emits a standards-compliant opaque change token representing the project plus all task-visible changes.
- [ ] A matching conditional request returns `304 Not Modified` with no list JSON body; a stale or absent token returns `200` with the full payload and current token.
- [ ] Multiple list changes inside one second cannot produce the same effective token and be missed by Fast polling.
- [ ] A `304` causes no visible loading flicker, task reordering, or state replacement; a changed `200` updates the list once.
- [ ] Background responses cannot overwrite newer optimistic/local changes; refresh behavior is deterministic when polling overlaps a mutation.
- [ ] Unauthorized/missing list behavior remains 401/404 according to the existing policy and anti-enumeration contract.
- [ ] Automated coverage verifies token generation, conditional 200/304 behavior, manual reconciliation, interval mapping, cleanup, and rapid-change handling.
- [ ] `npm run qa` passes and manual QA covers two authenticated sessions editing the same shared list on desktop and mobile.

## Dos

- Use React Query's authoritative cache as the single refresh source or explicitly synchronize local editable state after successful fetches.
- Reuse the API's existing freshness query or another migration-free derived token if it satisfies rapid-change correctness.
- Keep the preference UI keyboard-accessible and label the current interval clearly.
- Keep the custom block with the QuickList feature that owns it; follow the LingoCafe custom ProfileBlock composition pattern.

## Don'ts

- Do not schedule polling on the projects overview, list info route, or unrelated PickNote pages. The overview still keeps a working manual refresh.
- Do not return `{ changed: false }` with a `200` and a redundant JSON body when HTTP `304` semantics can express the result.
- Do not restore the archived second-precision ETag format unchanged.
- Do not introduce WebSockets, server-sent events, or a new synchronization framework for this task.
- Do not put the QuickList-specific preference component under `src/42go/components/ProfileBlock/blocks/`.
