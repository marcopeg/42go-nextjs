# Plan — PickNote: Repair List Refresh and Add Conditional Auto-Refresh

## Goal

Make manual refresh authoritative on both QuickList screens and add account-backed, conditional auto-refresh for open lists with final intervals Off, Slow (30s), Medium (15s default), and Fast (5s), without a database migration.

## Milestones

### Milestone 1 — Define and persist the QuickList refresh preference

- [x] Step 1 — Create the app-owned preference contract
  - Achieve: Define one typed account preference with values `off`, `slow`, `medium`, and `fast`; resolve a missing value to `medium`; map levels to `null`, `30000`, `15000`, and `5000` milliseconds.
  - Create: A QuickList-owned preference/options module near the QuickList feature, exposing the enum, default resolver, and interval mapping.
  - Modify: `src/config/quicklist/config.ts` to add an optional profile property with enum validation while remaining compatible with existing profiles that lack the key.
  - Delete: Nothing.
  - Touch points: `auth.users.profile`, QuickList `app.profile.schema`, `/api/profile` load/save behavior.
  - Validation: Native Node tests cover every level, the 15-second default, invalid/missing input handling, and schema compatibility with an empty existing profile.
  - Notes: Keep the setting account-wide, not keyed by list ID. Do not add a migration or a new preference API.

- [x] Step 2 — Add the QuickList custom profile block
  - Achieve: Render an accessible four-tab segmented control matching Theme Preference on the QuickList `/profile` page and save it through the existing global `Save preferences` action.
  - Create: A QuickList-owned client component modeled on `LingocafePreferences`, using `SimplePanel`, `useProfile()`, and `useProfileBlockHandle()`.
  - Modify: `src/config/quicklist/config.ts` to register the component with `type: 'component'` and the refresh key in `profileKeys`.
  - Delete: Nothing.
  - Touch points: `src/app/(app)/(lingocafe)/_components/LingocafePreferences.tsx` as the composition reference; shared ProfileBlock runtime only as a consumer.
  - Validation: Verify keyboard operation, visible current selection, interval labels, disabled loading/saving behavior, dirty-state detection, schema rejection of unsupported values, and persistence after sign-out/sign-in in another browser.
  - Notes: Keep all QuickList-specific UI outside `src/42go/components/ProfileBlock/blocks/`.

### Milestone 2 — Restore a standards-based conditional list API

- [x] Step 1 — Build a collision-resistant representation token
  - Achieve: Generate a quoted, opaque ETag that changes for every project/title/task field visible in the list response, including rapid consecutive changes, without relying on the archived second-precision format.
  - Create: A small QuickList refresh/ETag helper that canonicalizes the resource representation, generates the token, and safely evaluates `If-None-Match` values.
  - Modify: Nothing outside the helper in this step.
  - Delete: Nothing.
  - Touch points: Existing project/task timestamps and the canonical JSON response shape.
  - Validation: Native Node tests cover stable tokens for identical data, changed tokens for title/task/order/completion changes, quoted header matching, non-matching tokens, and rapid same-second changes.
  - Notes: Prefer a strong hash of the canonical visible representation when timestamp precision cannot guarantee uniqueness. No schema change is allowed.

- [x] Step 2 — Apply conditional semantics to the project GET route
  - Achieve: Return `200` with the complete list and ETag when no token is supplied or data changed; return bodyless `304` when `If-None-Match` matches.
  - Create: Focused route/helper tests or injectable handler coverage for the 200/304 contract.
  - Modify: `src/app/api/quicklists/[projectId]/route.ts` to emit the ETag, inspect `If-None-Match`, preserve deterministic ordering, and retain current 400/401/404 access semantics.
  - Delete: Any obsolete debug/query-parameter conditional behavior if encountered; header-based HTTP semantics become authoritative.
  - Touch points: `Cache-Control`, `ETag`, `If-None-Match`, access-controlled project/task queries.
  - Validation: Verify no JSON body on 304, full JSON on 200, a fresh ETag after every visible mutation, and no access-control information leakage.
  - Notes: Manual refresh deliberately omits `If-None-Match`; scheduled polling supplies it.
