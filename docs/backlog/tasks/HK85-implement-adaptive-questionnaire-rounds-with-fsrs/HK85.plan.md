# Plan — Implement Adaptive Questionnaire Rounds with FSRS

## Goal

Deliver a protected, transaction-safe reader service that starts or resumes a
10-question book round, selects adaptive questions from concept-level memory,
grades answers server-side, updates auditable FSRS-6 state exactly once, and
returns historical results without exposing answer keys before submission.

## Milestones

### Milestone 1 — Lock the runtime contract and concurrency invariants

- [x] Step 1 — Add active-round database uniqueness
  - Achieve: Guarantee at most one in-progress round per learner,
    questionnaire, and mode under concurrent starts.
  - Create: An additive Knex migration with a partial unique index.
  - Modify: Questionnaire schema tests and runtime data-model documentation.
  - Delete: Nothing.
  - Touch points: `lingocafe.questionnaire_rounds` and existing lifecycle checks.
  - Validation: Duplicate active inserts fail while completed or abandoned
    history and active rounds for another mode remain valid; rollback removes
    only the new index.
  - Notes: The service catches the uniqueness race and reloads the winner.

- [x] Step 2 — Define explicit service and HTTP response contracts
  - Achieve: Separate safe play payloads from post-answer feedback and complete
    historical results.
  - Create: Questionnaire runtime types, validation helpers, and route error
    mapping.
  - Modify: Nothing outside the new runtime module and routes.
  - Delete: Nothing.
  - Touch points: Existing protected LingoCafe route and no-store JSON patterns.
  - Validation: Before answering, payloads contain option text but no
    correctness flags; answer/result payloads expose correctness and the right
    answer only for answered historical items.
  - Notes: Request count stays internal and fixed at 10 in version one; mode is
    an open string with `standard` as the only accepted public value initially.

### Milestone 2 — Build the FSRS and adaptive-selection core

- [x] Step 3 — Add the version-pinned FSRS adapter
  - Achieve: Convert stored learning-item memory to and from FSRS cards using
    0.90 requested retention, binary `Again`/`Good` grades, enabled fuzz, and a
    stable review seed.
  - Create: A scheduler adapter with normalized card/review snapshots and
    parameter provenance.
  - Modify: Package dependencies and lockfile.
  - Delete: Nothing.
  - Touch points: `ts-fsrs@5.4.2`, FSRS version 6 semantics, and TG18 memory

  - Validation: Fixed histories reproduce due dates and before/after state;
    retries derive identical seeds and schedules; parameter digest remains

  - Notes: The adapter is the only module allowed to depend directly on the
    scheduler library, keeping later scheduler or parameter modes replaceable.

- [x] Step 4 — Implement deterministic candidate ranking
  - Achieve: Select distinct active current questions in due, unseen, then
    lowest-retrievability order while scheduling learning items rather than
    individual prompts.
  - Create: Candidate query/ranking functions with explainable selection data.
  - Modify: Runtime service module.
  - Delete: Nothing.
  - Touch points: Active questionnaire content, current revisions, revision
    learning-item links, memory due dates, and FSRS retrievability.
  - Validation: Due concepts rank by lateness/urgency; unseen concepts expand
    coverage deterministically; fallback ranks weakest retained concepts;
    withdrawn questions never enter a new round; one question appears once.
  - Notes: Stable IDs break ties. A question linked to multiple concepts uses
    its most urgent linked concept for ranking but answering reviews every
    linked concept exactly once.
