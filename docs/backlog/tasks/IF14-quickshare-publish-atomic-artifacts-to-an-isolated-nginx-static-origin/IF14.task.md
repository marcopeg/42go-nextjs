# QuickShare: Publish atomic artifacts to an isolated Nginx static origin

## Elevator's Pitch

Project explicit QuickShare publishes into versioned static artifacts served directly by a dedicated Nginx container.

## Business Gain

Published pages are fast, cacheable, and isolated from the editor, sessions, database, and Next.js runtime.

## Current State

QuickShare has no publication projection, shared output volume, Nginx public origin, static URL mapping, or atomic update protocol.

## Desired State

The publisher accepts a complete validated release bundle from a type-specific compiler and projects it into a configurable local output folder mounted as a shared Docker volume. IF14 owns the bundle/manifest input contract, staging, reference verification, immutable release storage, stable-route activation, purge, and Nginx delivery; it does not own text, Markdown, web-page, or template compilation. Each bundle contains `index.html`, a manifest, and zero or more content-hashed sidecar files such as CSS, JavaScript, images, fonts, and media. A dedicated Nginx image/container alone serves s.42go.dev. Each resource has exactly one stable URL mapped to a folder entry with `index.html`: its globally unique random short code (one segment) by default, or its custom ID beneath the owner's handle (two segments) after customization. Atomic release changes the active stable entry only after every file in the new bundle exists. When a published resource adopts a custom ID, that publish creates the new handle/custom-ID stable entry before removing or renaming the old short-code stable entry; when a custom ID is removed, the system first generates a new short code and the next publish performs the inverse switch. The old path must stop resolving after either switch.

The projection layer also owns complete resource-output purge for Unpublish and Delete. Unpublish removes every publicly reachable static file for the resource but preserves database source and lifecycle records. Delete uses the same purge before the caller removes the database record. Handle change atomically renames the owner's handle-scoped stable folder after availability validation; affected custom URLs change immediately, old handle paths stop resolving, and no redirects or aliases remain. Random one-segment short URLs are unaffected.

For a pending identifier switch, the old `publishedUrl` remains live while `nextPublicUrl` names the candidate. Atomic activation creates the candidate route first, retires the prior route, and only then promotes the candidate to published state. Content-only publication reuses the same route and never creates a second URL state.

## Definition of Success

Publishing creates a complete immutable multi-file release, atomically advances its stable URL, and public browser requests are answered only by Nginx. Stable entry documents revalidate so updates appear promptly; content-hashed assets receive long-lived immutable caching.

## Additional Context

The filesystem/object-key layout must distinguish stable public entries from immutable release files. A resource uses either `{code}/index.html` or `{handle}/{customId}/index.html`, never both; a custom ID replaces the default short code and is unique only within its normalized handle. Both forms reference assets beneath a reserved, versioned resource/release prefix that public handles and IDs cannot claim. Exact internal prefixes may change during planning, but stale HTML must continue to resolve every asset it references. Complete releases are retained in version one; publication is not temporary cleanup. The later S3/CloudFront origin must be able to preserve the same public URL and key semantics.

## Assumptions

- Atomic filesystem publication can use staging plus same-filesystem rename or an equivalent pointer switch.
- Stable entry HTML is revalidated or briefly cached; hashed release assets are safe for one-year immutable caching.

## Constraints

The local volume is a projection, never the source of truth. Public requests must not touch Next.js, PostgreSQL, server rendering, or sessions. Version artifacts rather than markup-internal versioning. Keep path/object-key design ready for later private S3 plus CloudFront migration, but implement neither. Cookies remain host-only to quickshare.42go.dev.

## Acceptance Criteria

- Environment configuration selects the shared publication folder and Docker mounts it into the publisher and Nginx containers.
- A versioned generic bundle/manifest interface accepts complete compiler output, rejects malformed or incomplete bundles before staging, and is verified independently with fixture bundles.
- The Nginx container is a separate image/container and serves only published static output on s.42go.dev.
- Exactly one active stable URL folder per resource uses index.html without exposing .html: the short-code folder by default, or the handle/custom-ID folder after customization.
- Publish stages a complete release bundle and manifest, verifies all references, then atomically updates the stable entry; failed publishes leave the prior public version intact. A custom-ID switch creates the new stable path before removing or renaming the old short-code path, and the old path then returns no public resource.
- Identifier-switch activation keeps `publishedUrl` live until `nextPublicUrl` is ready, then retires the former and promotes the latter in one coordinated success path; failures preserve the old route and pending candidate state.
- `index.html` can reference content-hashed CSS, JavaScript, images, fonts, and other sidecar assets without inlining them.
- Nginx sends revalidation-oriented cache headers for stable HTML and long-lived immutable cache headers plus correct MIME types for content-hashed assets.
- Previously published entry documents never lose referenced sidecar files as a consequence of a later publish.
- Unpublish removes every publicly reachable delivery artifact for the resource while leaving its database-authoritative draft available; a failed purge leaves lifecycle state unchanged and reports failure.
- Published-resource Delete completes the same delivery purge before database deletion can succeed, so successful deletion leaves neither a stable public route nor immutable delivery assets for that resource.
- Handle-folder rename is atomic, moves all handle-scoped stable entries together, leaves no old-handle routes or redirects, and does not affect random short-code routes.
- The immutable bundle namespace is reserved from user-selected handles/custom IDs and cannot be confused with the one-segment or two-segment stable URL forms.
- Static cache behavior, security headers, traversal protection, disabled directory listing, service-worker scope, and the mutually exclusive one- or two-segment URL routing are tested.
- Public-origin requests prove there is no Next.js, database, SSR, or session dependency.

## Dos

- Version the complete release and validate its manifest before switching the stable entry.
- Keep type-specific source rendering and compilation out of IF14; accept only the shared completed-bundle contract.
- Make the output layout portable to object storage and CDN caching.

## Don'ts

- Do not overwrite assets in place, rely on query-string cache busting, or require all assets to be inlined.
- Do not let Nginx proxy missing pages or assets to QuickShare.

## Open Questions

The exact atomic pointer representation is an implementation-plan decision; it must preserve the stable public URL, old release references, and later object-storage portability.
