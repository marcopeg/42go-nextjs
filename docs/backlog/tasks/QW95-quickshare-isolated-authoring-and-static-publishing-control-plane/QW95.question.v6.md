## Questions

### 1. Version one calls resources permanent, but YW90 and KQ66 promise delete operations. Should owners be able to delete a share? If yes, must deletion remove the stable public URL immediately while retaining immutable release bundles internally, or should version one support only archive/hide with no destructive resource deletion?

Answer:

Owners may delete a share. Deleting any draft requires confirmation. Deleting a resource that has ever been published requires a stronger confirmation explaining that the disruptive action permanently removes the account record and all of that resource's output from the static delivery folder, so its public URL stops working.

Also add an explicit Unpublish action. Unpublish removes the resource's complete static output from the delivery folder but preserves its database record and authoritative draft, returning it to draft-only mode so it remains available in the owner's account but is no longer shared.

### 2. Can a QuickShare account change its normalized handle after onboarding? If yes, what happens to every published `{handle}/{customId}/` URL: move on each resource's next publish, migrate all atomically, redirect, or remain bound to the old handle? If handle changes are not required in version one, should handles be immutable?

Answer:

Handles can change. The new normalized handle must pass availability validation before the change. The UI requires a strong confirmation explaining that this disruptive operation changes every handle-scoped public URL immediately. No redirects, aliases, or backward-compatible routes are retained. The publisher atomically renames the owner's handle folder in the delivery projection; one-segment random short-code URLs are not handle-scoped and therefore remain unchanged.
