# QuickShare: Isolated authoring and static publishing control plane

## Elevator's Pitch

Deliver QuickShare as a new, isolated 42 Connect application where authenticated accounts author durable text, Markdown, advanced web pages, and guided template mini apps, then explicitly publish versioned static bundles to a dedicated origin.

## Business Gain

QuickShare gives technical and non-technical accounts one dependable publishing control plane without changing QuickNotes or placing public traffic on the application, database, or session boundary. Guided templates make common mini apps publishable in minutes while advanced authors retain full HTML/CSS/JavaScript control.

## Current State

QuickNotes has separate existing implementation scope and prior backlog work. QuickShare does not yet exist as an app configuration, data space, editor, publishing projection, static origin, automation API, or automation skill.

## Desired State

QuickShare runs at quickshare.42go.dev as a new app-scoped account/editor surface. It owns draft source and template configuration in its own database schema and publishes only explicit versions to s.42go.dev through a shared Docker-volume projection served by a dedicated Nginx container. Every shareable resource—text, Markdown, web page, or template instance—has an internal UUID and exactly one active public URL. Creation assigns a random globally unique short-code URL and previews that final URL; an optional available custom identifier instead produces a handle-scoped URL. Each publish may emit `index.html` plus content-hashed CSS, JavaScript, images, fonts, and other sidecar assets. The public origin never calls Next.js, PostgreSQL, server rendering, or account-session authority.

## Definition of Success

A QuickShare account completes app-unique normalized-handle onboarding, creates a text, Markdown, plain HTML/CSS/JavaScript web page, or guided-template resource with its final public URL previewed, repeatedly saves durable drafts, explicitly publishes, and can replace the default random short-code URL with an available handle-scoped custom identifier. The API supports the same choice on creation and returns the resulting active public URL. The initial Linktree-style links template can be configured and published without code. Public traffic is served directly by Nginx from immutable versioned bundles while the editor's host-only cookies never reach s.42go.dev.

The editor exposes the version-one catalog through a `+ New Share` split button whose popover lists plain text, Markdown, web page, and maintained guided-template choices. Token-authenticated automation clients must provide the type explicitly. A token-authenticated GET discovery endpoint exposes enough live contract metadata for an agent to construct and validate supported CRUD and publish requests without relying on change-prone payload details embedded in its skill.

Owners can Unpublish a resource to purge its complete static delivery output while preserving its database-authoritative draft, returning it to draft-only mode. Owners can Delete a draft after normal confirmation. Deleting a resource that has ever been published requires stronger disruptive-action confirmation, purges its complete static delivery output, and permanently deletes its account record. A handle change requires availability validation and strong confirmation, atomically renames the owner's handle-scoped delivery folder, immediately changes every handle/custom-ID URL, and creates no redirect or alias; random one-segment short URLs remain unchanged.

## Additional Context

The first three delivery tasks require a corrected ordering decision because the text/Markdown task cannot prove a public update before the generic static publisher, delivery volume, and Nginx origin exist. Resources are durable until an owner explicitly unpublishes or deletes them; retention across ordinary republishes does not prevent explicit delivery-output purge on Unpublish or Delete. Any earlier use of "permanent" in this epic means no automatic expiry or cleanup, not protection from an explicit owner-confirmed Delete.

Core delivery order: (1) XO00 isolated app, onboarding, schema, and shared domain contracts; (2) IF14 generic validated-bundle projection, atomic activation/purge, handle-folder operations, and isolated Nginx origin, verified with fixture bundles; (3) YW90 durable text/Markdown authoring and the first real compilers integrated end to end with IF14; (4) QU22 plain HTML/CSS/JavaScript web-page authoring and compiler; (5) HZ42 extensible maintained templates and initial links page; (6) KQ66 personal-token lifecycle and authentication boundary; (7) ZA41 versioned automation API and live discovery; (8) VG23 maintained skill and deterministic client. Resources have no automatic expiry but remain explicitly unpublishable and deletable.

Every resource has an internal UUID independent of its public path and exactly one currently published route. Creation assigns a globally unique random short code and previews `s.42go.dev/{code}/`; an available custom ID instead selects `s.42go.dev/{handle}/{customId}/` and is unique only within that normalized handle. Removing a custom ID generates a new random code rather than restoring a former one. Resource state exposes nullable `publishedUrl` for the currently working route and `nextPublicUrl` for the configured route candidate. They differ only while a published resource has a pending identifier switch; content-only edits leave the URL unchanged and do not trigger duplicate URL treatment. After successful Publish, `nextPublicUrl` becomes `publishedUrl` and the old route disappears. An unpublished resource has `publishedUrl: null`. Ordinary republishes retain immutable releases, while explicit Unpublish or Delete purges the resource's complete delivery output.

Plain text is HTML-escaped into a minimal document and Markdown is rendered to final HTML at publish time. Version-one web pages accept plain HTML, CSS, JavaScript, and managed assets without rich editing, TypeScript, transpilation, CSS processing, package imports, or dependency bundling. Each compiler emits the shared validated bundle contract containing `index.html`, a manifest, and any content-hashed sidecar assets; IF14 never owns type-specific compilation. Templates are versioned schema-driven authoring modes using the same resource and publisher contracts. Rich web-page editing and CSS/JavaScript transpilation remain separate second-release tasks. Metering, statistics, access blocking, redirects, URL-shortener metrics, HAL, and bot integrations remain outside version one; Telegram Mini App compatibility is only a published-page boundary requirement.

The `+ New Share` picker, automation API validation, and discovery response must derive from the same supported-type contracts so the human and agent capability lists cannot drift. All automation APIs, including discovery, require a valid personal API token. Discovery is token-scoped and may report the token owner's effective capabilities. Its versioned response describes the resource-type and template catalog and, for each supported CRUD or publish operation, the method, endpoint template, request and response schemas, required and optional fields, types, enum values, defaults, constraints, limits, actions, custom-ID rules, machine-readable errors, and lifecycle metadata such as availability, deprecation, replacement, and removal timing. It never exposes secrets, client-selectable ownership, filesystem paths, or deployment pointers. YW90 owns the shared split-button creation flow, QU22 contributes the web-page type, HZ42 contributes maintained template choices, KQ66 owns personal-token lifecycle and bearer identity, ZA41 owns the versioned automation API and live discovery, and VG23 owns the stable authenticate-discover-interpret-execute skill/client workflow.

## Assumptions

- The existing authenticated account platform can scope a new application without sharing product data.
- A shared Docker volume is sufficient for the first static-origin projection and does not alter the stable public contract.

## Constraints

Leave QuickNotes and its implementation scope untouched. QuickShare is a separate AppConfig, schema, account-scoped data space, and public-origin deployment. Drafts are authoritative; release bundles and filesystem output are projections. Publish must create a complete versioned/content-hashed bundle and atomically move the one active stable URL to the new current release. A custom identifier replaces rather than supplements the default short-code URL, and is unique only within its owner's normalized handle. Keep public object keys migration-ready for a later private-S3-plus-CloudFront origin without implementing AWS now. Version one uses simple text areas and accepts only plain HTML, CSS, and JavaScript; rich editing, TypeScript, CSS/JavaScript transpilation, and package bundling are deferred. Do not add temporary lifecycles, expiry, cleanup, public rendering in QuickShare, shared QuickNotes resources, viewer credentials, or HAL launch flows. Account cookies must remain host-only to quickshare.42go.dev.

## Acceptance Criteria

- The retained children execute in explicit dependency order: XO00 → IF14 → YW90 → QU22 → HZ42 → KQ66 → ZA41 → VG23.
- IF14 proves the generic publisher independently with fixture bundles; YW90 then proves the first real end-to-end text/Markdown publication, and every later compiler targets the same validated-bundle interface.
- QuickNotes remains unmodified by the QuickShare delivery.
- The editor, database drafts, token API, compiler, template registry, bundle projection, and isolated Nginx public origin satisfy each child task's focused acceptance criteria.
- Text, Markdown, web-page, and initial guided-template resources all publish through one atomic versioned-bundle contract that supports sidecar assets, has an internal UUID independent of the public path, previews the final URL on editor creation, and exposes exactly one active URL per resource: its random short code by default or its available handle-scoped custom identifier.
- The editor exposes all available version-one types through a `+ New Share` split-button popover; token-authenticated automation creation requires an explicit type; and token-authenticated GET discovery provides the live schemas, options, operations, limits, errors, and lifecycle metadata an agent needs to construct supported CRUD and publish requests from the same contracts.
- Resource UI and API state expose `publishedUrl` and `nextPublicUrl`; the values differ and both are displayed only for a pending identifier switch, while content-only edits retain one unchanged URL and successful Publish promotes the candidate atomically.
- The maintained QuickShare skill keeps a stable authentication/discovery/execution workflow and obtains change-prone payload and option details from discovery rather than hard-coding them.
- Unpublish purges all delivery output for the resource without deleting its database draft; Delete requires confirmation, uses stronger disruptive confirmation after any publication, purges all delivery output, and deletes the account record.
- A handle change validates availability, requires strong disruptive confirmation, atomically renames the handle-scoped delivery folder, changes affected custom URLs without redirects or aliases, and leaves random short URLs unchanged.
- A full account-to-save-to-publish-to-public-URL proof shows public requests do not reach the Next.js app or database and do not receive editor cookies.
- The backlog index is regenerated deterministically and each QuickShare task appears once.

## Dos

- Execute child tasks in listed order and preserve their ownership boundaries.
- Treat a published version as immutable output from the authoritative draft.

## Don'ts

- Do not fold QuickShare into QuickNotes or route public pages through the editor application.
- Do not make future metering, statistics, access blocking, redirects, or URL shortening delivery work.
- Do not require assets to be inlined or create a separate publication system for templates.

## Open Questions

None. Resource lifecycle, URL-state semantics, compiler/publisher ownership, and the eight-child dependency sequence are concrete, and every retained child has an independent verification boundary.
