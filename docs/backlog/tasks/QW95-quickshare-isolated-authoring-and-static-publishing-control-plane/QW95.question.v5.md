## Questions

### 1. Should the documentation-as-API discovery endpoint be public, require an authenticated QuickShare session, or require a personal API token? Should its response be identical for every caller, or may it include account-specific availability?

Answer:

All automation APIs, including discovery, require a valid personal API token. Discovery is token-scoped and may report the effective capabilities available to that token owner.

### 2. Which machine-readable details must version one expose for each available type and option? For example: stable type ID, label and description, create/update payload schema, required fields and defaults, custom-ID rules, supported actions, template IDs/versions/configuration schema, limits, and capability/deprecation metadata.

Answer:

Design the response so an agent can construct and validate every supported share CRUD and publish request dynamically. The maintained skill explains how to authenticate, call discovery, interpret the contract, and execute the workflow, but it must not hard-code change-prone resource payloads or options.

Version one discovery returns a contract version plus the effective resource-type and template catalog. For each supported operation it provides the HTTP method and endpoint template, request and response schemas, required and optional fields, types, enum values, defaults, validation constraints and limits, supported actions, custom-ID rules, and representative machine-readable error codes. Template entries include stable template ID/version and their configuration schema. Capability entries can carry lifecycle metadata such as availability, deprecation, replacement, and removal timing. The response must contain no token secret, raw ownership selector, filesystem path, or deployment pointer.
