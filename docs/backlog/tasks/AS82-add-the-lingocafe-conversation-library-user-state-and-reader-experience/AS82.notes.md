# Execution Notes — Add the LingoCafe conversation database foundation
**Task**: ./AS82.task.md
**Plan**: ./AS82.plan.md

## Decisions

- The operator authorized autonomous refinement, plan acceptance, execution, and sub-agent delegation through completion.
- AS82 was split from the full frontend. YE24 owns import/population; QT31 owns APIs and UI.
- Source lifecycle status and runtime visibility are separate fields.
- Conversation-round positions are 1-based.
- The schema uses explicit `is_visible`; database checks forbid deprecated/retired rows from being visible.
- Materialized category/scenario membership is language-independent; applicability remains explicit on content rows.

## Problems Encountered

- The first migration sub-agent stalled before writing. Its turn was interrupted without filesystem changes; the primary agent implemented the migration and delegated the contract and fixture independently.
- The first fixture upsert attempted `DO UPDATE` for key-only edge rows, which PostgreSQL rejects. The helper now uses `ON CONFLICT DO NOTHING` when no non-key update columns exist.
- Independent review found missing lifecycle/visibility checks. Four database checks were added and verified live.

## Deviations From Plan

- PostgreSQL constraint probes were executed directly against the configured development database rather than added as an always-on test that would require database mutation in routine unit runs. Static migration/fixture tests remain deterministic and database-free.

## Additional Requests

- Complete the full three-task development cycle and leave the development app consumable end to end.

## Known Limitations

- The full corpus is intentionally unavailable until YE24 runs.
- The operator superseded the earlier additive-only assumption. The final
  pre-release baseline uses a prerequisite aggregate `lingocafe.personas`
  table with nested validated presentations, followed by one consolidated
  conversation migration and exhaustive
  `lingocafe.conversation_variant_cast`. A separate presentation table was
  rejected because presentations are never independently queried or
  lifecycle-managed.
- Presentation rows should store an environment-neutral relative avatar asset
  key plus SHA-256, not SVG bytes or an absolute host URL. The external assets
  service owns delivery; `LC_ASSETS_BASE_PATH` remains the deployment boundary.
- Refined prerequisite proposal: use a dedicated persona migration before the
  consolidated conversation migration. Store each persona as one aggregate row
  with a validated `presentations` JSONB map unless independent presentation
  querying/lifecycle becomes a demonstrated requirement. The conversation
  migration then adds an exhaustive `(scenario_id, variant_id, actor_id,
  persona_id nullable)` cast relation; null is the explicit scenario identity,
  not a missing row.
