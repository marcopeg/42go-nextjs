# Add the LingoCafe conversation database foundation

## Elevator's Pitch

Add the migration-derived PostgreSQL schema and standalone import contract that can safely hold the canonical LingoCafe category graph, scenarios, semantic variants, exact language/CEFR conversations, ordered actor rounds, runtime visibility, and per-user read/star state. Prove the schema in the development database before the books-side importer or frontend is built.

## Business Gain

LingoCafe gets a durable, constrained runtime model for a new content format without coupling the app to YAML or risking learner state during publication. The schema becomes the hard contract for `conv-push` and the full conversation frontend.

## Current State

The books repository's LL42 work has promoted a canonical corpus to `content/conversations/`. The current corpus has 79 query-backed categories with nine roots, 61 scenarios, 67 semantic variants, and 724 exact English, Swedish, and Italian A1-B2 conversations. Categories form a plural-parent DAG and do not own scenarios. Scenarios own actors and semantic context. Variants are scenario-scoped sub-scenarios. Exact conversations own localized title, description, language, CEFR, and ordered actor/text rounds.

42go-nextjs currently owns `lingocafe.books`, `books_pages`, `books_progress`, `books_completed`, and `translation_cache`. It has no conversation tables or standalone conversation data contract. Current source lifecycle values cannot be used as an accepted-only publication rule: all categories are `draft`, most scenarios/variants are release candidates or developed, and all exact conversations are `review`.

## Desired State

Add one new additive Knex migration in the `lingocafe` schema. Do not amend the historical create migration. Create these content-owned tables:

- `conversation_categories`: stable text ID, source lifecycle status, canonical title/description/goal, explicit language scope (`all` or `specific`) and specific-language array, tags, explicit runtime `is_visible`, source schema version/path/hash, flexible metadata JSONB, and created/updated timestamps.
- `conversation_category_parents`: plural directed edges with `(category_id, parent_category_id)` primary key, self-edge rejection, cascading category references, and a parent lookup index. Import validation owns DAG/cycle and visible-root reachability checks.
- `conversation_scenarios`: stable text ID, source lifecycle status, canonical language/title/description/learner promise, language scope, tags, `is_visible`, source audit fields, metadata JSONB, and timestamps.
- `conversation_scenario_localizations`: explicit scenario title/description by `(scenario_id, language, cefr_level)`.
- `conversation_category_scenarios`: materialized many-to-many category membership with match provenance JSONB and no runtime YAML-query evaluation.
- `conversation_scenario_actors`: scenario-scoped actor ID, ordered position, name, role, description, and metadata.
- `conversation_variants`: `(scenario_id, id)` identity, source lifecycle status, canonical title/description, language scope, tags, `is_visible`, source audit fields, metadata, and timestamps.
- `conversation_variant_localizations`: explicit variant title/description by scenario, variant, language, and CEFR.
- `conversations`: globally durable exact ID, scenario-scoped variant reference, source lifecycle status, language, CEFR, localized title/description, tags, `is_visible`, source audit fields, metadata, and timestamps. Enforce uniqueness for one scenario/variant/language/CEFR realization.
- `conversation_rounds`: ordered text with redundant `scenario_id`; enforce that the conversation belongs to that scenario and the actor belongs to that scenario. Use 1-based positions, non-empty trimmed text, and a `(conversation_id, position)` primary key.

Create these user-owned tables:

- `conversation_reads`: `(user_id, conversation_id)` primary key and `read_at` timestamp.
- `conversation_stars`: `(user_id, conversation_id)` primary key and `starred_at` timestamp.

Both user-state tables cascade on user/conversation deletion and have `(user_id, action_timestamp DESC)` indexes. Content import never writes them. Update the LingoCafe account-erasure handler and its reporting/tests to explicitly delete conversation reads and stars; do not expand this task into unrelated book-completion cleanup.

Separate source editorial `status` from runtime publication with `is_visible`. Preserve status verbatim. Deprecated categories and retired scenarios/variants/conversations must never be visible. The initial full-corpus importer will deliberately select the launch-visible set despite current draft/review statuses. A visible exact conversation also requires visible parents at runtime. Hard deletion remains an explicit future operation; normal withdrawal uses status/visibility so user state is not accidentally cascaded.

Publish `docs/lingocafe/CONVERSATIONS_DATA_MODEL.md` as the standalone contract for external importers. It must document accumulated migration authority, every table/column/key/check/index/FK, source-to-row mapping, 1-based ordering, language applicability, visibility, materialized membership, ownership boundaries, safe full/partial import behavior, schema-version compatibility, and forbidden user-state mutations.

Define surgical transaction semantics for YE24: acquire an advisory import lock; validate the full graph before SQL; upsert content rows; never infer top-level deletion from omission; replace outbound parent/membership rows only for explicitly imported categories; replace actors only under an explicit authoritative scenario scope and refuse actor deletion while rounds reference them; replace rounds only for explicitly imported exact conversations; never touch reads/stars or other LingoCafe tables. Empty authoritative replacement sets must be explicit.

Add a deterministic development fixture seed with fixed reserved IDs. It may upsert only its own category/scenario/variant/conversation/round rows and must not clear whole tables or user state. The full corpus is populated later by YE24.

Apply the migration and fixture to the development database. Verify clean `up -> down -> up`, final migration status, constraints, fixture rows, and unchanged pre-existing book/progress/completion counts.

## Definition of Success

The development database contains the complete, documented conversation schema and a small deterministic fixture. Invalid cross-scenario actor references, duplicate exact realizations, invalid language scopes, invalid statuses/levels, and empty rounds fail at the database boundary. Reapplying fixture/import-shaped upserts is safe and idempotent. User read/star rows are structurally separate and excluded from content publication. AS82's contract is sufficient for YE24 without reading this task.

## Assumptions

- PostgreSQL remains the only target.
- Stable structural IDs remain canonical English text IDs.
- Category/scenario language applicability is stored explicitly instead of inferred in runtime queries from tags.
- Scenario and variant localization tables are runtime data because category navigation may expose localized context before an exact conversation opens.
- Exact conversation read/star state attaches to the global exact conversation ID.
- Runtime visibility is explicit and independent of editorial lifecycle status.
- Full-text search, learning-goal browsing, variables, authoring, APIs, and frontend UI belong to later tasks.

## Constraints

- Treat the complete ordered migration history as schema authority.
- Add a new migration; do not rewrite historical migrations.
- Keep 42go-nextjs standalone and free of build/runtime dependencies on `../books`.
- Use PostgreSQL checks, composite foreign keys, indexes, timestamps, and Knex style consistent with existing migrations.
- Preserve scenario-scoped variant and actor identities; do not make either globally unique.
- Keep category membership many-to-many and parent edges plural.
- Do not store the whole runtime model as opaque JSONB; normalize relationships and display/query fields.
- Do not use source status alone as runtime visibility.
- Do not truncate or broadly delete conversation content or user state.
- Do not let content seeds/import contracts write reads, stars, profiles, consent, events, translations, books, or book progress.
- Use actor `RESTRICT` behavior where deletion could otherwise erase conversation rounds silently.
- Run migration up/down/up, migration status, targeted tests, `npm run qa`, and development-database verification.

## Acceptance Criteria

- A new additive migration creates all specified content and user-state tables in dependency-safe order.
- Categories enforce valid source status and coherent `all` versus `specific` language scope.
- Category parent edges reject self-links and support plural parents; cycle validation is explicitly importer-owned.
- Scenarios and variants enforce their allowed source lifecycle values and explicit visibility/language scope.
- Scenario and variant localizations are unique by parent, language, and A1/A2/B1/B2 level.
- Materialized category membership is many-to-many and can store query/explicit/blacklist audit provenance.
- Actors are unique and ordered within a scenario.
- Variants are unique only within a scenario.
- Exact conversations have global IDs and unique scenario/variant/language/CEFR realizations.
- Round constraints prove both conversation-scenario consistency and actor-scenario consistency; positions are 1-based and text is non-empty.
- Read and star rows are keyed by user/exact-conversation, cascade safely, and have user/timestamp indexes.
- Content ownership and user-state ownership are documented and enforced by seed/import semantics.
- The account-erasure handler explicitly deletes/reports conversation reads and stars and targeted tests cover it.
- `CONVERSATIONS_DATA_MODEL.md` fully documents the final accumulated schema and safe importer contract.
- A fixed-ID development fixture seed upserts only its own rows and never clears content or user state.
- Migration `up -> down -> up` succeeds on the development database and final migration status is current.
- Constraint probes reject invalid language scope, duplicate realizations, cross-scenario actors, bad CEFR/status values, and blank rounds.
- Pre-existing LingoCafe book, progress, and completion counts remain unchanged across migration verification.
- Targeted tests and `npm run qa` pass.
