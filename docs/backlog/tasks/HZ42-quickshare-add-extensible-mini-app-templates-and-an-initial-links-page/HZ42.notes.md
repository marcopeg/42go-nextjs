**Task**: ./HZ42.task.md
**Plan**: ./HZ42.plan.md

## Decisions

- Template instances use the foundation migration's dedicated `template_id`, `template_version`, and `template_config` draft-revision columns as their authoritative persisted state.
- The initial maintained template is `links-page@1`; drafts remain pinned to that exact version until an explicit upgrade succeeds.
- The catalog is intentionally generic: each entry owns its default draft, configuration parser, editor-form descriptor, and stable ID/version. The server compiler dispatches through a `templateId@version` implementation registry, so later templates do not alter the resource schema, persistence mechanics, or publisher.
- The initial Links Page uses a managed, bounded PNG/JPEG/WebP/GIF profile image rather than a remote image URL. Its static release remains self-contained and deterministic.
- No compatible upgrade is currently registered for `links-page@1`; the UI makes that explicit. The upgrade endpoint remains non-mutating on an unavailable target.

## Problems Encountered

- Direct Node test execution does not resolve `@/` aliases and throws for `server-only`. Template catalog/compiler imports use direct relative module paths so the focused contract test can run outside Next.js while feature entry points remain server-only.

## Deviations From Plan

- The current catalog contains only version one. The visible upgrade control therefore reports that no compatible upgrade is installed rather than presenting a fictitious migration.
