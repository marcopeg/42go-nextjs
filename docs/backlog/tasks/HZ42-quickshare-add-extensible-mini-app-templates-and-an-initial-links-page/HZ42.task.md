# QuickShare: Add extensible mini-app templates and an initial links page

## Elevator's Pitch

Let an account choose a maintained template, fill a small guided form, and publish a polished mini app without writing HTML, CSS, or JavaScript.

## Business Gain

Templates turn QuickShare from a developer-oriented publisher into a fast product for common pages such as Linktree-style link hubs, personal landing pages, and curricula.

## Current State

The QuickShare backlog covers plain text, Markdown, and advanced web-page source, but has no template registry, template configuration model, guided form, renderer, or upgrade contract.

## Desired State

QuickShare has an extensible template registry with stable template IDs, explicit template versions, validated configuration schemas, editor form definitions, previews, and publish renderers. The first maintained template is a Linktree-style links page with profile image, name, biography, ordered links, and a small set of visual options. A template instance stores its selected template version and account-owned configuration as authoritative draft data, then publishes through the same versioned static-bundle pipeline as every other resource.

## Definition of Success

A non-technical user can create the initial links-page template, enter content and options, preview it, click Publish, and receive the same stable QuickShare public URL and atomic static delivery guarantees as advanced pages.

## Additional Context

The template framework must make later personal landing page, curriculum/CV, and other mini-app templates additive. Existing instances remain deterministic when the template catalog evolves: they stay pinned to their recorded template version until an explicit, validated upgrade is performed. Template output may contain index.html plus content-hashed CSS, JavaScript, images, fonts, or other sidecar assets.

## Assumptions

Maintained templates are application code reviewed and shipped with QuickShare; user content enters only through each template's validated configuration schema.

## Constraints

Depend on the QuickShare data model, resource editor contracts, static publisher, and web build pipeline. Do not create a second publishing path or store rendered files as source of truth. Do not require users of guided templates to edit code. Template upgrades must never silently change a draft or published page.

## Acceptance Criteria

- A typed template registry defines stable ID, version, metadata, configuration validation, editor form, preview, and publish renderer contracts.
- Template instances are account-scoped permanent resources with database-authoritative versioned configuration drafts.
- The initial links-page template supports profile image, display name, biography, ordered links, and documented visual options with accessible output.
- Create, edit, reorder, preview, save, and explicit publish flows work without code editing.
- Publish emits a versioned bundle with index.html and content-hashed sidecar assets through the shared atomic static-origin pipeline.
- Existing instances remain pinned when a template changes; explicit upgrades validate or migrate configuration and cannot alter the current publication on failure.
- Adding a later landing-page or curriculum template requires a new registry entry and template implementation, not changes to the core data or publication architecture.
- Authorization, validation, rendering, visual, and QA tests pass.

## Dos

Keep template configuration portable, schema validated, previewable, and deterministic for a recorded template version.

## Don'ts

Do not call external template services, execute user code through guided configuration, or bypass the normal draft and explicit-publish lifecycle.

## Open Questions

The exact catalog after the initial links page is future product work; personal landing and curriculum/CV templates are directional examples, not acceptance dependencies.
