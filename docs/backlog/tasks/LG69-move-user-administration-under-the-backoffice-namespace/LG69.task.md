# Move User Administration Under the Backoffice Namespace

## Elevator's Pitch

Move the existing authenticated user-administration page, details workflow, and management API beneath the new top-level backoffice namespace so internal operational tools have one coherent home.

## Business Gain

- Establish a predictable URL hierarchy for backoffice tools instead of scattering privileged pages among ordinary app routes.
- Make future shared backoffice navigation, layout, breadcrumbs, and policy conventions easier to introduce.
- Preserve current user-management behavior and authorization while giving operators stable, explicit management URLs.

## Current State

- The backoffice-only user page is served from `src/app/(app)/users/page.tsx` at `/users`.
- User list, update, and deletion handlers are served from `/api/users`.
- The page and API already require feature flags, authenticated session, `backoffice` role, and user-management grants, but the URLs have no management namespace.
- OE92 introduces `/backoffice` for notification management and establishes it as the intended namespace for future management surfaces.

## Desired State

- Serve user administration from `/backoffice/users` under the authenticated `(app)` organization.
- Serve the corresponding management API from `/api/backoffice/users`.
- Preserve the existing `page:users` and `api:users` feature flags plus session, current-app, `backoffice` role, and exact grant checks.
- Move the complete list/details/edit/delete client workflow without changing its business behavior.
- Update every repository-owned AppConfig navigation entry, internal link, fetch URL, document, and test to use the namespaced routes. This includes the desktop/bottom menu entries in the LingoCafe and default app configs and the default app's mobile menu entry.
- Remove `/users` and `/api/users` immediately. No redirect, protected alias, deprecation period, or other backward-compatibility behavior is required, and there are no known external API consumers.
- Keep the current per-page `AppLayout` behavior. Do not introduce a shared `/backoffice` layout, navigation shell, or breadcrumbs in this task; every page and API continues to enforce its own policy.

## Definition of Success

- Backoffice operators use the new namespaced page and API without losing any current user-management capability.
- Repository-owned navigation and callers use only the namespaced routes, while the removed legacy page and API no longer resolve.
- No ordinary user or cross-app request gains access through the migration.

## Additional Context

- The existing page policy uses `page:users`, session, role `backoffice`, and `users:list`.
- The existing API uses `api:users`, session, role `backoffice`, and operation-specific user grants.
- The public URL `/backoffice/users` should still live under the invisible `(app)` route group.
- OE92 is the decision source for adopting `/backoffice` and `/api/backoffice` as management namespaces.

## Assumptions

- This is a route and organization migration, not a redesign of the users grid or details panel.
- Feature names remain `page:users` and `api:users` because availability is based on the capability, not the URL prefix.
- The migration should be independently deployable after the backoffice namespace convention is accepted.
- Repository-owned callers are the complete migration inventory; no external `/api/users` consumers are known.

## Constraints

- Authenticated pages remain client components using `AppLayout` and browser-side same-origin fetches.
- Route organization never replaces server-side feature/session/app/role/grant enforcement.
- Do not weaken `users:list`, `users:edit`, or `users:delete` boundaries.
- Do not combine the separate `users:edit` authorization repair into this routing task.
- Do not add a shared backoffice layout, navigation shell, or breadcrumbs.
- Use absolute `@/` imports and run `npm run qa`.

## Acceptance Criteria

- [x] The user-administration page is available at `/backoffice/users` under `src/app/(app)/backoffice/users/`.
- [x] User-management handlers are available under `/api/backoffice/users`.
- [x] Page and API preserve explicit `page:users`/`api:users`, session, current-app, `backoffice`, and exact-grant policies.
- [x] List, details, edit, refresh, and account-erasure/delete workflows use the new API URLs and retain their current behavior.
- [x] Every existing AppConfig user-management menu entry uses `/backoffice/users`, including LingoCafe's desktop/bottom entry and the default app's desktop/top and mobile entries.
- [x] All other repository-owned links and callers use `/backoffice/users` or `/api/backoffice/users` as appropriate.
- [x] The legacy `/users` page is removed and does not redirect or provide a compatibility route.
- [x] The legacy `/api/users` endpoint is removed and does not provide an alias or deprecation route.
- [x] Cross-app and unauthorized requests still fail closed with the platform's established response semantics.
- [x] Route and policy tests cover the new page/API locations and verify that the removed legacy routes do not resolve.
- [x] Backoffice routing documentation lists the user-management surface.
- [x] `npm run qa` passes.

## Dos

- Inventory every `/users` and `/api/users` reference before moving files.
- Keep page/API policies explicit after the move.
- Remove the old route files after every repository-owned caller and menu entry is updated.

## Don'ts

- Do not redesign user administration while moving it.
- Do not infer authorization from the `/backoffice` prefix.
- Do not silently leave stale menu or fetch URLs.
- Do not add legacy redirects or API aliases.
- Do not repair unrelated grant assignments in this task.
