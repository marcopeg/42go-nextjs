# Investigate and restore user editing in backoffice details

## Elevator's Pitch

Investigate why the Edit control is no longer available when an administrator opens a user record in Backoffice, then restore the authorized edit workflow without weakening user-management access controls.

## Business Gain

- Backoffice operators can again maintain user accounts from the user-details view.
- The application makes the distinction between view-only and edit-capable operators reliable and visible.

## Current State

- In the affected production database, the LingoCafe `backoffice` role was missing the dedicated `users:edit` grant, so the client policy intentionally hid Edit while user listing remained available.
- The production grant mapping has been fixed externally. The task required no application code change.
- Completed task YS05 established `users:edit` as the required exact grant for PATCH operations and intentionally hides edit controls for operators without that grant.

## Desired State

- Determine, with evidence, why the edit capability is absent for the affected administrator context.
- Restore an Edit action and the supported user-update workflow in the details view for authenticated, current-app backoffice operators who hold `users:edit`.
- Keep the control absent for unauthorized or view-only operators, and retain authoritative server-side PATCH enforcement.

## Definition of Success

- An edit-capable administrator can open a user, enter edit mode, save supported changes, and see the updated data.
- The regression cause and the repair are documented in the task execution notes.
- List-only, cross-app, unauthenticated, and non-backoffice users cannot reveal or perform edits.

## Additional Context

- User administration lives at `/backoffice/users` with handlers at `/api/backoffice/users`.
- The affected surface is LingoCafe user management.
- The operation grants are `users:list` for viewing, `users:edit` for PATCH updates and profile/consent resets, and `users:delete` for erasure.
- Relevant completed work: YS05 (authorization boundary) and LG69 (backoffice route migration).
- The intended audience is LingoCafe users with backoffice access, whose role configuration must include `users:edit`.
- Investigation on 2026-08-10 verified that the current local/test LingoCafe environment has the dedicated `users:edit` grant, assigns it to `backoffice`, and renders Edit after a fresh admin login. The production database was subsequently confirmed to lack that mapping and was fixed externally. See `RX01.notes.md`.

## Assumptions

- The expected capability is the existing supported user edit workflow, not an expansion of editable fields or a redesign.
- LingoCafe backoffice access is intended to include user-edit capability unless the investigation establishes a deliberate, documented split between view-only and edit-capable backoffice roles.

## Constraints

- Do not weaken feature, session, app-scope, backoffice-role, or exact-grant checks.
- Do not expose editing to operators who have only `users:list`.
- Do not reintroduce legacy `/users` or `/api/users` routes.
- Use the shared policy components for client-side visibility and keep server-side PATCH authorization authoritative.
- Run focused user-administration tests and `npm run qa`.

## Acceptance Criteria

- [x] The investigation records the verified cause of the missing Edit capability, including the affected policy/session/UI path.
- [x] A current-app backoffice operator with `users:edit` sees an Edit action after opening a user record; the missing production grant mapping has been fixed externally.
- [x] A list-only, unauthenticated, wrong-app, or non-backoffice actor cannot see or successfully invoke user updates.
- [x] Server-side `PATCH /api/backoffice/users` still requires exact `users:edit` and rejects unauthorized requests without writing data.
- [x] Automated tests cover the authorization boundary and relevant denial cases.
- [x] No source changes were made, so a full QA build was not required for this database-only repair.

## Dos

- Trace the rendered details UI, client policy evaluation, session grant data, and PATCH endpoint before selecting a fix.
- Verify the behavior in the affected app and role, including a fresh authenticated session after any grant-provisioning fix.
- Keep the repair narrow and document the regression cause.

## Don'ts

- Do not bypass `ProtectComponent` or treat `users:list` as edit permission.
- Do not grant `users:edit` broadly just to make the button appear.
- Do not fold unrelated user-management redesign or account-erasure changes into this task.
