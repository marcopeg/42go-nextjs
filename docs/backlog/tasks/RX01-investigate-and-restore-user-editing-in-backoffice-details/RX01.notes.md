# Execution Notes — Investigate and restore user editing in backoffice details

**Task**: ./RX01.task.md
**Plan**: ./RX01.plan.md

## Decisions

- Investigation only. No application code, configuration, database data, role/grant mapping, or user record was changed.
- Preserve the exact `users:edit` boundary. The missing control must not be restored by treating `users:list` or general backoffice membership as edit permission.

## Findings

### Authorization and UI path

- `src/app/(app)/backoffice/users/page.tsx` declares `editUsersPolicy` with exact `users:edit` and wraps both the user-details **Edit** button and the actions-menu **Edit user** item in `EditUsersOnly` / `ProtectComponent`.
- The component deliberately renders nothing while the client session lacks that grant or authorization is unresolved. This explains why a backoffice user can open the users page yet not see Edit.
- `PATCH /api/backoffice/users` independently requires feature `api:users`, an authenticated current-app user, role `backoffice`, and exact `users:edit`. The server remains authoritative.
- The client-side policy reads `session.user.grants`; JWT/session callbacks populate it from the app-scoped role/grant mapping. A changed mapping requires an updated session (sign out and sign back in) before the button can appear client-side.

### LingoCafe configuration and local data

- The LingoCafe test-user seed explicitly creates `users:edit` and assigns it to the LingoCafe `backoffice` role alongside `users:list` and `users:delete`.
- A read-only query against the active local database confirmed the same three user-management grants are currently assigned to `lingocafe | backoffice`; user `admin` is assigned that role.
- `npm run test:backoffice-users-routes` passed: 7 tests, 0 failures. Its coverage verifies the separate list/edit/delete policies and seed provisioning.

### Browser verification

- On 2026-08-10, a fresh login to `https://lc42go.ngrok.app/` with the documented LingoCafe admin test account reached `/backoffice/users`.
- The Users menu was visible. For John Doe, the actions menu showed **Edit user**, and the opened details panel showed **Edit**. No edit form was opened and no user data was changed.

## Diagnosis

The reported symptom was caused by the production database missing the `users:edit` mapping for the LingoCafe `backoffice` role. `ProtectComponent` correctly hid Edit because the active session did not include that exact grant. This was a production authorization-data drift issue, not a code or UI regression.

The production mapping has been fixed externally. No application code, configuration, or local database data was changed in this task.

The existing YS05 operator SQL script (`../YS05-enforce-users-edit-for-user-updates/YS05.provision-users-edit.sql`) remains the documented idempotent provisioning approach for this grant in existing environments; it was not run by this task.

## Problems Encountered

- The initially open browser session was a normal user at profile onboarding, so it could not test Backoffice. The session was replaced with the repository-documented LingoCafe admin test account.
- The production mapping was confirmed and fixed by the operator after the local/test investigation; this task did not directly connect to or mutate the production database.
