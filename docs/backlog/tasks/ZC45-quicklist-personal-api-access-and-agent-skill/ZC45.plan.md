# Plan — QuickList Personal API Access and Agent Skill

## Goal

Deliver opt-in, token-authenticated QuickList automation with owner-controlled per-list exposure and a reusable Codex skill that safely configures credentials and manages lists/items with the same permissions as the represented user.

## Milestones

### Milestone 1 — Persist and authenticate personal API access

- [x] Step 1 — Add QuickList token and list-exposure persistence
  - Achieve: Store one hashed token per app-scoped QuickList user and an explicit API-enabled flag per list.
  - Create: A forward-only Knex migration for `quicklist.api_tokens` and the project exposure field.
  - Modify: None.
  - Delete: None.
  - Touch points: PostgreSQL schema, foreign keys, uniqueness, lifecycle timestamps, safe rollback.
  - Validation: Migration structure review plus targeted unit coverage for defaults and token primitives.
  - Notes: UI-created lists remain disabled by the database default; v1 API creation explicitly enables them.

- [x] Step 2 — Build server-only token and access helpers
  - Achieve: Generate high-entropy tokens, store/compare SHA-256 hashes safely, parse bearer headers, update last-used metadata, and centralize owner/collaborator/list-exposure predicates.
  - Create: QuickList server modules for token lifecycle, token authentication, response helpers, and access checks.
  - Modify: Existing QuickList server utilities only where sharing a stable helper reduces drift.
  - Delete: None.
  - Touch points: Node crypto, constant-time comparison, app scoping, 401/404 semantics, list visibility.
  - Validation: Node tests for generation/hash/parse and pure authorization/list-resolution decisions.
  - Notes: Never log or return token hashes; the raw token exists only in create/rotate responses.

### Milestone 2 — Add account and owner-only list controls

- [x] Step 3 — Add session-authenticated token lifecycle endpoints
  - Achieve: Let the signed-in QuickList user inspect token status, create, rotate, and delete their one active token.
  - Create: Dedicated QuickList API-access management route(s).
  - Modify: QuickList feature/config wiring if needed.
  - Delete: None.
  - Touch points: NextAuth session, app ID resolution, no-store responses, idempotent status reads.
  - Validation: Route/build coverage and token lifecycle tests.
  - Notes: Create/rotate returns the raw token once; status returns only safe metadata.

- [x] Step 4 — Add profile token controls and one-time disclosure modal
  - Achieve: Show Create API token with explanatory copy when absent, then a masked active state, Rotate, and confirmed Disable when present, without a redundant account-level switch.
  - Create: App-owned QuickList API-access profile component.
  - Modify: QuickList profile configuration.
  - Delete: None.
  - Touch points: Shared `Modal`, semantic buttons, copy flow, loading/error/disabled states, mobile layout.
  - Validation: Type/build checks and browser verification at mobile and desktop widths.
  - Notes: Disable confirmation states that the token will be deleted; token disclosure cannot be reopened. The disclosure uses a single header action that progresses from Copy token to Done, and the token surface itself also copies.

- [x] Step 5 — Add owner-only list exposure control
  - Achieve: Let only the owner view/change the list-wide API-enabled switch from the signed-in list settings UI.
  - Create: Session-authenticated owner-only exposure endpoint or focused handler.
  - Modify: QuickList info response and settings page.
  - Delete: None.
  - Touch points: Owner visibility, inline amber warning when account token is absent, persistence independent from account token lifecycle.
  - Validation: Owner/collaborator route tests and browser verification.
  - Notes: Collaborators never receive the flag; token-authenticated APIs never read or mutate it as a setting.
