# Plan — Add the LingoCafe Questionnaire Content and Learner-State Schema

## Goal

Add a standalone, reader-owned PostgreSQL contract that imports the standard
book questionnaire package without touching learner history, preserves the
exact question revision shown in every round, and stores concept-level FSRS-6
state and review evidence for adaptive services to use later.

## Milestones

### Milestone 1 — Define the standalone relational contract

- [x] Step 1 — Specify ownership, identity, and lifecycle rules
  - Achieve: Document the boundary between books-owned source packages,
    publisher-owned reader content, and runtime-owned learner history.
  - Create: `docs/lingocafe/QUESTIONNAIRES_DATA_MODEL.md`.
  - Modify: Nothing else in this step.
  - Delete: Nothing.
  - Touch points:
    - `docs/lingocafe/BOOKS_DATA_MODEL.md`
    - books CM87 questionnaire contract

  - Validation:
    - one questionnaire is bound to exactly one reader book;
    - publisher scope is surgical by included book and never writes learner

    - omission does not delete a book or its questionnaire;

    - stable questionnaire, learning-item, and question IDs are distinguished

  - Notes: The document must be sufficient for a separate exporter to generate

  - Achieve: Define rounds, rendered items, answer selections, concept review

  - Modify: Nothing outside the document.

  - Touch points: FSRS-6 D/S/R model and its four grades.
  - Validation:
    - version one defaults to ten requested questions but stores any positive
      round size;

      1–4 rating is retained;
    - memory state is scoped to user, questionnaire, and learning item;
    - each review records scheduler/version/parameter identity so state can be
      audited or replayed;
    - mode and selection-policy identifiers are open strings, not a closed
      version-one enum.
  - Notes: Store stability and difficulty; calculate retrievability from state
    and elapsed time rather than treating it as durable truth.

### Milestone 3 — Add learner-owned rounds, answers, and FSRS state

- [x] Step 5 — Create generic round and rendered-item history
  - Achieve: Store each round's user, mode, selection-policy version, requested
    size, actual size, lifecycle timestamps, and score, plus the ordered exact
    question revision and answer set rendered at each position.
  - Create: Round and round-item tables in the migration.
  - Modify: The new migration only.
  - Delete: Nothing.
  - Touch points: Auth users and immutable question revisions.
  - Validation:
    - requested size is positive and defaults to 10 without a hard maximum;

    - completed/abandoned timestamps obey round lifecycle constraints;
    - a round item cannot reference an answer set from another revision.
  - Notes: The schema supports future practice modes without adding nullable
    mode-specific columns.

- [x] Step 6 — Create immutable answers, selections, and concept review logs
  - Achieve: Log one answer per rendered item, every selected option, correctness,
    duration, applied FSRS grade, and one scheduler review event per affected
    learning item.
  - Create: Answer, selected-option, and learning-item review-log tables.
  - Modify: The new migration only.
  - Delete: Nothing.
  - Touch points: Round items, exact answer options, and learning-item relations.
  - Validation:
    - selected options must belong to the exact answer set rendered;
    - grade is constrained to 1–4, while version-one binary policy is documented
      as 1/3;
    - answer/review rows are append-only historical evidence;
    - one round item produces at most one review event for each linked learning
      item;
    - indexes support user history, book/question history, and recent rounds.
  - Notes: The service task owns transactional grading; this card owns the
    integrity-safe storage contract.

- [x] Step 7 — Create current FSRS-6 learning-item state
  - Achieve: Store the latest concept-level memory state independently from the
    immutable review log.
  - Create: Per-user/per-questionnaire/per-learning-item memory-state table.
  - Modify: The new migration only.
  - Delete: Nothing.
  - Touch points: Auth users, learning items, and review logs.
  - Validation:
    - state stores scheduler name/version, parameter-set ID and digest, desired
      retention, card state, difficulty, stability, due time, last review time,
      scheduled/elapsed days, repetitions, and lapses;
    - desired retention accepts `(0, 1]` and defaults to `0.90`;
    - difficulty is null for new state or within `[1, 10]`, stability is null
      for new state or positive, and all counters are nonnegative;
    - due and user indexes support efficient adaptive candidate selection.
  - Notes: FSRS-6 currently uses 21 parameters and computes retrievability from
    elapsed time and stability; parameter values remain versioned data rather
    than hard-coded schema columns.
