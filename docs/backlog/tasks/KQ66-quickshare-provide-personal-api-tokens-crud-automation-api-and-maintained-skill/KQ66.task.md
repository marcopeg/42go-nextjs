# QuickShare: Establish personal API token lifecycle and authentication boundary

## Elevator's Pitch

Give each QuickShare account a secure, revocable personal bearer token and reusable authentication boundary for the later automation API.

## Business Gain

QuickShare gains a safe automation credential lifecycle without exposing browser sessions, reusable plaintext secrets, or cross-app identity.

## Current State

QuickShare has no bearer-token model, token management UI, or reusable token-authentication context.

## Desired State

QuickShare offers personal API tokens patterned after the proven QuickList design: create, identify, rotate, revoke/disable, and safely display approved metadata while storing only a secure token representation. A dedicated QuickShare table binds one active credential to the app-scoped user. A reusable server-only authentication context parses bearer headers, verifies the token safely, resolves the correct QuickShare app/account, updates approved lifecycle metadata, and provides the identity boundary consumed by ZA41. Browser token-management routes remain session-authenticated and separate from bearer automation routes.

## Definition of Success

An authenticated QuickShare user can create, copy once, inspect safely, rotate, and disable a personal token. Valid tokens resolve only their own app-scoped QuickShare account; missing, malformed, rotated, revoked, or foreign-app tokens fail closed immediately.

## Additional Context

Generate high-entropy personal tokens and display the raw value only in the direct create or rotate response. Persist only a deterministic hash or equivalently safe representation plus approved non-secret metadata such as a recognition prefix, creation/update time, and last-used time. Compare token material safely, never log Authorization values, and use HTTPS in deployed environments. Token existence is the account-level API-access state; disabling access deletes or revokes the credential without changing resource data.

Reuse the established QuickList security pattern where it fits, but keep storage in the QuickShare schema and identity app-scoped. KQ66 stops at credential lifecycle and reusable authentication context. ZA41 owns resource operations and live discovery. VG23 owns credential configuration outside the app, the maintained skill, and deterministic client.

## Assumptions

- One active personal token per QuickShare app-scoped user is sufficient for version one.
- A high-entropy bearer token can use deterministic hash-only storage and constant-time verification without password-style slow hashing.

## Constraints

Depend on XO00 account and schema isolation. Tokens are not viewer credentials and grant no public-origin authority by themselves. Do not implement resource CRUD, capability discovery, or the agent skill in this task. Do not store raw reusable bearer secrets, expose hashes through profile data, authenticate bearer routes with NextAuth cookies, log credentials, or permit cross-app identity. Preserve QuickNotes and QuickList behavior.

## Acceptance Criteria

- Session-authenticated account UI supports personal-token creation, approved metadata/status reading, rotation, and disable/revocation.
- Creation and rotation return the raw high-entropy token exactly once through a deliberate copy-and-store disclosure; later reads never recover it.
- The QuickShare schema stores the app-scoped user association, token hash or equivalent safe representation, recognition prefix, and approved lifecycle metadata, never reusable plaintext.
- Rotation and disable invalidate the previous token immediately.
- A reusable server-only bearer-authentication context rejects missing, malformed, unknown, rotated, revoked, and foreign-app tokens without leaking account details.
- Successful authentication derives the correct QuickShare app and account from verified token data; callers cannot select ownership.
- Token hashes, raw tokens, and Authorization headers never appear in ordinary profile payloads, logs, analytics, errors, screenshots, or tracked files.
- Browser token-management routes remain session-authenticated and separate from the bearer automation namespace consumed by ZA41.
- Automated tests cover generation entropy/format, one-time disclosure, hash-only persistence, safe comparison, rotation, immediate revocation, and app/account isolation.
- `npm run qa` passes.

## Dos

- Reuse or extract the proven QuickList token primitives where that preserves app isolation and avoids duplicated security logic.
- Keep credential lifecycle and bearer identity resolution centralized for ZA41.

## Don'ts

- Do not add resource CRUD, discovery, plugin packaging, or skill behavior to KQ66.
- Do not store or log reusable raw bearer tokens.

## Open Questions

None that blocks this milestone; exact token prefix, table names, and module decomposition belong to implementation planning. Multiple named tokens, fine-grained scopes, and mandatory rate limiting are deferred.
