# QuickShare: Provide personal API tokens, CRUD automation API, and maintained skill

## Elevator's Pitch

Give QuickShare accounts secure personal automation credentials and a maintained skill for durable draft and publish workflows.

## Business Gain

Users and agents can automate creation, editing, saving, and explicit publishing without browser-session coupling.

## Current State

QuickShare has no bearer-token model, token management UI, automation API, or QuickShare agent skill.

## Desired State

QuickShare offers personal API tokens patterned after QuickList: create, identify, revoke, and safely display token metadata while storing only secure token representations. Token-authenticated CRUD APIs operate on the token owner’s QuickShare resource space and expose explicit save and publish actions for plain text, Markdown, advanced pages, and template instances. A maintained QuickShare skill documents and uses the supported API safely.

## Definition of Success

A token owner can automate resource draft CRUD and explicit publishing, while revoked or foreign tokens cannot access account data.

## Additional Context

The API is the automation face of the same domain services used by the UI. It returns stable public URLs and publication/version metadata but never treats filesystem paths as editable state. Template automation selects a registered template ID/version and submits schema-validated configuration; it cannot upload executable code through a guided template contract.

## Assumptions

- One owner-scoped API vocabulary can cover all resource kinds while retaining kind-specific validated draft payloads.
- Publish responses can report the immutable release version and stable public URL without exposing deployment internals.

## Constraints

Depend on the core resource and publication contracts. Tokens are not viewer credentials and grant no public-origin authority. Derive owner scope from verified token data. Keep the QuickShare skill separate from the existing QuickList skill and preserve QuickNotes unchanged.

## Acceptance Criteria

- Account UI supports personal token creation, metadata listing, one-time secret display, and revocation.
- Tokens are stored and verified using QuickList-comparable secure patterns, never as recoverable plaintext.
- Token APIs support account-scoped resource CRUD, repeated draft saves, explicit publish, and clear validation/error responses.
- CRUD and publish contracts cover plain text, Markdown, advanced web pages with managed assets, and registered template instances without bypassing kind-specific validation.
- Token scope cannot cross accounts or apps and revocation takes effect immediately.
- The maintained QuickShare automation skill covers authentication, resource operations, save/publish semantics, and error handling.
- API authorization, revocation, skill smoke checks, and QA pass.

## Dos

- Reuse domain authorization, validation, compiler, and publisher services shared with the editor UI.
- Keep the skill synchronized with API examples and supported resource kinds.

## Don'ts

- Do not let bearer clients choose owner IDs, raw output paths, Nginx paths, or publication pointers.
- Do not turn template configuration into an arbitrary code-execution API.

## Open Questions

None that blocks the core API; any later fine-grained token scopes should be added deliberately rather than inferred here.
