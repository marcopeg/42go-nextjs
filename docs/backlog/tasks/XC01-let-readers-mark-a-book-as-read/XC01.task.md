# Let readers mark a book as read

## Elevator's Pitch

Let an authenticated reader explicitly mark a LingoCafe book as read from a convenient point in the reading journey. Candidate entry points are a three-dot contextual menu on the book cover in `/books`, a completion action at the end of the book's last page, and a dedicated action on `/books/[bookId]`. The final task may use one or more of these surfaces after refinement.

## Business Gain

Readers can close the loop on a finished book, keep their shelf state meaningful, and distinguish completed books from books that are merely in progress. This also creates a reliable completion signal for future reading history, recommendations, and engagement features.

## Current State

LingoCafe persists one `lingocafe.books_progress` row per user and book. The table already includes a nullable `completed_at` timestamp, but the current reader, book-details page, and bookshelf do not expose a confirmed user action for marking a book as read. Existing bookshelf behavior derives `Currently Reading` from `readingAction.kind === "resume"`, so completion must be integrated without leaving a completed book presented as actively reading.

## Desired State

An authenticated reader can deliberately mark a book as read through an accessible UI action placed at one or more of the proposed surfaces: the book-card contextual menu, the end of the final reader page, or the book information page. The server records completion for the current user and book using the existing progress model where appropriate. After success, all affected surfaces consistently represent the book as read rather than currently reading, provide clear feedback, and avoid stale actions or navigation state.

## Definition of Success

A reader can mark a book as read without manipulating reading progress manually, the completion is persisted for the authenticated user, and reloading the bookshelf, details page, or reader produces a consistent completed state.

## Additional Context

Operator request: add the possibility to flag a book as `read`, either from a three-dot contextual menu on the cover in the list, a button at the end of the last page, or a specific button on the book information page. The schema already provides `lingocafe.books_progress.completed_at`; refinement should decide which proposed entry points ship and how completed books appear on the shelf.

## Assumptions

- `lingocafe.books_progress.completed_at` is the intended persistence signal unless implementation review finds a stronger existing model.
- Completion is scoped to the authenticated user and selected book.
- Marking a book as read is an explicit user action; merely opening or scrolling the last page does not automatically complete it.
- A completed book should no longer qualify for the existing `Currently Reading` section.
- Whether the action can be undone or changed back to unread remains open for refinement.

## Constraints

- Validate the book and authenticated user on the server; never accept an arbitrary user ID from the client.
- Keep the completion state consistent across `/books`, `/books/[bookId]`, and `/books/[bookId]/[pageId]`.
- Preserve existing start, resume, progress-saving, and navigation behavior for books that are not completed.
- If the bookshelf uses a three-dot trigger, it must be keyboard accessible and must not hijack the cover's existing navigation click.
- Do not broaden this task into a general bookshelf redesign or reading-history feature.
- Run `npm run qa` after implementation.

## Acceptance Criteria

- [ ] An authenticated reader can mark a selected book as read from the entry point or entry points accepted during refinement.
- [ ] The completion mutation is authorized server-side and applies only to the authenticated user's progress for that book.
- [ ] Marking a book as read persists a reliable completion state, using `books_progress.completed_at` unless refinement establishes a different canonical signal.
- [ ] The action handles a book with no existing progress row without producing inconsistent or invalid progress data.
- [ ] The UI gives clear success feedback and prevents accidental duplicate submissions while the mutation is pending.
- [ ] After completion, refreshed bookshelf, book-details, and reader payloads agree that the book is read.
- [ ] A completed book is not shown as `Currently Reading` merely because a progress row exists.
- [ ] Existing reading links do not become broken when a book is marked as read.
- [ ] Any contextual-menu action is accessible by keyboard and does not trigger the underlying book-card navigation.
- [ ] Any final-page action appears only when the reader is on the actual last page of the book.
- [ ] Loading, error, and retry behavior are clear and do not falsely show a book as completed.
- [ ] `npm run qa` passes after implementation.

## Dos

- Reuse the existing authenticated LingoCafe book and progress API patterns.
- Return canonical completion state from the API instead of deriving it independently on each client surface.
- Make the action label and resulting state understandable to assistive technology.
- Resolve how completed books interact with the current shelf sections and reading actions during refinement.

## Don'ts

- Do not infer completion solely from reaching a scroll threshold.
- Do not trust client-provided ownership or user identity.
- Do not leave completed books classified as actively reading.
- Do not implement unrelated ratings, reviews, achievements, or recommendation logic in this task.

## Open Questions

- Which proposed surfaces should ship: book-card context menu, final-page button, book-details button, or all three?
- Should readers be able to undo completion or mark a book unread?
- Where should completed books appear on `/books`, and what visual read indicator should they use?
- After completion, should the primary book-details action allow rereading from the start, resuming at the end, or both?
- If no progress row exists, which page should be stored when a user marks the book as read outside the reader?
- Should marking the last page as read also force `progress_bps` to 10000, or should completion remain independent from scroll progress?
