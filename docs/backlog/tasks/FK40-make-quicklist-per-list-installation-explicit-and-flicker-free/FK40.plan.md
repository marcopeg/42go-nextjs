# Plan — Make QuickList Per-List Installation Explicit and Flicker-Free

## Goal

Make normal QuickList navigation a seamless client-side experience while retaining a deliberate, authorized document boundary for installing one list as its own virtual PWA.

## Milestones

### Milestone 1 — Separate manifest identity from ordinary navigation

- [x] Step 1 — Restrict the QuickList target declaration to the installer route
  - Achieve: Resolve the per-list install target only for `/quicklists/:projectId/install`; the index, list detail, list settings, and ordinary refreshes resolve the base QuickList target.
  - Create: None.
  - Modify: `src/config/quicklist/config.ts` and any focused target-path tests.
  - Delete: None.
  - Touch points: QuickList PWA declaration, path-pattern matching, server-side target resolution.
  - Validation: Prove that the installer pathname resolves the authorized list manifest while `/quicklists/:projectId` and `/quicklists/:projectId/info` resolve the base manifest.
  - Notes: Keep the existing server-only resolver unchanged as the authority for access checks, immutable target ID, list name, and launch URL.

- [x] Step 2 — Freeze the document’s initially rendered manifest link
  - Achieve: Render the manifest selected on the initial server document for the document lifetime. Client-side pathname changes must neither replace it with a different PWA identity nor reload the page.
  - Create: None.
  - Modify: `src/42go/pwa/ManifestLink.tsx`, `src/42go/pwa/HeadTags.tsx`, and `tests/pwa-install-targets.test.mts`.
  - Delete: `src/42go/pwa/document-identity.ts` and its obsolete reload-specific test coverage, if no other consumer remains.
  - Touch points: Root PWA head output, private manifest credentials, Next.js route transitions.
  - Validation: Cover the fixed manifest-link behavior and assert that no client code invokes `window.location.reload()` for a manifest transition; run `npm run test:pwa-install-targets`.
  - Notes: Do not attempt to update an installed PWA’s identity by changing `<link rel="manifest">` after hydration. Ordinary visual metadata may remain independently reactive where needed.

### Milestone 2 — Build the explicit per-list installer journey

- [x] Step 3 — Add the authenticated installer page
  - Achieve: Provide `/quicklists/:projectId/install` as a list-specific installation document with the list title, concise explanation, native install action/instructions, and a normal return path to `/quicklists/:projectId/info`.
  - Create: `src/app/(app)/quicklists/[id]/install/page.tsx` and any small installer presentation component needed to keep page logic focused.
  - Modify: Existing QuickList data hook/component only if the installer needs a minimal, authorized title-loading path.
  - Delete: None.
  - Touch points: `AppLayout`, list-access API behavior, `InstallAppAction`, `usePWAInstall`, PWA launch-target marker handling.
  - Validation: An accessible list can load its installer document and display the list-derived app name; a missing, revoked, or unauthorized list does not obtain a usable list target manifest or installation action.
  - Notes: Follow the protected app-page convention: client component, `AppLayout`, same-origin browser fetches, and feature/session policy. Let the existing resolver enforce manifest authorization server-side.

- [x] Step 4 — Make installation an intentional document navigation from settings
  - Achieve: Add an **Install this list** entry to the existing list settings page that performs a real document navigation to the installer route, rather than a Next.js client-side transition.
  - Create: None.
  - Modify: `src/app/(app)/quicklists/[id]/info/page.tsx` and any shared settings presentation components it uses.
  - Delete: None.
  - Touch points: List settings actions, navigation semantics, mobile/desktop settings layout.
  - Validation: Opening a list or returning to its settings remains client-side; choosing **Install this list** creates the one deliberate new document where the list manifest is server-rendered.
  - Notes: Use a deliberate native-anchor/document-navigation mechanism for this action. Do not route through `router.push()` or `next/link`, because the initial-document manifest boundary is required for a distinct install identity.

### Milestone 3 — Prove behavior and hand off device validation

- [x] Step 5 — Add regression coverage and run project gates
  - Achieve: Protect the base-versus-installer manifest selection, the no-reload client behavior, target authorization fallbacks, and installer route rendering as far as the project’s automated test surface permits.
  - Create: Focused test cases in `tests/pwa-install-targets.test.mts`; add a route/UI test only if the existing test infrastructure supports it without introducing a new test stack.
  - Modify: Existing PWA tests and any route fixtures required for the selected coverage.
  - Delete: Obsolete reload assertions.
  - Touch points: Manifest route, path-pattern tests, PWA install context helpers.
  - Validation: Run `npm run test:pwa-install-targets` and `npm run qa`.
  - Notes: Preserve existing manifest validation, same-origin launch URL checks, and private-manifest credential behavior.

- [ ] Step 6 — Execute focused browser and device acceptance checks
  - Achieve: Confirm the index/detail/settings route transitions no longer flash, and prepare the operator’s physical installation checks.
  - Create: Brief task notes recording automated/browser results and the exact iPhone/Android manual test checklist.
  - Modify: None unless verification uncovers an implementation defect.
  - Delete: None.
  - Touch points: QL42Go test tunnel, a list with valid user access, installed-list launch behavior.
  - Validation: Browser check of ordinary navigation and installer-document transition; operator manually installs and launches a list on iPhone and Android, verifies the title/launch route, and confirms normal in-app navigation remains smooth.
  - Notes: Automated mobile/desktop browser checks passed. Native install sheets cannot be fully automated or reliably detected on every platform; the operator's iPhone and Android installation/launch checks remain pending.
