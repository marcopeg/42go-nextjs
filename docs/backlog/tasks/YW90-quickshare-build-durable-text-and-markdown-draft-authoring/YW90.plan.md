# Plan — QuickShare: Build durable text and Markdown draft authoring

## Goal

Deliver the shared QuickShare library/editor lifecycle and safe plain-text and Markdown compilers, including the first real account-to-Nginx publication proof.

## Milestones

### Milestone 1 — Build shared authoring APIs and resource library

- [x] Step 1 — Add owner-scoped session APIs for drafts and lifecycle actions
  - Achieve: List, create, read, save, publish, unpublish, and delete only the authenticated account's resources through shared domain services.
  - Create: Protected QuickShare session routes, request/response schemas, serialization, conflict/error envelopes, and text/Markdown draft adapters.
  - Modify: Resource catalog registration for plain text and Markdown.
  - Delete: Nothing.
  - Touch points: XO00 ownership/state services, IF14 publication/purge services, `protectRoute`, revision control.
  - Validation: API tests cover missing/unknown explicit type, foreign ownership, repeated saves, stale revisions, publish failure, unpublish retention, and purge-before-delete.
  - Notes: Draft mutation never writes delivery files.

- [x] Step 2 — Implement the account library and shared `+ New Share` split button
  - Achieve: Show resource states/URLs and create a selected explicit type from one extensible catalog-driven popover.
  - Create: QuickShare page, library components/hooks, split-button/popover, empty/loading/error states, and responsive navigation integration.
  - Modify: QuickShare and default AppConfigs to expose the delivered page/API features.
  - Delete: Any UI-only resource-type list.
  - Touch points: AppLayout, shared design system, catalog metadata, mobile navigation.
  - Validation: Component/browser checks prove the primary button opens the type popover, plain text/Markdown appear, later registrations need no picker rewrite, and default `john/john` sees only `app_id=default` resources.
  - Notes: Use the shared UI-modal skill during execution for confirmation dialogs.

### Milestone 2 — Deliver durable editors and safe compilers

- [x] Step 3 — Build text and Markdown draft editors
  - Achieve: Create, reopen, edit, save, preview, and configure custom IDs while keeping draft and published state unmistakable.
  - Create: Shared editor container plus text/Markdown presentation and logic modules.
  - Modify: Library routing and URL-state presentation.
  - Delete: Nothing.
  - Touch points: Simple text areas, safe preview, availability checks, optimistic revisions, responsive layout.
  - Validation: Browser tests cover leave/reopen persistence, unsaved/saved preview distinction, content-only URL stability, pending URL switch display, and unpublished candidate labeling.
  - Notes: Display both URLs only while an already-published resource has a pending identifier switch.

- [x] Step 4 — Compile plain text and Markdown into IF14 bundles
  - Achieve: HTML-escape plain text and safely render Markdown at publish time without mutating source.
  - Create: Deterministic text/Markdown compilers, document shell, sanitization policy, and compiler tests.
  - Modify: Resource catalog compiler registrations and publish orchestration.
  - Delete: Nothing.
  - Touch points: IF14 manifest contract, `sanitize-html`/Markdown libraries, content hashes.
  - Validation: XSS and malformed-input tests, deterministic bundle snapshots, source immutability, and rejection before activation on compiler errors.
  - Notes: Preview policy may differ but must never claim to be the current publication.

### Milestone 3 — Complete disruptive lifecycle UX

- [x] Step 5 — Implement confirmations for Unpublish, Delete, and URL changes
  - Achieve: Explain retained drafts on Unpublish, require confirmation on every Delete, and use stronger copy after any publication or for disruptive identifier changes.
  - Create: Shared confirmation models/dialogs and affected-output summaries.
  - Modify: Editor/library lifecycle actions.
  - Delete: Nothing.
  - Touch points: Publication history, purge failures, toast/error reporting, accessibility/focus management.
  - Validation: UI/API tests prove cancel is harmless, published deletion is stronger, purge failure preserves records/state, and successful operations match the required lifecycle.
  - Notes: Never imply redirects or backward compatibility for changed URLs.

### Milestone 4 — Prove first real publication

- [x] Step 6 — Run seeded local and static-origin acceptance
  - Achieve: Use a real default-app seeded account to save, publish, update, switch URL, unpublish, and delete both text and Markdown resources.
  - Create: End-to-end tests and focused npm scripts where useful.
  - Modify: Task notes and environment documentation with the verified flow.
  - Delete: Test delivery artifacts through the real purge path.
  - Touch points: Localhost `john/john`, default app isolation, Nginx origin, mobile and desktop browser checks.
  - Validation: Focused tests, HTTP fetches from Nginx, cookie absence, authorization checks, and `npm run qa` all pass.
  - Notes: This is the first compiler-to-publisher proof and gates QU22.
