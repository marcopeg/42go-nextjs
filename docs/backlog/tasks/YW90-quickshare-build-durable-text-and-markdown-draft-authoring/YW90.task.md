# QuickShare: Build durable text and Markdown draft authoring

## Elevator's Pitch

Give QuickShare accounts a focused editor for durable plain-text and Markdown resources whose drafts remain authoritative until explicit publication.

## Business Gain

Accounts can create, reopen, and repeatedly save content without accidental public deployment.

## Current State

QuickShare has no resource CRUD, account library, or authoring editor.

## Desired State

The shared creation control is a `+ New Share` split button whose popover lists the available resource types. This milestone establishes the picker and its plain-text and Markdown entries so later web-page and template milestones can register their choices without replacing the creation flow.

The shared resource UI includes Publish, Unpublish, and Delete. Unpublish strongly distinguishes the draft retained in the account from the public output being removed. Delete always requires confirmation; a resource that has ever been published requires a stronger disruptive-action confirmation explaining that its public content and account record will be permanently removed.

The authenticated editor provides account-scoped create, list, open, edit, and delete flows for plain text and Markdown resources. Creation assigns the resource's random globally unique short code and previews the final short URL; the author can supply or later set an available custom ID to use the handle-scoped URL instead. Draft source and metadata are saved in the QuickShare database. Publish is an explicit action, not an edit side effect. Plain text is HTML-escaped into a minimal document and Markdown is rendered to final HTML only during publication; the editable source remains unchanged in the database.

The library and editor show one unchanged URL for content-only edits. When a published resource has a pending identifier switch, they show both the still-working `publishedUrl` and candidate `nextPublicUrl` until Publish succeeds. Unpublished resources show the candidate URL as a preview and no published URL.

## Definition of Success

An owner can save a text or Markdown draft repeatedly, leave and reopen it, and only obtain a public update after choosing Publish.

## Additional Context

The picker consumes the same supported-type metadata used by API discovery rather than maintaining a UI-only list.

This is the first authoring milestone after the generic publisher and establishes shared resource-library behavior later reused by advanced pages and guided templates. Preview may render from the current unsaved or saved draft, but it must be visibly distinct from the currently published version. YW90 owns safe plain-text and Markdown compilation into IF14's completed-bundle interface and provides the first real account-to-Nginx end-to-end publication proof.

## Assumptions

- Plain text publishes as a safe minimal HTML page with preserved whitespace rather than as an application-rendered route.
- Markdown rendering uses a documented safe policy and may reference managed sidecar assets in its release bundle.

## Constraints

Depend on XO00 foundation and IF14 generic static publication. Resources do not expire or clean themselves up, but owners may explicitly Unpublish or Delete them through the confirmed lifecycle. Do not implement public rendering, temporary notes, expiry, viewer credentials, or QuickNotes compatibility. Server derives account and app scope; client input never chooses ownership.

## Acceptance Criteria

- Owners can CRUD only their own text and Markdown resource drafts through the editor APIs and UI.
- `+ New Share` behaves as a split button whose popover lists supported creation types, initially including plain text and Markdown, and accepts later registered web-page and template choices from the shared catalog.
- Repeated saves update the database draft source without changing public output.
- Explicit publish intent is represented separately from draft mutation.
- Unpublish removes complete static delivery output through the publisher while preserving the resource and draft in a draft-only state.
- Delete requires confirmation for every resource and stronger disruptive confirmation after any publication; successful deletion removes delivery output before permanently deleting the account record.
- Plain text and Markdown types are explicit and validated; Markdown remains source until publish-time HTML rendering.
- Plain text publication HTML-escapes user content; Markdown publication produces final static HTML without changing stored Markdown source.
- Text and Markdown compilers emit IF14's validated bundle/manifest contract, and an end-to-end test proves a real account publish through atomic activation and Nginx delivery.
- The account library has clear draft/published state, stable internal resource identity, and the resource's current public URL; creation previews the default short URL or an available custom URL.
- URL presentation shows both current and next values only for a pending identifier switch; ordinary content edits retain one URL, unpublished resources label the candidate as not yet public, and successful Publish promotes it atomically.
- Browser, authorization, API, and QA tests pass.

## Dos

- Reuse one account library, editor save contract, and explicit Publish action across resource types.
- Make draft-versus-published state unmistakable.

## Don'ts

- Do not render public content through the QuickShare application.
- Do not couple draft saves to filesystem writes or automatic publication.

## Open Questions

None that blocks this milestone; editor polish can be refined during implementation without changing the storage or publication contract.
