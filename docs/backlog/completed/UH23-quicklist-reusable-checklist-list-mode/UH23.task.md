# QuickList: Reusable checklist list mode

## Elevator's Pitch

Add a per-list mode so QuickList can serve both disposable todo lists and reusable checklists. Chuck Norris checks a packing list twice, then resets it for the next trip.

## Business Gain

Users can reuse recurring lists—such as groceries, travel packing, or opening/closing routines—without recreating their items after every completion cycle.

## Current State

QuickList has one implicit todo behavior. `quicklist.projects` currently stores identity, title, ownership, and timestamps only; `quicklist.tasks` likewise has no extensible JSON fields. Completed tasks are moved below pending tasks in the UI, excluded from drag reordering, and the list detail page offers `Drop completed tasks`, which permanently deletes them through `POST /api/quicklists/:projectId/drop-completed` and re-packs remaining positions.

## Desired State

Add a database migration that gives `quicklist.projects` two non-null JSONB columns with empty-object defaults: `settings` and `metadata`. Add a non-null JSONB `metadata` column with an empty-object default to `quicklist.tasks`; task settings are explicitly out of scope. This is the selected future-proof schema foundation.

Persist the list mode as a validated `settings.mode` value of `todo` or `checklist`, with `todo` as the default for existing and newly created lists. Preserve unknown JSON keys when updating this setting so later features can use the same settings and metadata fields safely.

The list settings UI exposes a tab-style control for `Todo` and `Checklist`, reads the saved mode, and persists mode changes through an authorized API.

Todo mode retains the current behavior, including `Drop completed tasks`. Checklist mode retains every existing task completion and ordering behavior: checked items still follow the current UI ordering by most recently checked, manual ordering is unchanged, and checking or unchecking does not introduce any new ordering rule. Its only behavior change is the bottom bulk action: it does not expose the destructive completed-item removal action and instead offers `Reset checklist`. Reset clears every task's completed state in one authorized, atomic operation, without deleting tasks and without changing their stored `position` values. The reset action is offered only when at least one item is checked and uses clear confirmation wording appropriate to its non-destructive effect.

## Definition of Success

Anyone with edit access to a list can change its persisted `settings.mode` between Todo and Checklist in list settings, reload the page, and see the saved mode reflected. Existing lists and all newly created lists behave as Todo by default. A Todo list still offers and performs completed-task removal exactly as today. A Checklist list never offers completed-task removal; after users check items, `Reset checklist` restores every item to unchecked while retaining every item and its original stored ordering. Changing mode itself retains existing checked state because mode changes only the bottom bulk action. The list and task JSONB fields exist with safe empty-object defaults for future features. Access control, app scoping, cache freshness/ETags, collaborative updates, and error recovery remain correct.

## Additional Context

Relevant implementation surfaces: `knex/migrations/20250815120000_quicklist_schema_and_tables.js`; `src/app/api/quicklists/[projectId]/route.ts` for project read/create/update; `src/lib/quicklists/hooks/useQuicklistData.ts`; `src/app/(app)/quicklists/[id]/page.tsx`; and the list Info page at `src/app/(app)/quicklists/[id]/info/page.tsx`. The current Info page handles collaborators, invitations, leave, and delete, so it is the natural settings surface or host for a dedicated settings section.

The list detail GET response is ETag-backed and should include the mode so clients refresh correctly. Mode-changing and reset endpoints must preserve existing owner-or-collaborator authorization plus `app_id` isolation. Reset should clear both `completed_at` and `completed_by` for every task in the selected list and update project freshness.

Mode changes retain existing checked state; only an explicit Checklist reset clears it.

The implementation agent may run the migration in development. The operator will apply the migration manually in production before deployment; this task does not authorize an agent-run production migration or deployment.

## Assumptions

- Anyone with existing edit access may change mode and reset a checklist.
- A checklist still supports normal item creation, editing, deletion, completion toggling, and ordering; only its completed-item bulk action changes.
- Checklist mode keeps Todo's current checked-item behavior, including ordering checked items by most recently checked; reset never mutates stored positions or deletes/recreates task rows.
- `settings.mode` is the only JSON setting introduced by this task; list metadata and task metadata are schema foundation only and have no UI or API editing requirement in this delivery.

## Constraints

- Add JSONB columns only as specified: list `settings` and `metadata`, plus task `metadata`; do not add task settings.
- Existing database rows and create-list API callers must remain compatible and default to `todo`.
- Do not regress the current completion and ordering behavior in either mode; Checklist changes only the bottom bulk action.
- Use server-side validation and existing policy/access patterns for all writes.
- The agent may run migrations in development only. Production migration execution is manual by the operator before deployment.

## Acceptance Criteria

- A migration adds non-null JSONB `settings` and `metadata` columns with `{}` defaults to `quicklist.projects`, and non-null JSONB `metadata` with a `{}` default to `quicklist.tasks`.
- `settings.mode` is validated as `todo` or `checklist`; existing and new lists default to `todo`, and unsupported mode values are rejected without discarding other settings keys.
- Project/list APIs return the persisted mode from `settings.mode`, and anyone with edit access can update it while preserving unrelated settings data.
- List settings show a tab UI control for Todo and Checklist, including the persisted selection after refresh.
- Todo lists continue to show `Drop completed tasks` when items are completed and retain current deletion behavior.
- Checklist lists do not render or call the drop-completed action; when any item is completed they show `Reset checklist` instead.
- Checklist mode preserves today's completion and checked-item ordering behavior; its only UI behavior difference is replacing the bottom deletion action with reset.
- Reset checklist clears every completion marker in one list without deleting tasks or changing stored task positions.
- Unauthorized, cross-app, invalid-mode, and invalid-list requests fail safely; mode changes and reset are available to users with edit access; relevant automated tests and `npm run qa` pass.
- The migration is applied and verified in development; production migration execution is explicitly left to the operator before deployment.

## Dos

- Keep the mode visible in the canonical project payload used by polling and ETag refreshes.
- Use an atomic server-side bulk update for reset rather than client-side individual task mutations.
- Provide clear confirmation and success/error feedback for reset.
- Use PostgreSQL JSONB defaults and safely merge/preserve settings when changing `settings.mode`.

## Don'ts

- Do not delete checklist items during reset.
- Do not change the existing task ordering behavior or stored positions as a side effect of reset.
- Do not expose `Drop completed tasks` in checklist mode.
- Do not silently introduce unrelated settings storage.
- Do not run migrations or deploy in production as part of this task.
