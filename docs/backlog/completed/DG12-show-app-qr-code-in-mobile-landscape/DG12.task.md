# Show App QR Code in Mobile Landscape

## Elevator's Pitch

Add a configuration-driven QR screen that appears when a phone is flipped horizontally. The screen should show only a centered QR code linking to the current app by default, with an AppConfig override for custom QR destinations.

## Business Gain

Mobile users can quickly open the same app on another device without hunting for the URL, copying links, or fighting small landscape layouts. This is especially useful for app flows that are better continued on desktop or shared to another phone.

## Current State

There is no QR-specific AppConfig section today. The app layout and LingoCafe reader surfaces handle responsive mobile layouts, but flipping a phone to landscape does not trigger a dedicated share/open-on-another-device screen. Existing AppConfig sections include `public`, `auth`, and `app`, but no `qr` configuration exists yet.

## Desired State

Add a top-level AppConfig QR section, shaped for future extension as `qr`. The first supported fields should be `active`, `url`, and `pageURL`. When `qr.active` is enabled and the user is on a phone-sized touch device in landscape orientation, replace the normal page UI with a full-screen QR presentation. This applies to every page for that app, including public landing pages and authenticated app pages. The QR code should be vertically and horizontally centered, and no other app chrome, instructions, cards, or controls should be shown.

The QR destination should resolve in this order:

1. If `qr.url` is configured, use that URL.
2. If `qr.url` is missing and the current full URL matches any regular expression in `qr.pageURL`, use the current full URL.
3. Otherwise, use the current app root URL.

## Definition of Success

Any configured app can opt into the mobile-landscape QR screen through AppConfig. When enabled, rotating a phone horizontally shows a clean, centered QR code for the configured URL, a pageURL-allowed full page URL, or the app root URL. Rotating back to portrait restores the normal app UI.

## Additional Context

The operator requested: "Whenever flipping the phone horizontal, we should display the link to the current app. And the link can be the link to the app as default value, but it can also be customized with a config, main config QR section. So it's QR.active, QR.url, and then we will probably add more into that section. So flipping the phone horizontally, we should only have the QR code with the link in the center, vertically and horizontally centered to the screen."

During refinement, the operator chose a top-level `qr` config instead of `app.qr`.

During refinement, the operator chose to enable `qr.active` first for LingoCafe and Quicklist.

During refinement, the operator chose app root URL as the default QR destination when `qr.url` is not configured. They also requested `qr.pageURL` as a list of regular expressions that allow selected full-page URLs to be shared instead. LingoCafe should use this for book info pages.

During refinement, the operator clarified that the QR screen should trigger on phone-sized touch devices in landscape orientation, but not on tablets. Implementation may combine CSS touch media features with a max-width threshold that catches common iPhone and Android phone landscape sizes while excluding tablets.

During refinement, the operator clarified that the QR landscape behavior should apply to any page for enabled apps, including public pages and landing pages.

## Assumptions

- The QR config belongs at the top level as `qr`.
- `active` defaults to false or absent so existing apps do not change behavior.
- `url` is optional; absent means generate the QR from the current app root URL unless `qr.pageURL` matches the current full URL.
- `pageURL` is optional and contains regular expressions that opt selected pages into full-current-URL QR sharing.
- The first release only needs one QR screen state and does not need text, buttons, copy link, analytics, or per-page QR options.
- The behavior targets phone-sized touch-device landscape, not desktop windows or tablets that happen to be wider than tall.
- LingoCafe and Quicklist are the first apps that should opt into the QR landscape behavior.
- The QR landscape behavior applies to all pages for enabled apps, including public and authenticated pages.

## Constraints

- Preserve existing portrait mobile, tablet, and desktop layouts.
- Tablets must not trigger the QR landscape screen.
- Do not show app navigation, headers, sidebars, cards, helper copy, or unrelated controls in the landscape QR state.
- Keep the QR code centered both vertically and horizontally in the viewport.
- Make the config shape future-friendly so more QR options can be added later without breaking apps.
- Treat `qr.pageURL` patterns as config-owned allowlist patterns, not arbitrary user input.
- Use an established QR generation dependency or a small focused implementation, and avoid ad hoc canvas/string hacks if the codebase already has a reasonable package path.
- Follow authenticated app-page conventions and AppConfig type-safety patterns.
- Do not limit the behavior to authenticated app layouts; public layouts must participate too.
- Run `npm run qa` after implementation.

## Dos

- Do implement this as reusable app-layout behavior driven by AppConfig.
- Do implement this in a shared place that can cover both public and authenticated pages.
- Do keep the first version visually minimal: QR code only, centered on the screen.
- Do default to the app root URL when no custom URL is configured and no `qr.pageURL` pattern matches.
- Do support `qr.pageURL` as an allowlist for pages that should share the current full URL.
- Do make the QR config optional and non-breaking for existing apps.
- Do verify the behavior with a phone landscape viewport and a normal portrait viewport.
- Do use touch-capability detection where practical and a phone-oriented max-width threshold.

## Don'ts

- Don't make this a LingoCafe-only one-off unless implementation proves there is no generic layout hook.
- Don't limit this to authenticated app pages.
- Don't show extra explanatory text or marketing UI in the landscape QR state.
- Don't replace desktop landscape screens with the QR screen.
- Don't replace tablet landscape screens with the QR screen.
- Don't require every app to configure a URL before the feature works.
- Don't make all pages share the full current URL by default.
- Don't create a broad responsive-layout rewrite as part of this task.

## Open Questions

  A: Use top-level `qr`.
- Q: Which app should enable this first: LingoCafe only, all apps, or a test/default app?
  A: Enable it first for LingoCafe and Quicklist.
- Q: Should the default QR URL include the current path, or only the app origin/root URL?
  A: Use the app root URL by default. Add `qr.pageURL` as a regular-expression allowlist for pages that should use the current full URL instead. LingoCafe should use it for book info pages.
- Q: What exact viewport/device heuristic should define "phone horizontal"?
  A: Landscape orientation on a phone-sized touch device. Use touch detection where practical, including CSS media features, plus a max-width threshold that catches common phones but excludes tablets.
- Q: Should public pages also use this behavior, or only authenticated app pages?
  A: Apply it to any page, including public pages and landing pages.
