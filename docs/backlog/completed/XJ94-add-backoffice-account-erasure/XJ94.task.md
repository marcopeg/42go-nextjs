# Add Backoffice Account Erasure

## Elevator's Pitch

Add a destructive account erasure flow to the authenticated `/users` backoffice page. Operators should be able to delete or erase an account from the row actions menu and from the user detail panel. The flow must require the operator to type the user's email exactly, then confirm one more time before the server deletes the account.

## Business Gain

Backoffice operators can satisfy account removal requests without manual database work. The feature reduces support risk by making destructive deletion deliberate, audited by UI friction, and bounded to the current app.

## Current State

The `/users` page lists app-scoped users and supports viewing details, editing user fields, resetting profile, and resetting consent through `/api/users`. The user detail panel already has a Delete button, but it only shows `User deletion not yet implemented`. The row three-dots menu has no delete or erase action. The API route has GET and PATCH only. Database foreign keys are mixed: auth accounts, sessions, RBAC role assignments, and LingoCafe reading progress cascade from `auth.users`, while some Quicklist ownership and authored records use `ON DELETE RESTRICT` or `SET NULL`.

## Desired State

Backoffice users can erase an account from `/users` after a two-step destructive confirmation. The first confirmation requires typing the target user's email exactly. The second confirmation asks for final approval after the typed email matches. On confirmation, a server-side delete endpoint runs an app-aware account erasure pipeline. Core validates the request, starts the transaction, runs registered app cleanup hooks for the resolved app, then deletes the app-scoped `auth.users` record and relies on verified database cascades where they are correct. The implementation must detect and handle non-cascading references through app-owned cleanup hooks instead of failing with a vague database error.

## Definition of Success

An authorized operator can erase an eligible account from `/users`, the target user disappears from the list, related cascading rows are removed by the database, and app-owned data cleanup runs through registered hooks for the resolved app before the final `auth.users` delete.

## Additional Context

The operator suggested first trying to delete the `auth.users` record directly and relying on existing cascades. Current schema inspection shows this is partly viable: auth accounts, sessions, RBAC user-role rows, and LingoCafe reading progress cascade. Quicklist project ownership and authored records include `ON DELETE RESTRICT`, so the implementation must audit and handle those before claiming complete account erasure.

The refined direction is to make account erasure extensible. The core flow should not know every app schema. Instead, app-specific modules such as Quicklist and LingoCafe register server-side cleanup handlers that core runs during the erasure transaction. Historical event rows are not part of account erasure and must stay untouched. A successful admin-initiated account erasure must add a new audit event that records who was deleted without storing the deleted account payload.

## Assumptions

- This is a backoffice/admin operation, not self-service account deletion.
- Account erasure is scoped to the current resolved app ID.
- Exact email retyping is case-sensitive unless refinement decides otherwise.
- Existing event logs remain untouched because they are historical telemetry, not account-owned profile data.
- App-specific cleanup logic belongs in server-only app modules, not in public/client app configuration.
- Optional extension files under each `src/config/<app-id>/` folder are an acceptable expansion mechanic.
- Account deletion requires an explicit destructive `users:delete` grant.
- Operators cannot delete their own account, even with `users:delete`.
- Successful admin account deletion is audit logged as an event.

## Constraints

- Use the existing `/users` client page pattern: client component, browser `fetch`, and `AppLayout` policy.
- Use server-side validation and app-scoped database queries.
- Do not trust the typed confirmation email from the client; the API must load and compare the stored target user email.
- Do not add broad data deletion beyond the requested account scope without an explicit product decision.
- Do not put database cleanup functions directly into the current shared `AppConfig.ts` if that would expose server-only logic to client bundles.
- Do not rely on unconstrained variable-path runtime imports that Next.js may not bundle. Optional app extension files should be loaded through a static or generated server-only registry.

## Proposed Account Erasure Hook Design

Core should expose a server-only account erasure runner, for example under `src/42go/users/account-erasure/`.

Proposed handler shape:

```ts
type AccountErasureHandler = {
  id: string;
  label: string;
  order?: number;
  prepare?: (ctx: AccountErasureContext) => Promise<AccountErasureImpact>;
  erase: (ctx: AccountErasureContext) => Promise<AccountErasureResult>;
};
```

The context should include the current `appId`, the target user row, the acting operator, and the Knex transaction. The runner should:

1. Resolve app ID and target user.
2. Validate exact confirmation email and final confirmation intent.
3. Prevent self-delete unless explicitly allowed.
4. Open a transaction.
5. Run registered handlers for the resolved app in deterministic order.
6. Delete the `auth.users` row.
7. Record an audit event describing the deletion.
8. Return a summary of core and app-owned cleanup results.

Registration should be server-only and app-owned. The preferred expansion mechanic is optional convention files inside app config folders:

- `src/config/quicklist/account-erasure.server.ts`
- `src/config/lingocafe/account-erasure.server.ts`
- `src/42go/users/account-erasure/registry.server.ts`

Each optional `account-erasure.server.ts` file exports handlers for that app. If the file exists, it is included. If it does not exist, the app has no custom cleanup. Because Next.js bundling is static, implementation should use one of these approaches:

- maintain a small server-only registry that statically imports known optional handlers;
- or generate `registry.generated.server.ts` from existing `src/config/*/account-erasure.server.ts` files before build/dev;
- or use an explicit server-only app config layer that imports the optional files.

Quicklist must delete or otherwise resolve Quicklist-owned rows before the core user delete hits `ON DELETE RESTRICT`. For this task, Quicklist erasure includes deleting projects owned by the user and dependent project data such as tasks, collaborators, and invites. LingoCafe must delete user-owned reading state, including current book/chapter progress stored in `lingocafe.books_progress`. Event cleanup must not be registered for this account erasure flow.

Audit event requirement:

- Record one event after successful deletion inside the same transaction or otherwise only after the deletion is known to have succeeded.
- Use the acting operator as the event `user_id`.
- Use the event name `user.deleted`.
- Include only minimal target identity in `data`, for example `targetUserId`, `targetEmail`, and optionally handler result summaries.
- Do not include deleted profile, consent, feature flags, OAuth tokens, passwords, or app-owned deleted payloads.

## Acceptance Criteria

- `/users` row actions include a destructive Delete/Erase account item in the three-dots menu.
- The user detail panel Delete button opens the same destructive confirmation flow.
- The confirmation UI requires the operator to type the target user's email exactly before the final confirmation action is enabled.
- After the email matches, the UI asks for a second explicit confirmation before calling the delete API.
- The delete API is protected with `api:users`, session, `backoffice` role, and the dedicated `users:delete` grant.
- The UI only exposes or enables account deletion for operators whose policy grants include `users:delete`.
- The task adds the `users:delete` grant to RBAC seed/configuration and assigns it only to roles intended to erase accounts.
- The delete API resolves the current app ID and deletes only a user whose `auth.users.app_id` matches that app.
- The delete operation runs server-side in a transaction.
- The implementation uses a core account erasure runner that can execute registered app-specific cleanup hooks before deleting `auth.users`.
- App-specific account erasure hooks are discoverable through optional `src/config/<app-id>/account-erasure.server.ts` convention files, backed by a static or generated server-only registry.
- Quicklist registers an account erasure cleanup handler that deletes projects owned by the target user and dependent project data such as tasks, collaborators, and invites.
- LingoCafe registers an account erasure cleanup handler that deletes user-owned reading state, including current book/chapter progress in `lingocafe.books_progress`.
- The account erasure flow does not delete, anonymize, or otherwise mutate event history.
- Successful admin deletion writes an audit event describing who was deleted, including at least target user ID and email.
- The audit event uses the acting operator as the event user and does not store deleted account data beyond minimal identity.
- The implementation still relies on `ON DELETE CASCADE` where verified and appropriate for related auth, RBAC, session, and app rows.
- The implementation audits current foreign keys that reference `auth.users` and documents which references cascade, set null, or restrict.
- Non-cascading references, especially Quicklist ownership or created_by records that currently restrict deletion, are handled by app-specific hooks or fail with a clear app-level message.
- Successful deletion removes the user from the current list without requiring a full page reload.
- Errors are shown in the existing `/users` error surface or modal without losing the selected user context.
- The implementation prevents deleting the currently signed-in operator with a strong server-side check comparing acting operator user ID to target user ID.
- `npm run qa` passes.

## Dos

- Reuse the shared modal/panel patterns already used by `/users`.
- Add a `DELETE` handler or equivalent explicit delete action on `/api/users`.
- Add a server-only core erasure runner and typed app cleanup handler contract.
- Use optional `account-erasure.server.ts` files in app config folders as the extension convention.
- Keep Quicklist cleanup in Quicklist-owned code and LingoCafe cleanup in LingoCafe-owned code.
- Keep all destructive checks on the server.
- Return clear API errors for blocked deletion, missing user, invalid confirmation email, self-delete prevention, and app mismatch.
- Enforce `users:delete` server-side even if the client hides the delete controls.
- Reject self-delete server-side before running app erasure hooks or deleting `auth.users`.
- Record the deletion audit event only after all destructive work succeeds.
- Add focused tests or manual verification notes for successful cascade and blocked non-cascade cases.

## Don'ts

- Do not leave the existing detail-panel Delete button as an alert stub.
- Do not rely on client-only confirmation checks.
- Do not allow `users:list` alone to delete accounts.
- Do not allow operators to delete themselves.
- Do not catch database foreign-key failures and report them as generic update errors.
- Do not delete users across apps.
- Do not make core account deletion import app table knowledge directly when a registered app handler can own it.
- Do not silently delete or transfer app-owned data outside the registered erasure handlers.
- Do not touch event history.
- Do not put full deleted account payloads, tokens, passwords, profile JSON, consent JSON, or app-owned deleted records into the audit event.
