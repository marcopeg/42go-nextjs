# Plan — QuickList LLM-Guided Reordering

## Goal

Ship a concurrency-safe, LLM-oriented QuickList reorder workflow with persisted per-list sorting instructions, consistent server-side text limits, responsive settings UI, and first-class support in the existing QuickList agent skill.

## Milestones

### Milestone 1 — Establish shared contracts and settings persistence

- [x] Step 1 — Centralize QuickList text and settings rules
  - Achieve: Define one server-compatible contract for 250-character list names, 250-character item text, 4,000-character sorting instructions, Unicode-aware length counting, trimming, clearing, and settings resolution.
  - Create: A QuickList validation/settings module.
  - Modify: Session and bearer-token list/item create, update, and bulk-create validators.
  - Delete: Duplicated 255-character schema limits.
  - Touch points: Zod schemas, existing JSONB `quicklist.projects.settings`, list mode preservation.
  - Validation: Focused unit tests for boundaries, Unicode code points, trimming, and settings resolution.
  - Notes: Reuse the existing `settings` JSONB column; no migration is required.

- [x] Step 2 — Add signed-in sorting-instructions settings support
  - Achieve: Return sorting instructions from list Info and let authorized owners/collaborators update them using ordinary list-settings permissions.
  - Create: No separate persistence table.
  - Modify: Session-authenticated project PATCH and Info GET contracts.
  - Delete: None.
  - Touch points: App/user/list isolation, JSONB updates, freshness timestamps, empty-string clearing.
  - Validation: Contract tests for resolution and server-side limits; build/type verification for route shapes.
  - Notes: The reorder GET exposes instructions; Milestone 6 adds the separate bearer-token read/write resource.

### Milestone 2 — Deliver the concurrency-safe reorder API

- [x] Step 3 — Add reorder representation and precondition helpers
  - Achieve: Build the minimal GET representation and opaque ETag from list name, instructions, item IDs, text, and positions while excluding completion state.
  - Create: Reorder contract/helper module where pure logic improves testing.
  - Modify: Existing ETag utilities only where shared HTTP matching behavior belongs.
  - Delete: None.
  - Touch points: Stable hashing, strict POST schema, one-based gapless ordering, empty lists, `If-Match`.
  - Validation: Unit tests for representation shape, status omission, ETag changes, strict payload validation, and precondition decisions.
  - Notes: Missing/malformed `If-Match` returns 428; stale valid context returns 409.

- [x] Step 4 — Implement GET/POST `/api/quicklists/v1/{listId}/reorder`
  - Achieve: Read all items plus sorting context and atomically apply a complete ID/position order behind bearer-token and per-list API gates.
  - Create: Versioned reorder route.
  - Modify: Shared QuickList reorder logic if extraction prevents drift with `/items/reorder`.
  - Delete: None.
  - Touch points: API project access helper, strict JSON validation, transaction locking, `unnest()`/ordinality bulk update, project freshness, replacement ETag.
  - Validation: Targeted tests plus type/build checks.
  - Notes: Lock the project and reload reorder state inside POST before comparing ETag and mutating.

  - Modify: Shared sorting-instructions request validation and focused contract tests.
  - Delete: None.
  - Touch points: Personal-token authentication, API-enabled-list gating, owner/collaborator settings permission, JSONB settings preservation, 4,000-character server limit.

- [x] Step 11 — Teach instruction-aware sort behavior
  - Achieve: Make the QuickList skill preserve user-supplied sorting guidance for future runs, then reorder from a fresh context.
