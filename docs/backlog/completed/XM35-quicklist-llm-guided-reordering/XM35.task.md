# QuickList LLM-Guided Reordering

## Elevator's Pitch

Give token-authenticated agents one purpose-built QuickList endpoint that returns a complete list together with human-authored sorting instructions and accepts the agent's proposed item order as one authoritative reorder operation.

## Business Gain

A user can describe how a list should be organized once, then let an LLM inspect every item, reason over the requested ordering policy, and write back a deterministic new order without checking, unchecking, renaming, adding, or deleting items.

## Current State

The versioned personal bearer-token API under `/api/quicklists/v1` already exposes list/item CRUD and a low-level `POST /api/quicklists/v1/{listId}/items/reorder` operation that accepts every item ID. QuickList has no persisted, per-list natural-language sorting instructions and no purpose-built resource that gives an LLM the list name, instructions, item text, current position, and a concurrency token before accepting calculated positions. The signed-in list Info page also has no sorting-instructions control. Current session and token API validators generally allow 255 characters for list names and item text; this task standardizes both limits at 250 characters.

## Desired State

Add a dedicated token-authenticated resource at `GET/POST /api/quicklists/v1/{listId}/reorder`. `GET` returns the list identity/name, the persisted sorting instructions, and the complete ordered item set. Every item is included whether active or completed, while completion state is deliberately omitted. Each item exposes only the stable item ID, its text/title, and its current one-based position index. GET also emits an opaque ETag derived from reorder-relevant state: list name, sorting instructions, item IDs, item text, and item positions. Completion state is excluded from the ETag because it is intentionally invisible to this workflow.

`POST` accepts only `{ "items": [{ "id": "item-id", "position": 1 }] }`; it does not receive list metadata, sorting instructions, or item text. It requires the ETag from the preceding GET through `If-Match`, validates that the payload describes the complete current item set exactly once with unique gapless positions, and atomically replaces the full ordering. A stale ETag returns `409 Conflict` without mutation so the caller can fetch and reason again.

Add a **Sorting instructions** action to the signed-in list Info/settings page for every user who may edit ordinary list settings. Activating it opens an editable view titled **Sorting instructions**, using the same responsive interaction pattern as adding a new QuickList item: a modal/dialog on desktop and the established full-screen mobile view/panel on small screens. **Save** persists trimmed plain text as a per-list setting. The server allows at most 4,000 Unicode characters. Empty or whitespace-only input clears the setting, and reorder GET returns an empty string.

Add `GET/POST /api/quicklists/v1/{listId}/sorting-instructions` beside the reorder resource. GET returns only the persisted instruction value. POST accepts only `{ "sortingInstructions": string }`, trims and replaces the durable guidance, and uses the same bearer-token, API-enabled-list, and ordinary owner/collaborator settings permissions as the other personal API operations. Updating instructions changes reorder context, so an agent must fetch a fresh reorder ETag before applying positions.

Standardize QuickList list names and item text at a maximum of 250 Unicode characters. Enforce this server-side on every applicable session-authenticated and bearer-token create, update, and bulk-create path rather than relying on this new read-only reorder representation or client validation.

Update the existing QuickList agent skill, deterministic client, and API reference so an LLM can inspect or replace sorting instructions. A sort request without new guidance uses the stored instructions unchanged. A sort request that includes guidance persists a concise reusable update, fetches fresh reorder context, reasons over all items, and submits only item ID plus position with `If-Match`. The skill handles `409 Conflict` by fetching fresh context and reasoning again rather than retrying a stale payload.

## Definition of Success

With a valid personal bearer token and access to an API-enabled list, the QuickList skill can call one reorder GET, receive the list name, sorting instructions, all items in current order, and a revision ETag, then call the matching POST with `If-Match` plus item IDs and calculated positions. The visible QuickList order changes accordingly, including the relative placement of completed items, while item text and completion state remain unchanged. Concurrent reorder-relevant changes are rejected safely and trigger a fresh reasoning cycle.

## Additional Context

- Proposed GET representation: `{ "list": { "id": "...", "name": "...", "sortingInstructions": "..." }, "items": [{ "id": "...", "text": "...", "position": 1 }] }`.
- Final POST representation: `{ "items": [{ "id": "...", "position": 1 }] }`. No other list or item properties are accepted.
- GET emits the reorder revision through the HTTP `ETag` header; POST sends it through `If-Match`.
- The existing `/items/reorder` primitive may remain for existing clients. The new `/reorder` resource is optimized for LLM read-reason-write workflows and adds sorting instructions.
- Use the existing PostgreSQL bulk-order pattern with `unnest()` and `WITH ORDINALITY`, inside a transaction after validating the full item set.
- List setting persistence requires a forward-only migration or another established QuickList per-list settings mechanism. The sorting instructions must be scoped to the list and app.
- Public UI labels are **Sorting instructions** and **Save**.
- Existing QuickList schemas use 255-character title limits in several session and token API routes. This task intentionally aligns list-name and item-text validation at 250 characters across those paths.

## Assumptions

- The new endpoint belongs to the existing versioned personal bearer-token API and is subject to both valid-token and per-list API-exposure gates.
- The API uses the existing QuickList item title as the returned `text` value.
- Positions are one-based, matching current QuickList storage and API behavior.
- A successful POST is an authoritative full-list reorder, not a partial patch.
- Saving sorting instructions follows the same owner/collaborator permissions as editing ordinary list settings.
- Completed items remain completed; their hidden status is never inferred from or changed by this endpoint.
- The existing `/items/reorder` route remains supported; the new skill workflow uses the richer `/reorder` resource.

## Constraints

- Do not expose completion status, timestamps, collaborator data, API-exposure settings, or unrelated item/list fields from the reorder GET.
- Do not omit completed items from the reorder representation.
- Do not allow POST to rename items, alter completion state, add items, delete items, or move items across lists.
- POST accepts only item ID and position. Reject unknown keys rather than silently treating extra context as writable or ignorable.
- Reject duplicate IDs, unknown IDs, missing current IDs, IDs from another list, duplicate positions, gaps, invalid indexes, and stale/incomplete full-list payloads without applying a partial reorder.
- Preserve QuickList app isolation, bearer-token authentication, API-enabled-list gating, and the represented user's existing list permissions.
- Apply the reorder atomically and update project freshness/ETag inputs so open clients can observe the change.
- Require `If-Match` on reorder POST. Missing or stale reorder context must not mutate positions.
- Do not expose the sorting instructions through an API-disabled list or bypass existing list authorization.
- Use the shared responsive QuickList/modal patterns and keep the authenticated app page client-side.
- Enforce 4,000 characters for sorting instructions and 250 characters for list names and item text at server boundaries. Unicode character counting semantics must be consistent across session and token APIs.

- [x] GET requires a valid personal token, an API-enabled list, and the represented user's existing access to that list.

- [x] GET includes completed and uncompleted items without revealing which are completed.
- [x] Each returned item contains only its ID, text, and one-based position index; unrelated task fields are absent.
- [x] GET emits a standards-compliant opaque ETag derived from list name, sorting instructions, item IDs, item text, and positions, excluding completion state.

- [x] POST accepts only `{ "items": [{ "id": uuid, "position": integer }] }` and rejects extra list metadata, item text, and unrelated fields.

## Dos

- Reuse the personal API authentication and QuickList access helpers delivered by ZC45.
- Reuse or extract the existing transactional reorder logic so the old and new endpoints cannot drift.
- Return a small, stable, LLM-friendly JSON contract.
- Treat item IDs as authoritative identity and positions as the only writable item property.
- Keep list sorting instructions as plain text and validate the 4,000-character maximum server-side.
- Centralize the 250-character list/item limits where practical so session and token APIs cannot drift.
- Use existing responsive QuickList creation/editing primitives and the shared 42Go Modal where applicable.
- Extend the existing QuickList skill instead of creating a second reorder-only skill.
- Document one GET → reason → POST example with ETag/If-Match and without embedding a real token.

## Don'ts

- Do not ask the LLM to infer completed state or filter completed items.
- Do not accept a partial reorder that silently leaves unspecified items in place.
- Do not accept submitted text, sorting instructions, or list metadata in the POST payload.
- Do not duplicate bearer-token or authorization logic.
- Do not make sorting instructions global to the user; they belong to the selected list.
- Do not break existing `/items/reorder` clients unless refinement explicitly chooses a migration.
- Do not retry a stale reorder payload after `409 Conflict`.
